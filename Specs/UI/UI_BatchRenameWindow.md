# Batch Rename Window Specification

`BatchRenameWindow` is the preview-first bulk rename surface for pane selections and folder scopes. It combines macro templates, search/replace, regex replacement, manual names, and Change Case transforms into one validated rename plan before any file-system mutation occurs.

## Launch And Scope

- `cmd/pane/batchRename` opens Batch Rename for the focused pane, or the active pane when focus is outside both panes.
- `cmd/pane/rename` MUST keep the standard single-item rename prompt when the pane scope is exactly one focused file.
- When `cmd/pane/rename` is invoked with multiple selected items, it MUST open Batch Rename directly with that selected set as the target list.
- The standard rename prompt MUST always show a `Batch...` action that closes the prompt without renaming and opens Batch Rename: rooted at the prompted folder when the item is a folder, or seeded with exactly the prompted file when the item is a file. The file target is captured when the prompt opens, so selection changes (e.g. a watcher-driven refresh) while the prompt is open cannot change it.
- The top scope row MUST use the same shared `NavigationView` address-bar presentation as Find Files. The initial root comes from the target pane's current plugin, instance context, and current folder.
- Explicit multi-selection launch uses exactly the selected paths and does not enable recursive scope by default.
- Folder-scope launch supports mask filtering, files/folders toggles, and optional subdirectory traversal. A plain `*.*` mask is treated as the Batch Rename all-items default.
- Folder-scope launch with no explicit target paths collects matching child entries of the root in stable path order for the current preview. When a pane file-system provider is available, collection MUST enumerate through `IFileSystem::ReadDirectoryInfo`; local filesystem scopes may fall back to `std::filesystem` only when provider enumeration cannot be used. Recursive scope includes matching descendants when `Include subdirectories` is enabled, but MUST NOT recurse through directory symlinks, junctions, or other directory reparse points. File rows carry byte size and last-write date/time metadata; folder rows leave size blank. Targets MUST also retain creation-time metadata when the local file system or provider reports it, so `{created:...}` macros expand from collected metadata instead of an empty placeholder.
- Explicit-selection launch on a non-local provider context (archive, cloud) MUST resolve each seeded path's directory flag, size, and timestamps through provider `ReadDirectoryInfo` enumeration of the parent folder. If the provider cannot describe a selected entry, the host MUST preserve the selected path but mark its metadata unknown: do not run local `std::filesystem` probes for that non-local path, do not invent a directory classification, and keep size/date/time/created metadata blank. Local contexts keep the local metadata path.
- Folder-scope target collection runs on a background worker thread (MTA COM) and posts results back through the posted-payload mechanism; stale results from a superseded collection generation are discarded. Collection cancellation is cooperative: the collection loops and provider enumeration honor the window cancel flag. Collection failures other than cancellation are logged through `Debug::Error` and surfaced as a localized status-strip message.

## Window Contract

- The window is an app-owned top-level DxUi window following the Find Files visual density and navigation/header conventions.
- The window MUST remain responsive while collecting targets, recomputing preview, and executing renames. Folder-scope target collection and the provider dispatch phase of execution run on background `std::jthread` workers; explicit-selection seeding (bounded by the selection size) and preview recomputation may stay on the UI thread.
- The footer exposes a `Cancel` button that is enabled only while a collection or execution task is running. Pressing it sets the shared atomic cancel flag honored by `FileSystemShouldCancel`, the collection loops, and the execution layer loop, and switches the status strip to a canceling message.
- While a background task runs, `Rename` is disabled (re-entrancy guard) and the status strip shows a localized collecting or `Renaming {completed} of {total}...` progress message driven by `FileSystemProgress` callbacks and layer-boundary updates.
- Closing the window during a background task requests cancellation and joins the worker before teardown; pending posted payloads are then drained in `WM_NCDESTROY`.
- The window MUST restore persisted Batch Rename rule defaults before creating visible controls and MUST persist close-time state before DxUi child controls are destroyed.
- The window MUST initialize posted-payload tracking during create and drain pending posted payloads during `WM_NCDESTROY` before async collection or execution messages can target it.
- Focusable Batch Rename controls MUST expose stable accessible names and follow DxUi creation-order keyboard traversal. Rules mode starts at `Mask:`, proceeds through scope, mode, rule fields, helper buttons, options, case dropdowns, preview grid, `Hide unchanged`, the `Cancel` button (focusable only while a background task runs), and the enabled `Rename` button.
- Text fields that edit rules own normal text-edit keyboard behavior. Application shortcuts MUST NOT fire while those edit fields have focus.
- Helper menu buttons next to template, search, and replace fields MUST use the shared DxUi menu input contract. Invoking a helper command inserts its text at the caret or replaces the active selection in the owning field.
- The primary action is `Rename`; it is disabled while the current plan has blocking errors.
- The footer MUST show total rows, changed rows, unchanged rows, warnings, and errors.
- The Rules surface exposes user-editable controls for the new-name template, search text, replace text, regex mode, case sensitivity, whole words, replace once, exclude extension, and independent file-name/extension case transforms.

## Settings Persistence

- Batch Rename dialog state lives under `settings.batchRename`.
- The window restores the most recent mask, name template, search text, replacement text, scope flags, regex/options flags, flatten separator, and independent file-name/extension case transforms from `settings.batchRename`.
- On close, the window persists the current root path, scope flags, option flags, flatten separator, case transforms, most-recent-first mask/rule histories, preview grid layout, and preview sort.
- Manual mode text is transient. The multiline manual-name buffer MUST NOT be persisted and MUST NOT be written into rule histories.
- Window placement is stored separately under `settings.windows.BatchRenameWindow`.

## Preview Grid

- The visible preview grid columns are:
  - `Original Name`
  - `New Name`
  - `Size`
  - `Date`
  - `Time`
  - `Path`
- The `Path` column uses the same semantics as the Find Files results grid: it shows the containing folder relative to the window root displayed in the navigation bar (empty for items directly under the root; the absolute parent folder for items outside the root). The cell tooltip shows the absolute path, and context-menu copy and report exports keep absolute paths.
- Sorting the `Path` column MUST sort by the displayed root-relative path text, not by the hidden absolute source path. Equal primary sort keys MUST preserve the existing preview/source order for both ascending and descending sorts.
- The grid uses shared `DxUi::Grid` behavior for virtualization, column resize/reorder, sorting, clipped-cell tooltips, keyboard selection, and accessibility.
- The `Original Name` column MUST render as an icon/text cell. File and folder rows resolve system icon indices through the shared `IconCache`; Fluent file/folder glyphs are the text fallback when a bitmap cannot be produced.
- Blocking and warning row issues are shown through status styling, glyphs, and tooltips rather than a required extra visible column. Rows with errors use the grid error tone; rows with warnings and no errors use the grid warning tone. The `New Name` cell renders a warning/error glyph and its tooltip lists each issue as a localized description followed by the stable issue ID in parentheses, for example `Unknown macro (macro_unknown)`; unknown issue IDs fall back to the raw ID, and unmapped `regex_*` IDs use a generic regular-expression error description.
- Preview row order is the authoritative order for counter macros and manual-mode line mapping.
- The preview grid context menu MUST support copying the clicked row's original name, new name, and source path. It MUST also support copying the full visible preview as tab-separated text with localized column headers in grid column order; tab and newline characters inside copied fields are normalized to spaces.
- When the launch context supplies a reveal callback, the preview grid context menu MUST expose `Reveal in Active Pane`, using the clicked row's source path so the owning pane can navigate to the parent folder and focus the source item.
- When the launch context supplies a reveal callback, activating a preview grid row through double-click or Enter MUST use that row's source path and the same reveal-in-active-pane behavior.
- No-op rows MUST remain visible by default. The footer MUST provide a `Hide unchanged` toggle that filters only the visible preview rows; preview statistics, validation, and execution continue to use the complete plan.

## Rename Rules

- Rule mode applies transformations in this order:
  1. New-name template macro expansion.
  2. Search/replace.
  3. Change Case transforms.
  4. Validation and duplicate detection.
- Canonical macro syntax uses `{macro}`. `$(Macro)` aliases MAY be accepted for compatibility, but helper menus insert canonical tokens.
- Literal braces use `{{` and `}}`.
- Initial macro support includes `{name}`, `{filename}`, `{stem}`, `{ext}`, `{extNoDot}`, `{parent}`, `{relativeFolder}`, `{relativeFolderFlat}`, `{size}`, `{date:yyyy-MM-dd}`, `{time:HH-mm-ss}`, `{created:yyyy-MM-dd}`, `{counter}`, `{counter:000}`, and `{index}`.
- Counter/index pad formats accept an all-zero pattern (`{counter:000}` pads to the pattern length) or a plain numeric width (`{counter:3}` zero-pads to three digits). Any other non-empty format is a blocking `macro_invalid_format` error.
- `{relativeFolder}` expands from the target folder relative to the active Batch Rename root; `{relativeFolderFlat}` uses the same relative folder with path separators replaced by the configured flatten separator.
- Date/time macros format optional target metadata through deterministic tokens (`yyyy`, `MM`, `dd`, `HH`, `mm`, `ss`) rather than reading current UI column text. Timestamps are converted to local wall-clock time before formatting; the engine falls back to UTC fields when time-zone data is unavailable. The preview grid `Date` and `Time` columns MUST use the same shared formatter as `{date}`/`{time}` macros, so a row's macro-expanded date/time text and its metadata columns agree for the same timestamp.
- Unknown macros are blocking validation errors.
- Macro or manual output containing path separators is invalid for v1 because `IFileSystem::RenameItems` accepts leaf names only.
- Search/replace supports literal and `std::wregex` ECMAScript modes. Invalid regex patterns are blocking validation errors. Match-time regex failures (such as MSVC complexity/stack limits on backtracking-heavy patterns) are per-row blocking errors with the stable ID `regex_match_failed` rather than preview crashes.
- Replacement supports ECMAScript replacement tokens such as `$&`, `$1`, `$2`, and `$$` when regex mode is enabled.
- Whole-word regex matching wraps the user pattern in a non-capturing `\b(?:...)\b` group so `$1`, `$2`, ... keep their user-pattern indexes.
- Literal replacement supports case sensitivity, whole-word matching, first-match-only replacement, and exclude-extension mode.
- Whole-word literal replacement MUST NOT accept a match boundary that splits a UTF-16 surrogate pair.
- File name and extension Change Case controls MUST reuse the same transformation logic as `cmd/pane/changeCase`.
- Editing any visible Rules control MUST recompute the preview through the shared `BatchRename::BuildPlan` engine and update the `Rename` enabled state from the resulting validation stats.
- The template helper menu inserts canonical macro tokens such as `{name}`, `{stem}`, `{ext}`, `{counter:000}`, `{date:yyyy-MM-dd}`, and escaped literal braces.
- The regex helper menu exposes only syntax supported by the chosen ECMAScript engine. Unsupported constructs such as non-capturing groups are omitted rather than shown as broken affordances. The selected-text literal helper escapes ECMAScript metacharacters in the current search-field selection before inserting the result; when the selection is empty, it inserts a two-backslash literal skeleton and selects the second slash for immediate overwrite.
- The replacement helper menu inserts ECMAScript replacement tokens including `$$`, `$&`, `$1`, and `$2`. The custom matched-subexpression helper prefixes selected ASCII digits with `$`; when no numeric selection is present it inserts `$1` and selects the `1` for quick overwrite.

## Manual Mode

- The window exposes a `Manual` mode next to `Rules`; switching into Manual for the first time seeds the multiline editor from the current preview `New Name` values.
- Manual mode uses one target leaf name per line.
- Manual line count MUST match the target count before rename can run.
- Empty manual names, `.` / `..`, path separators, Windows-invalid/control characters, reserved DOS device names, target leaf names longer than 255 UTF-16 code units, and duplicate targets in the same parent are blocking preview errors. The leaf-name limit is counted in UTF-16 code units: 255 code units is valid, while 256 code units is `name_too_long`, including leaves where a surrogate pair contributes two code units. Provider-specific filename rules are not preview-validated until a file-system capability exists for them; providers may still reject such names during execution.
- Manual names are exact input except CR removal; leading or trailing spaces are not silently trimmed.
- Editing the manual multiline field MUST recompute the preview through `BatchRename::BuildPlan`, and switching away/back without changing the target set MUST preserve manual text. When the target set changes while Manual mode is active, the existing manual text stays visible and the preview remains blocked until the user reconciles the line count.
- Manual command-row actions include `Fill from preview`, `Clear`, `Paste`, and `Sort like preview`. `Paste` reads Unicode clipboard text into the manual editor without normalizing line endings; preview line mapping removes CR characters while preserving one row per clipboard line.
- `Sort like preview` rewrites the manual editor lines into the current preview sort order computed over the complete target set, independent of the `Hide unchanged` visibility filter, and reorders the transient target mapping for that preview, so each target remains paired with the same manual destination after sorting. The mapping MUST be a bijection over the complete target set; if a row cannot be matched exactly once, the command MUST fail without rewriting the editor.
- Rule-control edits MUST NOT discard the transient manual-name buffer while the target set is unchanged.

## Validation And Execution

### Provider Path Identity

- Batch Rename is a same-provider, same-instance mutation surface. Before preview validation can enable `Rename`, the window MUST resolve the active provider's `pathIdentity` profile from `IFileSystem::GetCapabilities()` as defined in `Specs/Plugins/Plugins_VirtualFileSystem.md`.
- If the provider does not advertise `operations.rename == true`, returns invalid capabilities, omits `pathIdentity`, advertises `pathTextStableIdentity == false`, advertises a `componentComparison` other than `ordinalCaseSensitive`/`ordinalIgnoreCase` (a plugin emitting `unknown` — or any unrecognized value — is a capability contract violation, not a legal state), or advertises a `pathIdentity` field value unsupported by the host helper, Batch Rename MUST fail closed before mutation. The preview MUST show a blocking provider issue (`provider_path_identity_unknown`) or the command MUST be disabled for that provider instance. (`provider_path_identity_unknown` is the host-side blocking issue ID; it does not imply the plugin is allowed to send `componentComparison: "unknown"`.)
- All Batch Rename decisions that answer "same item/path/name?" MUST use the one resolved `FileSystemPathIdentity` profile for the active provider. This includes duplicate-target detection, case-only detection, local/provider destination collision probes, planned-source exemptions, execution dependency and cycle detection, temp-hop rollback matching, per-item outcome pairing when item index is unavailable, post-execution target refresh, directory-move rewrites, cache notifications, and undo/current-path finalization. The success callback is not a path-rewrite site; its target paths follow the raw as-of-execution contract below.
- **Local Windows file system — `ordinalIgnoreCase` everywhere (no per-site variant).** For the local Windows file system (`builtin/file-system`, and the local-equivalent `builtin/file-system-dummy`) the resolved relation is `componentComparison == "ordinalIgnoreCase"`. This **single** Windows ordinal case-insensitive relation — equivalent to `CompareStringOrdinal(left, -1, right, -1, TRUE) == CSTR_EQUAL`, accent- and normalization-sensitive — MUST be applied at **every** site enumerated above. There is exactly one local identity relation; the host MUST NOT mix folds across sites. Concretely, the legacy divergent implementations are forbidden and MUST all route through the one `ordinalIgnoreCase` profile via the shared `FileSystemPathIdentity` helper: duplicate/case-only detection MUST NOT key on `CharUpperBuffW` (uppercase) folding; execution dependency/cycle detection and per-item outcome pairing MUST NOT fold with `LCMapStringEx`/`OrdinalString::FoldCaseInvariant` (invariant lowercase); destination exemption, target refresh, directory-move rewrite, cache notification, and undo finalization MUST NOT use `std::filesystem::path` equality or `_wcsicmp`. When the local pane has no live `IFileSystem` instance (empty plugin id, `context.fileSystem == nullptr`), the host MUST synthesize the default local `ordinalIgnoreCase` profile for preview rather than skipping identity normalization or falling back to a guessed relation.
- Batch Rename code MUST NOT use `CharUpperBuffW`, `LCMapStringEx`, `_wcsicmp`, `std::filesystem::path` equality, raw `==`, or direct `CompareStringOrdinal` at Batch Rename call sites for provider path identity. Those operations are allowed only inside the shared `FileSystemPathIdentity` helper or for non-identity UI text work.
- User text features are separate from provider path identity: macro-name lookup, case-insensitive search/replace when the user turns off "Match case", and grid sorting MAY use UI text semantics, but those helpers MUST NOT be reused for collision, dependency, refresh, cache notification, callback outcome pairing, pane matching, or undo decisions.
- `BatchRename::BuildPlan` MUST receive or otherwise use the active `FileSystemPathIdentity` profile for mutating validation. A pure engine test MUST cover both `ordinalIgnoreCase` and `ordinalCaseSensitive` profiles so `Readme.txt` -> `README.txt` is a case-only warning only under the case-insensitive profile, while sibling targets `A.txt` and `a.txt` are duplicates only under the case-insensitive profile.
- For performance, Batch Rename MAY build folded map keys only through the shared helper. Every folded-key hit that can affect mutation safety MUST be verified with helper equality before it is accepted as an identity match.

- Batch Rename custom messages MUST be reserved in `Common/WindowMessages.h`; the current reserved IDs are `WndMsg::kBatchRenameTaskUpdate`, `WndMsg::kBatchRenameCompleted`, and test-only `WndMsg::kBatchRenameWindowDebug`.
- Batch Rename MUST build a complete preview plan before execution.
- A plan row records source path, original leaf name, proposed new leaf name, file/folder flag, size, row issues, and stable row id.
- Duplicate proposed names in the same parent are compared with the active provider's `pathIdentity.componentComparison`. Case-sensitive providers allow siblings that differ only by case; case-insensitive providers do not.
- Blocking validation issues use stable IDs: `name_empty`, `name_dot`, `name_separator`, `name_invalid_character`, `name_reserved_device`, `name_too_long`, `name_duplicate`, `macro_invalid_format`, and `provider_path_identity_unknown`.
- Proposed leaf names that resolve to classic DOS device names (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM0`-`COM9`, `LPT0`-`LPT9`, bare or followed by any extension, applying Win32 trailing space/dot trimming to the first dot-delimited token) are blocking errors with the stable ID `name_reserved_device`, because `\\?\`-prefixed renames to such names succeed but create un-openable files.
- Warning issues use stable IDs: `name_unchanged` for no-op rows, `name_case_only` for case-only renames, and `name_edge_space_or_dot` for names with leading/trailing spaces or trailing dots.
- The footer validation summary shows total rows, changed rows, unchanged rows, blocking error rows, and warning rows. These counts MUST come from the complete plan through the shared `BatchRename::RecomputeStats` rules: `changedRows` is `newName != originalName`, `unchangedRows` is `newName == originalName`, and an error row is not also counted as a warning row. Window-level contextual validation that appends issues after `BatchRename::BuildPlan` (for example provider identity failure or local destination probing) MUST call `BatchRename::RecomputeStats` before updating Rename enablement, status text, or the execution abort gate.
- Rule-template/search/replace, manual multiline, and mask text edits SHOULD debounce preview recomputation at roughly 150 ms. Explicit helper-menu insertions and command/debug-driven state changes may rebuild immediately.
- For local file-system targets, preview validation MUST mark changed rows as blocking errors when the proposed destination already exists and is not itself a source in the same validated plan under the active provider path identity profile. The stable issue ID is `name_destination_exists`; destination probe failures use `name_destination_probe_failed`.
- Execution MUST skip no-op rows and rename only changed valid rows.
- Execution MUST revalidate before mutating provider state.
- For local file-system targets, execution revalidation MUST fail before dispatch when a changed source is missing or when a changed destination exists and is not itself a source in the same validated plan.
- Local file-system execution revalidation MUST allow case-only leaf changes that point to the same existing source path under the local provider's `ordinalIgnoreCase` identity profile, so provider-level temp-rename handling can preserve the requested casing.
- Execution MUST use `IFileSystem::RenameItems` for same-provider leaf renames when possible. The host marshals changed rows through the shared arena-backed `FileSystemRenameBatch` helper so `FileSystemRenamePair` arrays and their UTF-16 strings obey the plugin arena ownership contract. If a provider reports bulk rename unsupported with `E_NOTIMPL`, `ERROR_CALL_NOT_IMPLEMENTED`, or `ERROR_NOT_SUPPORTED`, the helper MAY fall back to one `IFileSystem::RenameItem` call per changed row. The fallback MUST report `FileSystemItemCompleted` with the submitted item index for every attempted rename (including the failing one) so per-item bookkeeping never mistakes a partial fallback run for a total failure, and MUST honor `FileSystemShouldCancel` between items. Duplicate per-item reports for the same submitted item are benign: the host keeps the last report for that item.
- Each execution attempt MUST pass an `IFileSystemCallback` to the rename helper. `FileSystemShouldCancel` reflects the current Batch Rename cancel state, `FileSystemIssue` defaults to `FileSystemIssueAction::Cancel`, and provider cancellation HRESULTs such as `ERROR_CANCELLED` or `ERROR_OPERATION_ABORTED` MUST produce a retained report with `canceled = true`.
- The provider dispatch phase of execution runs through `BatchRenameExecutionEngine.{h,cpp}` on a background `std::jthread` worker. The worker wrapper initializes MTA COM, keeps the provider owner alive until before `CoUninitialize`, passes the shared `cancelRequested std::atomic_bool&` into the window-free engine, and posts the completion payload back to the UI thread. Plan building, validation, and local revalidation stay synchronous on the UI thread before the worker starts; all bookkeeping (cache notifications, target refresh, report retention, success callback) happens back on the UI thread from the posted completion payload. While execution runs, `Rename` is disabled (re-entrancy guard) and the footer `Cancel` button sets the shared cancel flag.
- Parent/child selections MUST be ordered so child paths are not invalidated by an earlier parent directory rename (deepest-first depth groups).
- Within each depth group, execution MUST be dependency-aware so swap and chain renames admitted by preview validation succeed: an op whose target identifies another pending op's source path under the active provider path identity profile runs only after that source is vacated. A self rename whose target identifies only its own source is not a dependency. Independent ops execute together as one provider batch (which may run in parallel inside the provider); successive dependency layers run sequentially.
- Pure rename cycles (swaps) are broken by first renaming one cycle member to a unique temp name in the same directory (`<original leaf>.rsren-<guid suffix>`), letting the rest of the cycle complete, then renaming the temp entry to its final name. Undo entries and success reporting record only the NET original-to-final transition; temp hops are an implementation detail. A failed temp step surfaces as that row's failure, and an orphaned temp entry is renamed back to its original name on a best-effort basis when its row cannot complete.
- Execution MUST record per-item outcomes from `FileSystemItemCompleted` so a partially failed parallel batch still: records undo entries for the rows that succeeded, notifies `DirectoryInfoCache::NotifyPathMoved` for them, includes them in completed counts, target refresh, and the success callback, and counts only rows that actually failed or never ran as failed. Matching MUST prefer the callback `itemIndex` when it is in range for the submitted batch. Source-path matching is only a fallback and MUST use the active provider path identity profile. Providers that never call `FileSystemItemCompleted` conservatively fall back to all-or-nothing semantics for that batch.
- Successful rows MUST notify `DirectoryInfoCache::NotifyPathMoved`; affected panes then refresh through the same watcher-aware rules used by other file operations. The window refreshes its target list to the renamed paths for every successful row, including rows that succeeded before a later failure or cancellation. Target refresh MUST build a source-to-target-index bucket once, consume at most one still-unrefreshed target index per successful source, and verify every bucket hit with the active provider path identity profile before mutating the target row; duplicate source rows must consume distinct target indexes rather than refreshing the first row repeatedly. When a selected parent directory and child are renamed together, child preview paths and the window's internal target refresh MUST use the child path rewritten under the renamed parent directory. The **success callback**, by contrast, reports each row's path **as of its own rename** (parent moves NOT folded in); consumers replay the parallel source/target pairs sequentially to compute final paths (see the `onSuccessfulRename` contract in `BatchRenameWindow.h` and `FolderWindow::RefreshPanesAfterBatchRename`).
- The pane launch context exposes a successful-rename callback that receives the successful source paths and the corresponding target paths in execution order (parallel lists). Those target paths are each row's as-of-execution target paths, not parent-folded final descendant paths; consumers replay the source/target pairs sequentially when they need fully rewritten descendants. The callback is also invoked on the failure and canceled paths when at least one row renamed, so panes still refresh for the rows that did rename before the batch stopped. Because the window is modeless, `FolderWindow` captures the originating pane's plugin identity (`pluginId` + `instanceContext`) at launch time and matches panes against that captured identity, not against the originating pane's live state. Panes with matching identity whose visible folder matches an affected source or target path/parent under the provider path identity profile are refreshed. A plain local file-system pane whose visible folder lies under a renamed directory is navigated to the corresponding folder under the rename target using the local provider's `ordinalIgnoreCase` profile; if the rewritten path does not exist, the pane navigates to the nearest existing ancestor so it never stays on a dead path.
- Each execution attempt MUST retain a window-level execution report with total planned rows, completed changed rows, skipped no-op rows, failed rows, canceled state, first failure HRESULT, and first failure text when applicable. The status strip shows a localized execution summary after execution and returns to preview counts when the user changes the target set or rename rules. When an execution report exists, the preview context menu MUST expose `Copy Execution Report`, exporting a tab-separated report with total rows, completed rows, skipped rows, failed rows, canceled state, first failure HRESULT, and first failure text.
- View-only preview refreshes (column sorting and the `Hide unchanged` toggle) MUST preserve the retained execution report and its undo plan; the report is cleared only when the plan actually changes (rule edits, manual edits, scope or target-set changes). View-only refreshes MUST reuse the cached full-plan rows, MUST NOT rerun `BatchRename::BuildPlan`, re-probe local destinations, re-resolve preview icons, or rewrite full-plan preview statistics/Rename gating, and MUST stay synchronous rather than using the text-edit debounce timer.
- Each execution report MUST retain an undo-plan artifact for successful changed rows only. The artifact is informational, not an automatic undo command, and MUST be copyable as a tab-separated report with current path, restore leaf name, and original path.
- Execution completion payloads are generation-scoped like collection payloads; stale completions from superseded execution generations MUST be discarded without refreshing targets, retaining a report, notifying cache/panes, or invoking the successful-rename callback.
- Execution progress is surfaced through the window status strip (`Renaming {completed} of {total}...`) from `FileSystemProgress` callbacks and layer-boundary updates. Progress counts are clamped to the visible changed-row total; cycle-breaking temp hops MUST NOT make `completed` exceed `total`. Surfacing long-running execution as a File Operations informational task remains a SHOULD for a future slice.

## Performance Contract

- Batch Rename is perf-sensitive because target collection, preview recomputation, regex validation, grid refresh, and execution can affect interactive file-management latency.
- `BatchRename::BuildPlan` MUST emit `batchrename.preview.build_plan_us` when perf capture is enabled. The metric detail is `rules` or `manual`, `value0` is total preview rows, and `value1` is changed rows.
- Preview planning MUST also emit count metrics `batchrename.preview.rows`, `batchrename.preview.changed`, `batchrename.preview.errors`, and `batchrename.preview.warnings` so large preview runs can be checked without relying only on wall-clock selftest duration.
- Regex-enabled preview planning MUST compile the search regex once per preview generation, before row iteration, and emit `batchrename.regex.compile.us`. The metric detail is `regex`, `whole_words`, or `invalid`, `value0` is total target count, and `value1` is final compiled pattern length.
- Preview validation MUST emit `batchrename.validation.us` around leaf validation, warnings, duplicate detection, and final stats. The metric detail is `rules` or `manual`, `value0` is total row count, and `value1` is blocking error row count.
- Duplicate detection, post-execution target refresh, and provider-selection parent matching MAY cache provider-identity keys only through `FileSystemPathIdentity` helpers, and every key hit that affects safety MUST be verified with helper equality before use. Duplicate detection MUST stay linear for helper-keyable large previews.
- Window-level preview recomputation MUST emit `batchrename.preview.recompute.us` around rules/manual planning. The metric detail is `rules` or `manual`, `value0` is total preview rows, and `value1` is changed rows. Visible preview model/grid refresh MUST emit `batchrename.preview.visible_refresh.us`; the detail is `grid` or `model`, `value0` is visible row count, and `value1` is changed rows. A column sort or `Hide unchanged` toggle MUST emit a visible-refresh metric but MUST NOT increase `batchrename.preview.build_plan_us` or `batchrename.preview.recompute.us`.
- Target collection MUST emit `batchrename.collect.us` and `batchrename.collect.targets` when perf capture is enabled. The duration metric detail identifies the source path (`selection`, `provider`, `local`, `local-fallback`, or `empty-root`), and `value0` carries the collected target count. Folder-scope collection MUST parse and normalize the scope mask once per collection run. Provider directory walks MUST poll cancellation between entries after malformed-buffer bounds checks, never before validating `NextEntryOffset`.
- Execution MUST emit `batchrename.execute.us` and count metrics `batchrename.execute.rows`, `batchrename.execute.completed`, and `batchrename.execute.failed` for each execution attempt. The duration metric detail describes the terminal path, and `value0`/`value1` carry rows-to-execute/completed rows. Post-execution target refresh MUST emit `batchrename.execute.target_refresh_match.us`; `value0` is the successful source count and `value1` is the number of provider-identity candidate comparisons, which must remain linear for all-changed large batches.
- Deterministic preview perf coverage MUST include a 10,000-target synthetic scenario that exercises macro expansion, date/time formatting, literal replacement, and Change Case, with an explicit upper bound asserted from the emitted preview duration metric.
