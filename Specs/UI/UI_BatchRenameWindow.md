# Batch Rename Window Specification

`BatchRenameWindow` is the preview-first bulk rename surface for pane selections and folder scopes. It combines macro templates, search/replace, regex replacement, manual names, and Change Case transforms into one validated rename plan before any file-system mutation occurs.

## Launch And Scope

- `cmd/pane/batchRename` opens Batch Rename for the focused pane, or the active pane when focus is outside both panes.
- `cmd/pane/rename` MUST keep the standard single-item rename prompt when the pane scope is exactly one focused file.
- When `cmd/pane/rename` is invoked with multiple selected items, it MUST open Batch Rename directly with that selected set as the target list.
- The standard rename prompt MUST always show a `Batch...` action that closes the prompt without renaming and opens Batch Rename: rooted at the prompted folder when the item is a folder, or seeded with exactly the prompted file when the item is a file. The file target is captured when the prompt opens, so selection changes (e.g. a watcher-driven refresh) while the prompt is open cannot change it.
- The top scope row MUST use the same shared `NavigationView` address-bar presentation as Find Files. The initial root comes from the target pane's current plugin, instance context, and current folder.
- Explicit multi-selection launch uses exactly the selected paths and does not enable recursive scope by default.
- Folder-scope launch supports mask filtering, files/folders toggles, and optional subdirectory traversal. A plain `*.*` mask is treated as the Batch Rename all-items default.
- Folder-scope launch with no explicit target paths collects matching child entries of the root in stable path order for the current preview. When a pane file-system provider is available, collection MUST enumerate through `IFileSystem::ReadDirectoryInfo`; local filesystem scopes may fall back to `std::filesystem` only when provider enumeration cannot be used. Recursive scope includes matching descendants when `Include subdirectories` is enabled, but MUST NOT recurse through directory symlinks, junctions, or other directory reparse points. File rows carry byte size and last-write date/time metadata; folder rows leave size blank. Targets MUST also retain creation-time metadata when the local file system or provider reports it, so `{created:...}` macros expand from collected metadata instead of an empty placeholder.
- Explicit-selection launch on a non-local provider context (archive, cloud) MUST resolve each seeded path's directory flag, size, and timestamps through provider `ReadDirectoryInfo` enumeration of the parent folder. If the provider cannot describe a selected entry, the host MUST preserve the selected path but mark its metadata unknown: do not run local `std::filesystem` probes for that non-local path, do not invent a directory classification, and keep size/date/time/created metadata blank. Local contexts keep the local metadata path.
- All target collection, including explicit provider selections, runs on an MTA threadpool worker and posts results back through the posted-payload mechanism; `Create` and `SetContext` MUST NOT enumerate or stat provider/local targets on the UI thread. Stale results from a superseded collection generation are discarded. Collection cancellation is cooperative: the collection loops and provider enumeration honor the generation-owned cancel flag. Collection failures other than cancellation are logged through `Debug::Error` and surfaced as a localized status-strip message.

## Window Contract

- The window is an app-owned top-level DxUi window following the Find Files visual density and navigation/header conventions.
- The window MUST remain responsive while collecting targets, recomputing preview, and executing renames. Target collection and debounced preview planning/validation run on module-pinned MTA threadpool workers. Rename execution is owned by an admitted File Operations task and never by a window-owned provider-dispatch thread. Preview generation tokens discard stale worker results.
- The footer exposes a `Cancel` button that is enabled only while a collection or execution task is running. For collection/preview it sets the shared atomic cancel flag; for execution it requests cancellation of the admitted File Operations task. Both paths switch the status strip to a canceling message.
- While a background task runs, `Rename` is disabled (re-entrancy guard) and the status strip shows a localized collecting or `Renaming {completed} of {total}...` progress message driven by `FileSystemProgress` callbacks and layer-boundary updates.
- Closing the window requests cancellation of any admitted rename task but does not join or own its worker. Collection/preview threadpool workers own their provider/context snapshots and module pins, so teardown invalidates their generations and drains posted payloads without waiting for blocked provider I/O; a late task completion is discarded by the posted-payload generation/lifetime gate.
- The window MUST restore persisted Batch Rename rule defaults before creating visible controls and MUST persist close-time state before DxUi child controls are destroyed.
- The window MUST initialize posted-payload tracking during create and drain pending posted payloads during `WM_NCDESTROY` before async collection or execution messages can target it.
- Focusable Batch Rename controls MUST expose stable accessible names and follow DxUi creation-order keyboard traversal. Rules mode starts at `Mask:`, proceeds through scope, mode, rule fields, helper buttons, options, case dropdowns, preview grid, `Hide unchanged`, the `Cancel` button (focusable only while a background task runs), and the enabled `Rename` button.
- Text fields that edit rules own normal text-edit keyboard behavior. Application shortcuts MUST NOT fire while those edit fields have focus.
- Helper menu buttons next to template, search, and replace fields MUST use the shared DxUi menu input contract. Invoking a helper command inserts its text at the caret or replaces the active selection in the owning field.
- The primary action is `Rename`; it is disabled while the current plan has blocking errors.
- The footer MUST show total rows, changed rows, unchanged rows, warnings, and errors.
- The Rules surface exposes user-editable controls for the new-name template, search text, replace text, regex mode, case sensitivity, whole words, replace once, exclude extension, and independent file-name/extension case transforms.

## Settings Persistence

- Batch Rename dialog state lives under `settings.batchRename`.
- The window restores the most recent mask, name template, search text, replacement text, scope flags, regex/options flags, flatten separator, and independent file-name/extension case transforms from `settings.batchRename`.
- On close, the window persists the current root path, scope flags, option flags, flatten separator, case transforms, most-recent-first mask/rule histories, preview grid layout, and preview sort.
- Manual mode text is transient. The multiline manual-name buffer MUST NOT be persisted and MUST NOT be written into rule histories.
- Window placement is stored separately under `settings.windows.BatchRenameWindow`.

## Preview Grid

- The visible preview grid columns are:
  - `Original Name`
  - `New Name`
  - `Size`
  - `Date`
  - `Time`
  - `Path`
- The `Path` column uses the same semantics as the Find Files results grid: it shows the containing folder relative to the window root displayed in the navigation bar (empty for items directly under the root; the absolute parent folder for items outside the root). The cell tooltip shows the absolute path, and context-menu copy and report exports keep absolute paths.
- Sorting the `Path` column MUST sort by the displayed root-relative path text, not by the hidden absolute source path. Equal primary sort keys MUST preserve the existing preview/source order for both ascending and descending sorts.
- The grid uses shared `DxUi::Grid` behavior for virtualization, column resize/reorder, sorting, clipped-cell tooltips, keyboard selection, and accessibility.
- The `Original Name` column MUST render as an icon/text cell. File and folder rows resolve system icon indices through the shared `IconCache`; Fluent file/folder glyphs are the text fallback when a bitmap cannot be produced.
- Blocking and warning row issues are shown through status styling, glyphs, and tooltips rather than a required extra visible column. Rows with errors use the grid error tone; rows with warnings and no errors use the grid warning tone. The `New Name` cell renders a warning/error glyph and its tooltip lists each issue as a localized description followed by the stable issue ID in parentheses, for example `Unknown macro (macro_unknown)`; unknown issue IDs fall back to the raw ID, and unmapped `regex_*` IDs use a generic regular-expression error description.
- Preview row order is the authoritative order for counter macros and manual-mode line mapping.
- The preview grid context menu MUST support copying the clicked row's original name, new name, and source path. It MUST also support copying the full visible preview as tab-separated text with localized column headers in grid column order; tab and newline characters inside copied fields are normalized to spaces.
- When the launch context supplies a reveal callback, the preview grid context menu MUST expose `Reveal in Active Pane`, using the clicked row's source path so the owning pane can navigate to the parent folder and focus the source item.
- When the launch context supplies a reveal callback, activating a preview grid row through double-click or Enter MUST use that row's source path and the same reveal-in-active-pane behavior.
- No-op rows MUST remain visible by default. The footer MUST provide a `Hide unchanged` toggle that filters only the visible preview rows; preview statistics, validation, and execution continue to use the complete plan.

## Rename Rules

- Rule mode applies transformations in this order:
  1. New-name template macro expansion.
  2. Search/replace.
  3. Change Case transforms.
  4. Validation and duplicate detection.
- Canonical macro syntax uses `{macro}`. `$(Macro)` aliases MAY be accepted for compatibility, but helper menus insert canonical tokens.
- Literal braces use `{{` and `}}`.
- Initial macro support includes `{name}`, `{filename}`, `{stem}`, `{ext}`, `{extNoDot}`, `{parent}`, `{relativeFolder}`, `{relativeFolderFlat}`, `{size}`, `{date:yyyy-MM-dd}`, `{time:HH-mm-ss}`, `{created:yyyy-MM-dd}`, `{counter}`, `{counter:000}`, and `{index}`.
- Counter/index pad formats accept an all-zero pattern (`{counter:000}` pads to the pattern length) or a plain numeric width (`{counter:3}` zero-pads to three digits). Any other non-empty format is a blocking `macro_invalid_format` error.
- `{relativeFolder}` expands from the target folder relative to the active Batch Rename root; `{relativeFolderFlat}` uses the same relative folder with path separators replaced by the configured flatten separator.
- Date/time macros format optional target metadata through deterministic tokens (`yyyy`, `MM`, `dd`, `HH`, `mm`, `ss`) rather than reading current UI column text. Timestamps are converted to local wall-clock time before formatting; the engine falls back to UTC fields when time-zone data is unavailable. The preview grid `Date` and `Time` columns MUST use the same shared formatter as `{date}`/`{time}` macros, so a row's macro-expanded date/time text and its metadata columns agree for the same timestamp.
- Unknown macros are blocking validation errors.
- Macro and manual output is a proposed child component. The active provider's typed child-name contract is the sole executable validation/join authority; the host does not impose Windows separator rules on another provider.
- Search/replace supports literal and `std::wregex` ECMAScript modes. Invalid regex patterns are blocking validation errors. Match-time regex failures (such as MSVC complexity/stack limits on backtracking-heavy patterns) are per-row blocking errors with the stable ID `regex_match_failed` rather than preview crashes.
- Replacement supports ECMAScript replacement tokens such as `$&`, `$1`, `$2`, and `$$` when regex mode is enabled.
- Whole-word regex matching wraps the user pattern in a non-capturing `\b(?:...)\b` group so `$1`, `$2`, ... keep their user-pattern indexes.
- Literal replacement supports case sensitivity, whole-word matching, first-match-only replacement, and exclude-extension mode.
- Whole-word literal replacement MUST NOT accept a match boundary that splits a UTF-16 surrogate pair.
- File name and extension Change Case controls MUST reuse the same transformation logic as `cmd/pane/changeCase`.
- Editing any visible Rules control MUST recompute the preview through the shared `BatchRename::BuildPlan` engine and update the `Rename` enabled state from the resulting validation stats.
- The template helper menu inserts canonical macro tokens such as `{name}`, `{stem}`, `{ext}`, `{counter:000}`, `{date:yyyy-MM-dd}`, and escaped literal braces.
- The regex helper menu exposes only syntax supported by the chosen ECMAScript engine. Unsupported constructs such as non-capturing groups are omitted rather than shown as broken affordances. The selected-text literal helper escapes ECMAScript metacharacters in the current search-field selection before inserting the result; when the selection is empty, it inserts a two-backslash literal skeleton and selects the second slash for immediate overwrite.
- The replacement helper menu inserts ECMAScript replacement tokens including `$$`, `$&`, `$1`, and `$2`. The custom matched-subexpression helper prefixes selected ASCII digits with `$`; when no numeric selection is present it inserts `$1` and selects the `1` for quick overwrite.

## Manual Mode

- The window exposes a `Manual` mode next to `Rules`; switching into Manual for the first time seeds the multiline editor from the current preview `New Name` values.
- Manual mode uses one target leaf name per line.
- Manual line count MUST match the target count before rename can run.
- Manual line-count and transform errors are host-owned. Every changed manual name is then validated by the active provider's typed `ValidateChildName`/`JoinPath`/`GetChildNameCollisionKey` contract. Provider-invalid, unsupported, or malformed output is blocking; a provider-valid name remains valid even when Windows would reserve or reject it. Duplicate targets in one typed parent are determined only from provider collision keys.
- Manual names are exact input except CR removal; leading or trailing spaces are not silently trimmed.
- Editing the manual multiline field MUST recompute the preview through `BatchRename::BuildPlan`, and switching away/back without changing the target set MUST preserve manual text. When the target set changes while Manual mode is active, the existing manual text stays visible and the preview remains blocked until the user reconciles the line count.
- Manual command-row actions include `Fill from preview`, `Clear`, `Paste`, and `Sort like preview`. `Paste` reads Unicode clipboard text into the manual editor without normalizing line endings; preview line mapping removes CR characters while preserving one row per clipboard line.
- `Sort like preview` rewrites the manual editor lines into the current preview sort order computed over the complete target set, independent of the `Hide unchanged` visibility filter, and reorders the transient target mapping for that preview, so each target remains paired with the same manual destination after sorting. The mapping MUST be a bijection over the complete target set; if a row cannot be matched exactly once, the command MUST fail without rewriting the editor.
- Rule-control edits MUST NOT discard the transient manual-name buffer while the target set is unchanged.

## Validation And Execution

### Provider Path Identity And Name Feasibility

- Batch Rename is a same-provider, same-instance mutation surface. Before preview validation can enable `Rename`, the window MUST retain `IFileSystemRouteCapabilities`, query typed route facts for `FILESYSTEM_RENAME`, and use the canonical composite child-name helper defined in `Specs/Plugins/Plugins_VirtualFileSystem.md`. Diagnostic capability JSON is never executable authority.
- If the provider does not advertise typed Rename, returns invalid route facts, lacks stable path identity, or returns unsupported/malformed child-name validation, join, or collision output, Batch Rename fails closed before mutation. The preview shows a blocking provider-path/name issue and disables `Rename`.
- All Batch Rename decisions that answer "same item/path/name?" MUST use the one resolved typed provider contract. Path and parent identity use `FileSystemPathIdentity`; child-name feasibility, joined destinations, and duplicate/existing-name identity use provider child-name validation and collision keys. This includes case-only detection, provider destination collision probes, planned-source exemptions, execution dependency and cycle detection, per-item outcome pairing when item index is unavailable, post-execution target refresh, directory-move rewrites, cache notifications, and undo/current-path finalization. The success callback is not a path-rewrite site; its target paths follow the raw as-of-execution contract below.
- **Local Windows file system — `ordinalIgnoreCase` everywhere (no per-site variant).** For the local Windows file system (`builtin/file-system`, and the local-equivalent `builtin/file-system-dummy`) the typed route descriptor resolves `FILESYSTEM_ROUTE_COMPONENT_ORDINAL_IGNORE_CASE`. This **single** Windows ordinal case-insensitive relation — equivalent to `CompareStringOrdinal(left, -1, right, -1, TRUE) == CSTR_EQUAL`, accent- and normalization-sensitive — MUST be applied at every path-identity site enumerated above, while child-name decisions flow through the provider collision-key method. There is exactly one local identity relation; the host MUST NOT mix folds across sites. Concretely, the legacy divergent implementations are forbidden and MUST all route through the shared typed helpers: case-only detection MUST NOT key on `CharUpperBuffW` (uppercase) folding; execution dependency/cycle detection and per-item outcome pairing MUST NOT fold with `LCMapStringEx`/`OrdinalString::FoldCaseInvariant` (invariant lowercase); destination exemption, target refresh, directory-move rewrite, cache notification, and undo finalization MUST NOT use `std::filesystem::path` equality or `_wcsicmp`.
- Batch Rename code MUST NOT use `CharUpperBuffW`, `LCMapStringEx`, `_wcsicmp`, `std::filesystem::path` equality, raw `==`, or direct `CompareStringOrdinal` at Batch Rename call sites for provider path identity. Those operations are allowed only inside the shared `FileSystemPathIdentity` helper or for non-identity UI text work.
- User text features are separate from provider path identity: macro-name lookup, case-insensitive search/replace when the user turns off "Match case", and grid sorting MAY use UI text semantics, but those helpers MUST NOT be reused for collision, dependency, refresh, cache notification, callback outcome pairing, pane matching, or undo decisions.
- `BatchRename::BuildPlan` MUST receive or otherwise use the active `FileSystemPathIdentity` profile for transform-stage case-only and duplicate-source validation. A pure engine test MUST cover both `ordinalIgnoreCase` and `ordinalCaseSensitive` profiles so `Readme.txt` -> `README.txt` is a case-only warning only under the case-insensitive profile. Target-name duplicates are never decided by the pure engine; provider-backed preview tests MUST prove the active provider collision keys are authoritative.
- For performance, Batch Rename MAY build folded map keys only through the shared helper. Every folded-key hit that can affect mutation safety MUST be verified with helper equality before it is accepted as an identity match.
- `FileSystemPathIdentity` keys use invariant, non-expanding simple uppercase folding for ordinary non-ASCII ordinal-ignore-case names. A mapping that cannot be represented safely returns `nullopt`, which requires an `EquivalentPath`/`EquivalentComponent` fallback. This is a documented approximation of the volume-specific NTFS `$UpCase` table; mutation-affecting hash hits are always verified with `CompareStringOrdinal`-backed helper equality.

- Batch Rename custom messages MUST be reserved in `Common/WindowMessages.h`; the current reserved IDs are `WndMsg::kBatchRenameTaskUpdate`, `WndMsg::kBatchRenameCompleted`, `WndMsg::kFileOperationBatchRenameArtifactPrompt`, and test-only `WndMsg::kBatchRenameWindowDebug`.
- Batch Rename MUST build a complete preview plan before execution.
- A plan row records source path, original leaf name, proposed new leaf name, file/folder flag, size, row issues, and stable row id.
- Every changed row retains the provider-owned joined path, source collision key, target collision key, and typed parent path key for that preview generation. Duplicate targets combine parent key plus target collision key; they are not inferred from host case folding or raw leaf text.
- Blocking validation issues include `name_duplicate`, `name_destination_exists`, `name_destination_probe_failed`, `name_dependency_cycle`, `macro_invalid_format`, `source_duplicate`, and `provider_path_identity_unknown`. Provider-invalid names use the provider-probe issue in preview; worker admission preserves the exact provider failure HRESULT.
- Warning issues use stable IDs: `name_unchanged` for no-op rows, `name_case_only` for case-only renames, and `name_edge_space_or_dot` for names with leading/trailing spaces or trailing dots.
- The footer validation summary shows total rows, changed rows, unchanged rows, blocking error rows, and warning rows. These counts MUST come from the complete plan through the shared `BatchRename::RecomputeStats` rules: `changedRows` is `newName != originalName`, `unchangedRows` is `newName == originalName`, and an error row is not also counted as a warning row. Window-level provider validation that appends issues after `BatchRename::BuildPlan` (for example provider identity, child-name, collision, listing, or cycle failure) MUST call `BatchRename::RecomputeStats` before updating Rename enablement, status text, or the execution abort gate.
- Rule-template/search/replace, manual multiline, and mask text edits SHOULD debounce preview recomputation at roughly 150 ms. Explicit helper-menu insertions and command/debug-driven state changes may rebuild immediately.
- For every provider, preview validation MUST mark changed rows as blocking errors when the provider-canonical destination already exists and is not itself a source in the same validated plan. The stable issue ID is `name_destination_exists`; enumeration/name-contract failures use `name_destination_probe_failed`. Validation runs off the UI thread, enumerates each distinct typed parent through `IFileSystem::ReadDirectoryInfo` at most once per preview generation, canonicalizes listing entries through the provider collision-key method, and never issues Local-only `std::filesystem` probes or one synchronous `stat` per row.
- Preview dependency validation MUST mark every exact member of a rename cycle with the blocking issue `name_dependency_cycle`, disable `Rename`, and show guidance to use a temporary intermediate name followed by a second acyclic pass. It MUST NOT silently invent a temporary name or offer execution/recovery for a cyclic plan.
- Execution MUST skip no-op rows and rename only changed valid rows.
- Execution MUST revalidate before mutating provider state.
- The UI admission boundary captures only the immutable originating pane/provider identity, changed
  source-to-leaf mappings, preview-generation provider joined paths/collision keys, Queue/Parallel choice, and completion/progress endpoints. Preview facts are comparison inputs only, never mutation authority. It publishes the
  ordinary File Operations task/card and releases its gated worker without issuing row-proportional
  capability, provider-parent, or object-binding calls. The worker then resolves path capabilities,
  re-queries every source and target child-name contract, rejects preview/worker drift, derives provider parents/destinations, binds every source no-follow, rejects duplicate physical
  objects, proves one identity domain, builds the immutable acyclic dependency schedule, validates the
  complete plan, and
  atomically publishes that immutable plan. Any qualification failure or cancellation completes the
  already-published task through the registered completion path with no plan and no mutation.
- After worker plan publication but before the first mutation, the worker performs one bounded
  selection-sized recheck of every changed source and every unrelated final target. Missing/replaced
  sources and occupied/indeterminate unrelated targets fail the attempt with no renamed row; a target
  occupied by another planned source remains a dependency edge. This is not a window-owned or
  recursive pathname preflight and grants no replacement authority. Later destination races are
  handled per hop by the central typed conflict surface with a freshly bound exact-destination receipt.
- Execution repeats the composite provider child-name query immediately before each conditional rename attempt and Retry. A changed joined path or collision key, provider Invalid, Unsupported, or malformed output stops that row before mutation; no Windows validation or host path joining is a fallback.
- Local file-system execution revalidation MUST allow case-only leaf changes that point to the same existing source path under the local provider's `ordinalIgnoreCase` identity profile, so provider-level temp-rename handling can preserve the requested casing.
- Rename submits the latest generation-complete changed-row envelope to the existing File Operations task surface. The worker materializes one typed `RenamePlan` with `RenameOrigin::BatchRename`; the plan captures qualified provider/context endpoints, ingress identity snapshots, destination intent, one immutable acyclic dependency schedule, and the immutable options snapshot. A cycle rejects the complete plan with `ERROR_CIRCULAR_DEPENDENCY` before any provider mutation. Exact destination authority is bound fresh by the File Operations engine only when a collision must be replaced. The engine owns no-follow revalidation, conflict grants, provider dispatch, cancellation, progress, and typed results. Batch Rename MUST NOT retain a direct `RenameItems`/`RenameItem` executor bypass.
- Every changed row is qualified at its concrete source path. All rows must resolve to the same
  `(pluginId, instanceId, pathProfileId, rootId)` and stable path identity profile; otherwise the
  complete plan is rejected by the published task before mutation. The plan stores comparison-only ingress identity,
  and the worker acquires and cross-checks exact no-follow rename authority when each dependency step
  is reached.
- The dependency scheduler never calls provider `RenameItems` or `RenameItem`. The current engine
  executes every final rename through one retained-authority `RenameIfUnchanged` call and
  publishes one typed result per submitted row. A future provider batch primitive is admissible only
  if it accepts and returns the same exact per-row authority; method availability alone is not enough.
  Cancellation is checked at every dependency layer and conditional-mutation boundary.
- Execution consumes the worker-published immutable plan; it does not rebuild rules, probe the preview synchronously, or reread the live pane after UI capture. Navigating or replacing pane state after publication cannot retarget the captured request. The window receives generation-scoped task/result updates from File Operations, applies cache/pane refresh on the UI thread, disables `Rename` while its task is live, and routes `Cancel`/close to that engine task.
- Parent/child selections MUST be ordered so child paths are not invalidated by an earlier parent directory rename (deepest-first depth groups).
- Within each depth group, execution MUST be dependency-aware so acyclic chain renames succeed: an op whose target identifies another pending op's source path under the active provider path identity profile runs only after that source is vacated. A self rename whose target identifies only its own source is not a dependency. Independent ops share one logical layer, but the current identity-owned executor applies their conditional mutations individually. Unless cancellation is requested, it attempts every row already admitted to the current runnable layer even when an earlier sibling fails or is skipped. A non-completed row does not vacate its source and never unlocks a dependent layer. Successive dependency layers remain sequential.
- Pure rename cycles, including two-name swaps, are blocking plans. Preview identifies every cycle member and disables `Rename`; worker admission independently returns `ERROR_CIRCULAR_DEPENDENCY` before the first mutation. Users resolve a cycle explicitly with a temporary intermediate name and then run a second acyclic pass.
- Execution MUST publish one typed terminal result per changed row. Successful rows alone create undo
  entries, `DirectoryInfoCache::NotifyPathMoved` updates, target refresh, and success-callback pairs.
  A user Skip is `Skipped` with source retained and no destination publication; cancellation records
  every already-committed row truthfully and leaves unstarted rows retained. Provider callbacks may
  refine progress, but cannot replace the engine's source-index/result authority.
- One physical source object may appear in at most one Batch Rename row. Preview marks repeated provider paths with the blocking `source_duplicate` issue on every affected row. Central admission compares the no-follow ingress object snapshots and rejects distinct path aliases or hard links that bind to the same object. It never invents an execution order in which one object is renamed to multiple final names.
- Successful rows MUST notify `DirectoryInfoCache::NotifyPathMoved`; affected panes then refresh through the same watcher-aware rules used by other file operations. The window refreshes its target list to the renamed paths for every successful row, including rows that succeeded before a later failure or cancellation. Target refresh MUST build a source-to-target-index bucket once and verify every bucket hit with the active provider path identity profile before mutating the target row. Duplicate source rows cannot reach this stage. When a selected parent directory and child are renamed together, child preview paths and the window's internal target refresh MUST use the child path rewritten under the renamed parent directory. The **success callback**, by contrast, reports each row's path **as of its own rename** (parent moves NOT folded in); consumers replay the parallel source/target pairs sequentially to compute final paths (see the `onSuccessfulRename` contract in `BatchRenameWindow.h` and `FolderWindow::RefreshPanesAfterBatchRename`).
- The pane launch context exposes a successful-rename callback that receives the successful source paths and the corresponding target paths in execution order (parallel lists). Those target paths are each row's as-of-execution target paths, not parent-folded final descendant paths; consumers replay the source/target pairs sequentially when they need fully rewritten descendants. The callback is also invoked on the failure and canceled paths when at least one row renamed, so panes still refresh for the rows that did rename before the batch stopped. Because the window is modeless, `FolderWindow` captures the originating pane's plugin identity (`pluginId` + `instanceContext`) at launch time and matches panes against that captured identity, not against the originating pane's live state. Panes with matching identity whose visible folder matches an affected source or target path/parent under the provider path identity profile are refreshed. A plain local file-system pane whose visible folder lies under a renamed directory is navigated to the corresponding folder under the rename target using the local provider's `ordinalIgnoreCase` profile; if the rewritten path does not exist, the pane navigates to the nearest existing ancestor so it never stays on a dead path.
- Each execution attempt MUST retain a window-level execution report with total planned rows, completed changed rows, skipped no-op rows, failed rows, canceled state, first failure HRESULT, and first failure text when applicable. The status strip shows a localized execution summary after execution and returns to preview counts when the user changes the target set or rename rules. When an execution report exists, the preview context menu MUST expose `Copy Execution Report`, exporting a tab-separated report with total rows, completed rows, skipped rows, failed rows, canceled state, first failure HRESULT, and first failure text.
- View-only preview refreshes (column sorting and the `Hide unchanged` toggle) MUST preserve the retained execution report and its undo plan; the report is cleared only when the plan actually changes (rule edits, manual edits, scope or target-set changes). View-only refreshes MUST reuse the cached full-plan rows, MUST NOT rerun `BatchRename::BuildPlan`, re-query provider destination contracts/listings, re-resolve preview icons, or rewrite full-plan preview statistics/Rename gating, and MUST stay synchronous rather than using the text-edit debounce timer.
- Each execution report MUST retain an undo-plan artifact for successful changed rows only. The artifact is informational, not an automatic undo command, and MUST be copyable as a tab-separated report with current path, restore leaf name, and original path.
- Execution completion payloads are generation-scoped like collection payloads; stale completions from superseded execution generations MUST be discarded without refreshing targets, retaining a report, notifying cache/panes, or invoking the successful-rename callback.
- Execution progress is surfaced through both the window status strip (`Renaming {completed} of {total}...`) and the ordinary File Operations task card. Progress counts are clamped to the visible changed-row total. Batch Rename always uses ordinary queue/card behavior and never inherits the silent Inline-F2 presentation exception.
- Batch Rename MUST NOT create, read, enumerate, migrate, acknowledge, or delete a durable recovery journal. Existing journal bytes from older builds are ignored and retained exactly as found. The File Operations popup exposes no Batch Rename Resume or Roll back action. The informational undo-plan report remains non-authoritative and is not recovery or G2.

## Performance Contract

- Batch Rename is perf-sensitive because target collection, preview recomputation, regex validation, grid refresh, and execution can affect interactive file-management latency.
- `BatchRename::BuildPlan` MUST emit `batchrename.preview.build_plan_us` when perf capture is enabled. The metric detail is `rules` or `manual`, `value0` is total preview rows, and `value1` is changed rows.
- Preview planning MUST also emit count metrics `batchrename.preview.rows`, `batchrename.preview.changed`, `batchrename.preview.errors`, and `batchrename.preview.warnings` so large preview runs can be checked without relying only on wall-clock selftest duration.
- Regex-enabled preview planning MUST compile the search regex once per preview generation, before row iteration, and emit `batchrename.regex.compile.us`. The metric detail is `regex`, `whole_words`, or `invalid`, `value0` is total target count, and `value1` is final compiled pattern length.
- Preview validation MUST emit `batchrename.validation.us` around leaf validation, warnings, duplicate detection, and final stats. The metric detail is `rules` or `manual`, `value0` is total row count, and `value1` is blocking error row count.
- Duplicate detection, post-execution target refresh, and provider-selection parent matching MAY cache provider-identity keys only through `FileSystemPathIdentity` helpers, and every key hit that affects safety MUST be verified with helper equality before use. Duplicate detection MUST stay linear for helper-keyable large previews.
- Window-level preview recomputation MUST emit `batchrename.preview.recompute.us` when the worker result is applied. The metric detail is `worker-rules` or `worker-manual`, `value0` is total preview rows, and `value1` is changed rows. Typed provider validation emits `batchrename.preview.provider_name_validation.us`, `.provider_name_queries`, `.provider_name_arena_fallbacks`, `.provider_name_rejected`, `.provider_name_key_bytes`, `.destination_directory_listings`, and `.collision_index_retained_bytes`; the listing count is the number of distinct typed parent directories enumerated once for that generation. Visible preview model/grid refresh MUST emit `batchrename.preview.visible_refresh.us`; the detail is `grid` or `model`, `value0` is visible row count, and `value1` is changed rows. A column sort or `Hide unchanged` toggle MUST emit a visible-refresh metric but MUST NOT increase `batchrename.preview.build_plan_us`, `batchrename.preview.provider_name_validation.us`, or `batchrename.preview.recompute.us`.
- Target collection MUST emit `batchrename.collect.us` and `batchrename.collect.targets` when perf capture is enabled. The duration metric detail identifies the source path (`selection`, `provider`, `local`, `local-fallback`, or `empty-root`), and `value0` carries the collected target count. Folder-scope collection MUST parse and normalize the scope mask once per collection run. Provider directory walks MUST poll cancellation between entries after malformed-buffer bounds checks, never before validating `NextEntryOffset`.
- Central admission MUST emit `batchrename.admission.ui_thread_us` for the complete UI capture/task-publication call, `batchrename.admission.wall_us` for end-to-end publication-to-qualified wall time, and `batchrename.admission.worker_wall_us` for worker-only qualification. A 1,024-row Local or deterministic delayed-provider request MUST keep the complete UI metric at or below 50,000 us; row-proportional provider calls on that thread are forbidden. The 50 ms limit is the E4 reference-profile budget derived from a cold attested-run maximum of 28.926 ms with about 1.7x scheduling headroom. Admission also emits `batchrename.admission.ui_capture_us`, capability/bind call counts, zero retained bindings, and cancel-request-to-terminal `batchrename.admission.cancel_latency_us`. `batchrename.admit.us` spans the end-to-end worker-owned qualification; its detail is `accepted` or `not-published`, `value0` is changed-row count, and `value1` is declared cycle count.
- Schedule construction MUST emit `batchrename.schedule.build.us`, `batchrename.schedule.layers`, `batchrename.schedule.cycle_members`, and `batchrename.schedule.retained_index_bytes`. Execution MUST emit `batchrename.execute.us`, `batchrename.execute.rows`, `batchrename.execute.completed`, `batchrename.execute.failed`, `batchrename.execute.mutations`, and `batchrename.execute.journal_writes` for each attempt. An accepted 1,024-row acyclic plan performs exactly 1,024 final mutations and zero journal writes; a cyclic plan reports its exact cycle-member count and performs zero mutations. Post-execution target refresh MUST emit `batchrename.execute.target_refresh_match.us`; `value0` is the successful source count and `value1` is the number of provider-identity candidate comparisons, which must remain linear for all-changed large batches.
- Deterministic preview perf coverage MUST include a 10,000-target non-ASCII synthetic scenario that exercises macro expansion, date/time formatting, literal replacement, Change Case, and asserts zero duplicate-detection fallback rows, with an explicit upper bound asserted from the emitted preview duration metric. A gated-provider window case MUST prove target collection can block while `ShowBatchRenameWindow` returns and the window remains responsive.
