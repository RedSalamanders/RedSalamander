# Shared DirectX UI and Grid Specification

Last updated: 2026-04-26

## Purpose

This document is the authoritative behavior and UI contract for the shared `DxUi` toolkit and `DxGrid`.

The completed closeout record for this migration wave lives at `Specs/Plans/Done/UI_DxUiRemainingMigrationCloseoutPlan.md`. WIP plans are not the source of truth for required behavior.

## Scope

This specification applies to:

- `Common/DxUi/`
- full-window DirectX migrations that use `DxUi::WindowHost`
- the shared virtualized `DxUi::Grid`
- the WinUI-like focus, hover, keyboard, popup, and animation behavior expected from migrated windows
- pilot windows:
  - `Plugins/ViewerSqlite/ViewerSqlite.cpp`
  - `RedSalamander/FindFilesWindow.cpp`

## Core Architecture

- Migrated pilot windows MUST render all visible window content through `DxUi`.
- Migrated pilot windows MUST NOT depend on visible Win32 child controls for buttons, toggles, checkboxes, text fields, combos, status strips, scrollbars, or result surfaces.
- The active migration target is zero visible Win32/comctl chrome across migrated windows. Any still-visible native surface is a deferred removal target, not an accepted end-state.
- The `SysListView32` / `WC_LISTVIEWW` report-surface subset of that broader audit is now explicitly inventoried in `Specs/UI/UI_VisibleComctlAudit.md`, and every remaining hit is classified as migrated fallback or hidden-backing scaffolding rather than an accepted visible native exception on the validated live DX paths.
- The current non-report visible-native inventory recorded in `Specs/UI/UI_VisibleNativeAudit.md` is now empty; any reintroduced visible native surface is a regression, not an accepted end-state DX replacement.
- Hidden helper HWNDs MAY exist only for non-visual plumbing such as the implemented text-input bridge.
- `DxUi::WindowHost` MUST use D3D11 hardware-first creation with WARP fallback, DXGI swap-chain presentation, Direct2D rendering, and DirectWrite text layout.
- Rendering, hit-testing, focus, hover, capture, and animation dispatch MUST remain UI-thread-owned.
- Shared `DxUi::WindowHost` graphics-device singletons MUST remain single-UI-thread-owned; mixed-thread access to the shared D3D11/D2D/DXGI/DirectWrite state MUST fail fast with diagnostics instead of proceeding unsafely.
- Shared app-theme DX palette derivation used by mixed legacy/DX dialog shells MUST come from one shared helper per palette contract rather than from diverging per-window copies.
- `DxUi` controls MUST be composed through a retained control tree rooted under one DirectX host surface per migrated window.
- Preferences-class and dialog-shell migrations SHOULD prefer one shared DX host surface per migrated page or pane over many per-control swap-chain hosts; while multiple child `DxUi::WindowHost` surfaces still exist during migration, they MUST reuse shared graphics-device resources instead of constructing an isolated D3D11/D2D graphics stack per child host.
- Preferences-class shells MUST NOT instantiate hidden page containers or DX child-host trees for inactive pages during initial dialog creation; non-active pages MUST create or attach their active DX page subtree lazily on first activation.
- Hidden or minimized child `DxUi::WindowHost` surfaces MUST NOT keep invalidating, resizing swap chains, or attempting present work until they are effectively visible again.
- Shared `DxUi::WindowHost` graphics resources MUST be released when the last attached host detaches so standalone plugin smoke and process teardown do not depend on DLL-unload or process-exit ordering.
- During the current stabilization milestone, the live Preferences DX shell is intentionally limited to the category tree, a one-host shell surface for the page title/description plus OK/Cancel/Apply footer chrome, the shared page-host background/card surface, and the re-landed direct-host `Preferences.General`, `Preferences.Viewers`, `Preferences.Panes`, `Preferences.HotPaths`, `Preferences.Advanced`, `Preferences.Themes`, `Preferences.Keyboard`, `Preferences.CompareDirectories`, `Preferences.Plugins`, `Preferences.Editors`, and `Preferences.Mouse` page surfaces; the previous hidden pane-container layer is gone and the broader remaining work is now the later architectural collapse from direct-host page surfaces to one active retained page subtree, not a rollback to visible legacy pages.
- Keeping inactive Preferences page subtrees alive after first activation is temporary migration debt, not the target architecture; migrated pages should move toward active-page-only retained ownership, with inactive page subtrees destroyed or detached once their page-local UI state has been preserved.
- Destroy-on-leave is now landed across the full current Preferences page set, and the dedicated page-pane HWND layer is gone. `Preferences.General`, `Preferences.Viewers`, `Preferences.Panes`, `Preferences.HotPaths`, `Preferences.Advanced`, `Preferences.Themes`, `Preferences.Keyboard`, `Preferences.CompareDirectories`, `Preferences.Plugins`, `Preferences.Editors`, and `Preferences.Mouse` now attach their active DX page subtree directly to the shared page host and intentionally report zero created or visible pane-host windows.
- `Preferences.Editors` and `Preferences.Mouse` now attach their active DX note subtree directly to the shared page host and intentionally report zero created or visible pane-host windows while still exposing one visible DX note host and zero visible legacy note statics.
- `Preferences.Editors` and `Preferences.Mouse` now also create their placeholder note content DX-first on the reset path instead of creating visible legacy note statics as backing controls.
- `Preferences.General`, `Preferences.HotPaths`, `Preferences.CompareDirectories`, `Preferences.Advanced`, and `Preferences.Panes` now attach their active DX page subtree directly to the shared page host and intentionally report zero created or visible pane-host windows while still exposing one visible DX page host and zero visible legacy page chrome.
- `Preferences.General` now creates its visible toggle-card content DX-first on the reset path and updates settings directly from DX toggle callbacks instead of relying on visible legacy backing toggles.
- `Preferences.General` no longer builds or mirrors hidden Win32 label/toggle backing controls on the direct-host DX path; the shared page-host DX subtree now owns its labels, descriptions, and toggle state directly from `workingSettings`.
- `Preferences.HotPaths` now does the same for its static/toggle chrome on the direct-host DX path: hidden Win32 slot headers, field labels, and toggle backers are no longer built or mirrored there, and the remaining temporary hidden backers are limited to the edit/frame/browse bridge controls.
- `Preferences.Panes` now does the same for its static/toggle chrome on the direct-host DX path: hidden Win32 section headers, field labels, descriptions, and toggle backers are no longer built or mirrored there, and the remaining temporary hidden backers are limited to the combo/edit frame-control bridges.

The active DX grid rebinds its model when the page width changes so the extension/viewer columns fill the available page width without leaving a broken half-empty surface or stale cached column widths.

The native page-host `WS_VSCROLL`/scroll-info path owns page position, thumb drag, track clicks, and wheel fallback; retained DX page content follows that owner through a scroll-offset-aware DX content surface and MUST NOT add a second internal `ScrollPanel` scrollbar for the same page extent. A `DxUi::ScrollPanel` with its internal scrollbar disabled MAY be used only as the retained DX transform/clip surface.

- Shared Preferences page creation readiness MUST be driven by the real active-page DX/backing state for that page, not by generic `GetWindow(..., GW_CHILD)` heuristics on the shared page host; direct-host pages can legitimately have zero child HWNDs while still being fully initialized, and blank/broken rebuilds are the result if category switches treat child-HWND presence as the page-created signal.
- Shared Preferences page reuse MUST NOT treat stale per-page `_dxState` ownership as sufficient readiness after the shared retained content root has been cleared. Once category switching calls `Panel::ClearChildren()` on the shared page root, any previously visited page MUST rebuild its retained children before syncing or laying out the page again.

- Shared Preferences page-host subtree rebuilds MUST hard-reset the shared retained page surface before binding the next category, including focus, hover, capture, text-input-bridge observer state, the shared content-root children, and any page-local note/card bookkeeping; switching categories without clearing that retained surface can leak stale page content into the next category.

- Child `DxUi::WindowHost` surfaces embedded inside an existing Win32 shell MUST return `MA_ACTIVATE` for `WM_MOUSEACTIVATE` so the first click reaches the retained DX control tree instead of being consumed by shell activation.
- `DxUi::Grid` mouse-selection handlers MUST tolerate delegates that synchronously rebuild, replace, or clear the bound model during `OnGridSelectionChanged(...)`; post-selection mouse handling MUST NOT read stale row/cell state from the pre-callback model after the delegate returns.

Non-duplicate tooltip or infotip text MUST be exposed through the cell UI Automation provider as `UIA_HelpTextPropertyId`. Name/value properties remain reserved for the visible cell content, including icon text, badge text, checkbox state, and color/progress summaries.
- `DxUi::WindowHost` MUST resolve client-area mouse cursors through the retained DX control under the pointer, or through the captured control during capture, instead of leaving discoverability to window-specific Win32 subclasses.
- `DxUi::Grid` header resize hit zones for resizable columns MUST expose the horizontal resize cursor through that shared `WindowHost` cursor path, active column-resize capture MUST keep that horizontal cursor, and ordinary header/body hit zones keep the default cursor.
- If an interactive child `DxUi::WindowHost` surface is wrapped in a Win32 `Static` window, that wrapper MUST use `SS_NOTIFY` so pointer input reaches the subclassed DX host path.
- Window-specific child-host subclasses that forward messages into `DxUi::WindowHost::HandleMessage(...)` MUST keep their subclass refdata in stable owner storage for the full child-HWND lifetime; stack-local or move-invalidated owner addresses are forbidden.
- Retained DX callback lambdas used by dialog/page-owned hosts MUST NOT capture raw dialog state by reference unless that owner lifetime is proven to dominate the host lifetime. Live page callbacks should re-resolve dialog state from a still-valid HWND at callback time or use another equally explicit lifetime-safe indirection.
- `DxUi::WindowHost` accessibility registration MUST use a retained per-HWND target object rather than a raw `WindowHost*` window property so UI Automation providers can outlive UI-thread detach windows without dereferencing freed host storage.
- Shared UI Automation provider entrypoints that resolve retained accessibility targets or host-backed fragments MUST serialize that lookup/dispatch through the retained accessibility-target lock so UIA background-thread callbacks cannot race UI-thread unregister/detach work mid-call.
- Shared UI Automation provider actions that mutate retained DX state or Win32 focus/window lifetime, including `InvokePattern`, `TogglePattern`, `ValuePattern::SetValue`, `RangeValuePattern::SetValue`, selection changes, expand/collapse, and UIA-driven focus changes, MUST execute on the owning host window thread rather than touching the control tree directly from the UIA callback thread.
- While a retained root tree is installed, host observer slots for focus, hover, capture, default button, and cancel button MUST reference controls from that tree only.
- Replacing or detaching the retained root tree MUST clear or invalidate focused, hovered, and captured control pointers before the old tree is destroyed.
- Host-owned non-owning control slots such as default-button, cancel-button, and mnemonic-target references MUST also be revalidated against the live installed tree at use time before invocation.
- Shared draw helpers MUST NOT mutate singleton DirectWrite format objects in place during paint; any alignment, paragraph, or wrapping variants MUST be cached or created as independent formats.

## Robustness And Diagnostics Contract

- Shared `DxUi` behavior MUST remain safe under empty or changing models:
  - empty grids MUST not synthesize row hits for row `0`
  - grids clearing or swapping models mid-interaction MUST cancel resize or hover state instead of dereferencing stale column or model pointers
- Shared empty-state strings such as combo-popup and grid empty messages MUST come from resources, not hardcoded literals.
- Shared keyboard/accessibility-visible strings such as shortcut conflict markers and unassigned-shortcut labels MUST come from resources, not hardcoded literals.
- Device, swap-chain, DirectWrite, Direct2D, and fallback-resource creation failures MUST log with `Debug::Error(...)` or `Debug::Warning(...)` once enough context exists to diagnose the failure.
- Brush acquisition failures MUST prefer a logged fallback path over silent failure so unexpected D2D resource exhaustion does not fail invisibly.
- Shared clipboard reads and writes used by DX-hosted text controls MUST tolerate short-lived clipboard contention by retrying `OpenClipboard(...)` for a bounded period before failing.
- `DxUi::WindowHost` MUST clear the previous Direct2D target before calling swap-chain `ResizeBuffers(...)` so repeated relayout or resize traffic does not spam `DXGI_ERROR_INVALID_CALL` failures while old back-buffer references are still held by the D2D context.
- Hidden or redraw-suppressed DX child hosts MUST defer swap-chain creation and swap-chain resize work until they are visible again; batched shell redraw suppression MUST NOT cause invisible hosts to allocate or resize live swap chains.
- `DxUi::WindowHost` MUST treat `ResizeBuffers(...)` failure as size-dependent-resource invalidation and retry on a later visible render instead of immediately constructing a fresh swap chain on the same resize path.
- `DxUi::WindowHost` MUST also recover from device-loss or shared-graphics reset on a later repaint without leaking resize churn or resize-failure spam; attached-host harness coverage for DPI-change handling and simulated device-loss recovery is part of the shared acceptance contract.
- Batched redraw suppression used by migrated shells such as Preferences MUST also cover DX child hosts created while the redraw block is active; newly created DX hosts MUST NOT visibly reveal themselves one-by-one before the batch is released.
- Preferences redraw-suppression helpers MUST NOT allocate during destructor or redraw-release paths; cleanup and teardown of redraw blocks MUST remain non-throwing.
- Preferences category/page switches MUST keep redraw scoped to the affected shell/page DX hosts; they MUST NOT fall back to dialog-wide erase or redundant category-tree invalidation that causes white flash or unnecessary tree repaint.
- Preferences category/page switches MUST release redraw suppression before invalidating the affected shell/page DX hosts, and they MUST NOT force immediate dialog-wide `RDW_UPDATENOW` redraw passes that reintroduce white flash during rapid pane switching.
- Preferences category/page switches MUST also force an immediate redraw of the newly active pane subtree after redraw suppression is released so nested page-local DX hosts do not briefly show default white HWND background or remain visually stale until a later incidental repaint.
- Preferences layout refreshes for the shell, page host, and active pane MUST skip no-op move or resize work when bounds are unchanged so category switches and scroll-host relayout do not churn gratuitous repaint on fixed DX hosts.

  - a standard edit-combo variant for history/search entry fields

- `DxUi::Checkbox` MUST be the standard checkbox control, not a switch and not a card-row surrogate

## Modern Windows Interaction Contract

`DxUi` MUST feel closer to modern WinUI/XAML controls than to classic common-control chrome, while still honoring the app's existing theme palette and density.

- Input modality MUST be tracked so focus chrome is stronger for keyboard-driven focus and quieter for pointer-driven focus, matching the Preferences dialog behavior contract.
- Toggle and checkbox focus chrome MUST follow the same modality rule as buttons and combos: keyboard-visible focus gets the stronger ring, pointer focus stays quieter, and high-contrast mode keeps focused controls visibly discoverable even when keyboard-focus visibility is off.
- `DxUi::WindowHost` MUST track modifier-key state consistently enough that `Tab` / `Shift+Tab`, default-button routing, popup shortcuts, and keyboard context-menu shortcuts remain predictable and testable.
- `DxUi::WindowHost` native focus loss to a non-descendant HWND MUST retain the logical focused control so `Tab` / `Shift+Tab` can continue from the same retained target when focus returns, while clearing active focus visuals, modifier state, and any active text-input bridge. Hidden text-input bridge blur to an external HWND is a stronger leave-editing signal and MUST clear the focused bridge-backed control and deactivate the bridge; bridge focus transfers back to the host or its descendants MUST keep the focused control and bridge active.
- Hover, pressed, disabled, and focused states MUST transition consistently across buttons, toggles, checkboxes, text fields, combos, tree items, grid rows, and scrollbars.
- `Alt` MUST reveal mnemonic cues, `Tab` / `Shift+Tab` MUST follow a stable and predictable order, and window-level default and cancel actions MUST not fight with focused controls.
- Keyboard-only use MUST be first-class:
  - `Space` activates buttons and toggles the focused checkbox or switch
  - `Enter` activates the default action when no control is focused, or when the focused control does not own Enter
  - `Esc` cancels transient popup state before it cancels the host window
  - `Shift+F10` and the Menu key MUST route through the host and invoke the focused control's context menu
- Shared controls that expose a context menu MUST also support pointer right-click invocation through the same control-level callback contract used by host-routed Menu-key and `Shift+F10` handling.
- Right-click context-menu invocation on toggles and checkboxes MUST move focus but MUST NOT mutate the checked state or fire the toggle callback.
- Right-click or keyboard context-menu invocation on bridge-backed text fields or editable combos MUST keep the hidden text-input bridge active.
- Scrollable controls MUST support wheel, keyboard, scrollbar, and pointer interactions without leaving stale hover, capture, or popup state behind.
- Animations MUST remain lightweight, deterministic, and optional enough to stay legible under reduced-motion expectations; focus, state, and selection cues MUST remain clear without animation.
- `ThemePalette` MUST expose an explicit `reducedMotion` policy bit, and the default shared palette SHOULD derive that bit from the current Windows client-area animation preference so migrated windows follow system motion expectations by default.
- Non-essential DXUI motion such as shared grid spinner frames, indeterminate marquee motion, and header-busy animation MUST degrade to a static presentation when `ThemePalette.reducedMotion` is enabled.
- Native-feeling text-entry affordances such as caret visibility and bridge-owned editor behavior MUST remain intact under reduced motion; reduced motion MUST NOT be implemented by disabling the editing caret or breaking editor feedback.
- Deterministic regression coverage now explicitly locks reduced-motion gating for shared-grid sort-glyph transitions plus spinner, header-busy, and indeterminate marquee animation while keeping focused text-field and editable-combo caret animation active.
- Deterministic regression coverage now also explicitly locks retained-panel animation-tick propagation plus shared-grid tick-request behavior, including the rule that text-only and determinate-progress cells stay static while drawable sort-transition, header-busy, and indeterminate-marquee states request ticks only when they are actually animating.
- Viewer-backed `ThemePalette` derivation MUST carry the live `ViewerTheme` colors through the derived header, border, button, input, scrollbar, hover/pressed, and tooltip chrome instead of leaving those shared control surfaces on generic defaults.

## Button Visual Contract

`DxUi::Button` MUST align with the flat button treatment used by the Preferences dialog and `ThemedControls::DrawThemedPushButton`.

- Idle buttons MUST use a neutral filled surface with no visible outer border.
- Hovered buttons MUST show a subtle neutral border and a slightly stronger fill.
- Pressed buttons MUST keep the border and offset their text by `1 DIP` on both axes.
- Focused buttons MUST draw a subtle inner focus ring instead of a legacy dotted or XOR focus rectangle.
- Disabled buttons MUST dim fill and text without reverting to classic Win32 chrome.
- Dialog-style windows MUST support an explicit primary/default button treatment and host-level Enter activation contract.
- Primary/default buttons MUST use a muted accent-tinted fill closer to modern WinUI/XAML dialog chrome, not a full solid-accent block, while preserving the same hover, pressed, and focused interaction model as neutral buttons.
- Default-button routing MUST remain host-owned so no-focus dialogs and focused controls that do not own Enter can trigger the dialog action without each form reimplementing Enter handling.
- Shared hover-state transitions MUST invalidate the host when the hovered control changes so hover visuals appear immediately without waiting for unrelated repaint triggers.

## Checkbox Visual Contract

`DxUi::Checkbox` MUST be a standard checkbox control rather than a switch or a boxed push-button card.

- Idle checkboxes MUST render a leading checkbox indicator and label with no card treatment.
- Hovered and pressed states MAY add a subtle background tint, but that tint MUST remain weaker than list or grid selection fills.
- Checked state MUST be communicated primarily through the checkbox indicator.
- Focused state MUST use subtle focus chrome without reverting to classic XOR or dotted focus rectangles unless high-contrast requires it.
- Disabled text and indicator colors MUST dim consistently with the rest of the DirectX control stack.
- Focused checkboxes own `Space` for toggling, but they MUST NOT consume
  `Enter` in dialog-style hosts with a default button. `Enter` from a focused
  checkbox must fall through to the host default-button route, matching standard
  Windows dialog behavior and the Find window default-action contract.

## Toggle Contract

- `DxUi::Toggle` is the switch-style boolean control.
- Focused toggles own `Enter` and `Space`; pressing either key toggles the switch and must not fall through to a dialog default button.
- When a migrated window requires switch-style booleans, `DxUi::Toggle` MUST converge on the Preferences switch treatment used by `ThemedControls::DrawThemedSwitchToggle`.
- Switches MUST support keyboard focus, `Space` toggle, left/right semantics where appropriate, pointer hover/press states, and low-contrast focus chrome consistent with the Preferences dialog.
- Empty-text switches used as dedicated switch-only slots inside migrated cards or rows MUST collapse to compact switch-only chrome instead of painting a full-width row slab inside the host bounds.
- Empty-text switches used as dedicated switch-only slots inside migrated cards or rows MUST center the visible switch track within that compact host instead of reusing the text-bearing right-slot geometry unchanged.
- Switches with explicit checked/unchecked state labels MUST reserve the text lane for the active state label even when the primary label text is empty, so migrated surfaces such as `Preferences.Panes` can render stateful switch text without falling back to visible legacy statics or combo surrogates.
- Switches and checkboxes that expose a context menu MUST share the host-routed keyboard and pointer context-menu contract without treating that invocation as a toggle gesture.
- Switches MUST NOT be reused as the default checkbox treatment for ordinary boolean fields that are expected to look like standard Windows checkboxes.

## Migration Gate Contract

- A window MUST NOT migrate until `DxUi` supports every visible control pattern that window depends on.
- Migration waves MUST classify windows into at least these capability buckets:
  - form plus simple report/grid
  - grouped, checkable, or icon-rich report surfaces
  - tree or navigation shell surfaces
  - DX-hosted viewer shells that still use visible Win32 chrome
- Preferences, Connection Manager, and other dialog-like shells MUST meet the modern Windows interaction contract in this spec before they can replace their current Win32 controls end-to-end.
- Later-wave dialog-shell migrations that still leave part of the visible shell on native controls MUST document that remainder explicitly in the migration plan as a deferred removal target instead of leaving the split implicit.
