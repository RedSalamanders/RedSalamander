## Why this plan exists

**Verdict: ship-ready *with fixes* — the core is genuinely solid.** A line-by-line trace of the file-mutating path and the teardown path found **NO reachable wrong-file-renamed, silent-overwrite, lost-file, UAF, deadlock, or undo-corruption bug in normal use.** Verified correct (see "Verified correct" at end): provider renames with `FILESYSTEM_FLAG_NONE` (no `REPLACE_EXISTING` → an existing destination returns `ERROR_ALREADY_EXISTS`, never a silent overwrite); deepest-first ordering + dependency layering + temp-hop swap/cycle breaking are correct; `restoreTempBestEffort` is reached on every failure/cancel/never-ran path; the worker is always cancel+joined before teardown and posted payloads are drained; the pure engine is correct and well-tested.

The defects are concentrated in three classes, none of which is an active data-loss bug *in normal use with in-tree providers* — **but see the Review addendum below: an independent re-verification (2026-06-17) re-rated severity to ≈5 high, found two phantom-success vectors reachable on under-reporting providers (one a mid-flight swap corruption), and corrected several proposed fixes that were wrong or ineffective.** All of which must close before this feature earns a "rock solid, business-critical" sign-off:

1. **Data safety was intact in CODE but under-verified in TESTS.** The single most dangerous recovery path — renaming an orphaned `<leaf>.rsren-<guid>` temp back to its original after a failed/canceled swap — and the close-during-in-flight-task teardown contract now have focused window selftests (T-S0-1/T-S0-2). The remaining data-safety bar is to keep those tests in the Commands battery and close the lower-priority contract/perf gaps below before final sign-off.
2. **One genuine consistency hole on the mutating pipeline.** Batch Rename currently lets engine validation, execution dependency ordering, provider callbacks, cache refresh, and destination probing answer "same path/name?" through different hard-coded relations. Worse, a single hard-coded Windows fold is the wrong abstraction for non-local providers: S3/SFTP are case-sensitive, Microsoft Drive is case-insensitive, FTP must commit to a concrete relation per server (a conservative `ordinalCaseSensitive` default when it cannot prove the instance relation — `unknown` is NOT a legal plugin value), and Google Drive fails closed via `pathTextStableIdentity == false` because display names can duplicate. Because of `FLAG_NONE` the worst case is a spurious `ERROR_ALREADY_EXISTS` partial failure, not an overwrite, but a valid preview failing mid-apply is unacceptable for "rock solid."
3. **Interactive performance does not meet the spec's own 10k-target budget.** Pure VIEW operations (sort-column click, Hide-unchanged toggle) re-run the full `BuildPlan` engine plus ~2 filesystem syscalls per changed row and per-row icon resolution on the UI thread; the post-execution refresh adds an O(success×targets) match. They compound right after a large rename completes.

A residual cluster of latent third-party-provider contract gaps (unreachable with every in-tree provider), engine Unicode/spec edges, and a 5582-line god-object that makes the data-safety-critical execution engine testable only end-to-end round out the work.

**Standing rule for every Truename slice:** a slice is not done because a self-test is green. For each P0/P1 slice the proof must make the *dangerous or slow condition observable* and **FAIL (RED) on the current tree** (or, for a recovery-path test, exercise a body that runs in zero current tests) before the fix, then pass after.

**Cross-cutting first:** the provider path-identity gap (T-S0-0/T-S0-3) and the duplicated leaf/stats/date primitives (T-S1-4) are each one architectural mistake with multiple instances. Fix the **class** (one provider identity helper; one shared formatter/stats core), not the instances.

## Review addendum — corrections before execution (independent re-verification 2026-06-17)

> A second, independent line-by-line re-verification against the working tree (BatchRename `.cpp/.h` unchanged from `c557bc45b`; spec contract since landed in `dc5b81f2b`) confirmed the data-safety **diagnosis** and the two top P0 gaps, but found **several proposed fixes that are wrong, ineffective, or out-of-scope, plus a spec self-contradiction the original framing would have entrenched**. Apply these before executing any slice. Each is reflected inline in the slice text below.
>
> **Severity re-rating: "0 critical, 3 high" is too low. Net ≈ 5 high (one item is critical *as a plan defect*).**
>
> 1. **T-S1-3 is largely WRONG — do not rewrite `onSuccessfulRename`.** Passing the directory-move-rewritten path to `onSuccessfulRename` breaks a **documented + tested + consumer-relied** contract: the raw per-op (as-of-execution) path is intentional. Evidence: header contract `BatchRenameWindow.h:28-33` ("a later parent-directory rename in the same batch is intentionally NOT folded in… Consumers must replay the pairs sequentially"); the **"Contract pin"** test `Commands.SelfTest.BatchRename.cpp:2069-2075` asserting the child under the *pre-rename* parent; and the consumer `FolderWindow::RefreshPanesAfterBatchRename`/`findDescendantRetarget` (`FolderWindow.cpp:2378-2396`) which **already composes the parent move by sequential replay** — feeding it a pre-folded path double-applies and yields a dead path. The `NotifyPathMoved` half is **unproven** and likely *also* not fixed by passing the rewritten path: `NotifyPathMovedLocked` (`DirectoryInfoCache.cpp:1352-1394`) posts *absolute* `RelocateCurrentFolder` impacts computed against the **stale entry key** (keys are not updated between the child and parent calls), so a pinned descendant can be double-relocated regardless of which path is passed. T-S1-3 is rewritten below into a **test-first investigation** + the spec correction.
> 2. **Spec contradiction (own it in T-S1-3):** `dc5b81f2b` made the UI spec require success-callback target rewriting under renamed parents, directly contradicting `:132`, the header, the pin test, and the consumer. The authoritative UI spec has now been corrected to remove success-callback target rewriting from the identity-rewrite list; T-S1-3 must keep that raw callback contract pinned while investigating cache notification.
> 3. **T-S3-2 COM fix originally targeted a parameter that did not exist.** Pre-fix, `RunBatchRenameExecution` took the provider as `const wil::com_ptr<IFileSystem>&` (`BatchRenameWindow.cpp:607`), a **reference**. The owning copy that outlived `coUninit` was the **jthread lambda capture** (`fileSystem` at `4051`, captured by copy at `4063`; collection captured `context=_context` by value at `4125`, `BatchRenamePaneContext::fileSystem` at `BatchRenameWindow.h:22`). "Move the by-value param into a com_ptr after the guard" would have been a **no-op false fix**. Corrected below; T-S3-2 is now implemented.
> 4. **Second phantom-success vector missed by T-S3-2.** Pre-fix, the cycle/swap **temp hop** (`722-744`) decided success purely on `if (FAILED(tempHr))` (`728`) and never inspected `callback.TakeItemOutcomes()`, so a provider returning overall `S_OK` while reporting the lone temp item failed could strand the file and drive the rest of the cycle against a non-existent temp path — *worse* than the per-op-loop hole. This was promoted to **HIGH** and fixed under T-S0-3 with temp-hop coverage.
> 5. **`itemIndex` is discarded at the callback and is layer-relative.** `FileSystemItemCompleted` marks `itemIndex` `[[maybe_unused]]` (`200`) and stores only `{sourcePath,status}` (`213`); the submitted batch is the **per-layer** vector (`761`), so the index must be paired as `layer[outcome.itemIndex]` within the layer loop, not a global op index. Spec `:130` already mandates index-first pairing, so the current source-fold pairing is non-conformant.
> 6. **Capabilities-gate ordering hazard / orphaned cross-feature mandate.** `dc5b81f2b` also made `pathIdentity` **mandatory for all same-context Copy/Move/Delete** (`FileSystem_FileOperations.md:225`), but at addendum time no provider capability JSON emitted it (capability JSON lives in headers too, so do not rely on a `.cpp`-only grep) and the shared parser `FolderWindow.FileOperations.cpp:126-130` checked only `operations`/`concurrency`/`crossFileSystem`. Adding a missing-`pathIdentity` rejection to that shared gate before every provider's JSON emitted the field would **brick all file operations, including local**. T-S0-0a sequenced rename-capable provider JSON ahead of the Batch Rename guard; T-S0-0b owns the remaining non-rename provider declarations plus shared Copy/Move/Delete rollout.
>
> **Net effect on the plan:** T-S1-3 is reduced and re-scoped; T-S3-2's temp-hop + COM bullets are corrected and the phantom-success cluster is promoted to T-S0-3/HIGH; T-S0-0 is split (P0 minimal vs P3 machinery) and gains the ordering hazard; T-S3-1 stays P3 (not a P0-enabler); several proofs gain harness prerequisites that otherwise make them unimplementable.

## Guiding Principle

> **Simple, always working, clear status.** Never leave a user file under a temp name; never block the UI thread on disk I/O for a view-only refresh; one provider path-identity profile from preview through execution; one local-time formatter shared by macros and columns. Prove the dangerous path on the user's route, not just the happy path.

## Normative filesystem comparison decision

The old T-S0-3 framing ("use one ordinal fold everywhere") was incomplete. Batch Rename must not pick one global string relation. It must use the active provider's declared path identity relation.

Authoritative contract now lives in:
- `Specs/Plugins/Plugins_VirtualFileSystem.md` — mandatory `IFileSystem::GetCapabilities().pathIdentity`.
- `Specs/FileSystem/FileSystem_FileOperations.md` — provider matrix with each built-in provider's identity profile.
- `Specs/UI/UI_BatchRenameWindow.md` — Batch Rename fail-closed and one-helper requirements.

Implementation rule:
- Add one shared `FileSystemPathIdentity` helper that parses the provider `pathIdentity` object and exposes component/path equality plus helper-owned map keys.
- All code that decides provider path identity MUST call that helper. Direct `CharUpperBuffW`, `LCMapStringEx`, `_wcsicmp`, `std::filesystem::path` equality, raw `==`, and direct `CompareStringOrdinal` are banned at Batch Rename identity call sites.
- User text features are not provider identity. Case-insensitive search/replace, macro-name lookup, and grid sorting may keep UI text semantics, but they must not feed collision/dependency/refresh/undo decisions.
- If a provider's profile is missing, malformed, `pathTextStableIdentity == false`, carries a `componentComparison` that is not one of the two legal concrete values (a plugin emitting `unknown` is a contract violation, not a legal state), or uses a normalization mode the helper does not implement, Batch Rename fails closed before mutation with `provider_path_identity_unknown` or a disabled command.
- `FileSystemItemCompleted.itemIndex` becomes the primary outcome-pairing key. Source-path equality is only a fallback and must use `FileSystemPathIdentity`.

## Performance / Safety Validation Contract (mandatory)

Every slice that touches destructive-recovery correctness (T-S0-1, T-S0-2) MUST exercise the recovery body and assert **on-disk file state** (original content present, no `.rsren-` leftovers, no half state). Every slice that touches provider path identity, file-mutating ordering, target refresh, callback pairing, cache notification, or pane matching (T-S0-0, T-S0-3, T-S1-2, T-S1-3) MUST assert the resulting on-disk/refresh/callback result, not just counts. Every slice that touches interactive latency (T-S1-1, T-S1-2, T-S3-4) MUST define the protected scenario up front, reuse or add `batchrename.*` metrics, add deterministic selftest coverage, and **archive validation runs under `Specs/TestRuns/<machine>/Commands/<timestamp>/`** with baseline-vs-candidate evidence. Prefer the existing `--commands-selftest` paths; register every new `Test*` in `RunBatchRenameCommandsSelfTestCases`'s `runCase(...)` list — **there is no family-definition table; an unregistered case silently never runs** (cf. the FileOps `kFileOpsFamilyDefinitions` lesson).

### T-S0-3. `[HIGH / reliability — file-mutating pipeline]` Batch Rename identity decisions bypass the provider profile

**Symptom:** A Batch Rename plan can be validated with one relation and executed/refreshed with another. On local Windows-like providers this can surface as rare Unicode fold disagreement; on non-local providers it is a more basic contract error because case-sensitive and case-insensitive providers require different duplicate/dependency decisions. A preview-admitted plan can therefore dispatch a colliding parallel batch and partially fail with `ERROR_ALREADY_EXISTS`, or a case-sensitive provider can be incorrectly blocked from a valid `A.txt` / `a.txt` sibling result.

**Root cause:** Batch Rename has no single provider profile threaded through the engine/window/execution path:
- Engine duplicate-target and case-only checks use `CharUpperBuffW` keys.
- Execution dependency, cycle detection, and outcome matching use `OrdinalString::FoldCaseInvariant`.
- Destination-exists exemptions, target refresh, directory-move rewrites, cache notifications, and callbacks use direct ordinal/equality helpers or nested scans.
- `FileSystemItemCompleted.itemIndex` exists in the plugin callback contract but Batch Rename currently pairs outcomes primarily by folded source path.

> **Intra-host divergence is present TODAY with the single local provider — not only cross-provider.** Three different relations are live on the mutating pipeline: engine `CharUpperBuffW` (uppercase) for duplicate/case-only keys; `OrdinalString::FoldCaseInvariant` (`LCMapStringEx` LCMAP_**lowercase**, `BatchRenameWindow.cpp:690/698/768/779`) for dependency/cycle/outcome pairing; and `CompareStringOrdinal(...,TRUE)` via `PathsEqualIgnoreCase` (`506-511`) for revalidation/exemption/`ApplyExecutedDirectoryMoves`/`_targets`-refresh/`FinalizeUndoEntryCurrentPaths`. These disagree on Unicode edge cases. Outcome pairing is currently fold-*self*-consistent (build and lookup both use `FoldCaseInvariant`), so there is no *live* phantom-success from divergence today — but `ApplyExecutedDirectoryMoves`/undo using the ordinal fold while the executor folded with `LCMapStringEx` can leave a stale undo `currentPath`. Collapsing to one relation is correctness hardening, not just cross-provider plumbing.

**Fix (fix the class):**
1. Thread the active `FileSystemPathIdentity` profile into `BatchRename::BuildPlan` for mutating validation. Keep UI text semantics separate for macro lookup/search/sort. **Null-`fileSystem` local case:** an empty-`pluginId` pane sets `state.fileSystem = nullptr` (`FolderWindow.FileSystem.cpp` ~4137-4148) and `CommandBatchRename` copies it unguarded (`FolderWindow.cpp:2499`); `RebuildPreview` runs `BuildPlan` with no provider to query `GetCapabilities()` from. Resolve by synthesizing a default local `ordinalIgnoreCase` profile for preview (spec table prescribes local = `ordinalIgnoreCase`) OR blocking Batch Rename for that pane in `CommandBatchRename`. Execution already returns `E_POINTER` for this state (`BatchRenameWindow.cpp:3964`), so the gap is **preview-only**.
2. Replace duplicate-target keys, case-only detection, destination planned-source exemptions (both the preview `ApplyLocalDestinationConflictValidation` site AND the separate pre-dispatch `RevalidateLocalRenamePlan` at `~1022`), execution dependency/cycle detection, post-execution target refresh, **`CollectProviderSelectionTargets` folded-leaf/parent maps (`BatchRenameWindow.cpp:1290-1334`, folds at `1299/1312/1328` — the most provider-sensitive site, missing from the original list; note its fabricated-local-metadata fallback at `~1332` ties to T-S2-3)**, cache notifications, and undo/current-path finalization with `FileSystemPathIdentity`. **Do NOT** add "success-callback target paths" here — the success callback keeps RAW per-op paths (see T-S1-3); identity at that site is only the *pairing*, handled by step 3.
3. Extend `BatchRenameItemOutcome` to retain `itemIndex` **AND stop discarding it at the callback** — `FileSystemItemCompleted` currently marks `itemIndex` `[[maybe_unused]]` (`BatchRenameWindow.cpp:200`) and stores only `{sourcePath,status}` (`213`). The submitted batch is the **per-layer** vector (`761`), so `itemIndex` is **layer-relative**: pair as `layer[outcome.itemIndex]` *within the current layer loop* (`~771-784`), NOT a global `ops` index (that mispairs every layer after the first). Fall back to `FileSystemPathIdentity` source-path match only when the index is out of range. (Out-of-order completion is contract-legal — `FileSystem.h` — so index-keying is the robust primary.) Spec `:130` already mandates this; current source-fold pairing is non-conformant.
4. Add the blocking issue `provider_path_identity_unknown` and fail closed **(in Batch Rename only — not the shared file-ops capability gate)** before mutation when the provider profile is not plannable.
5. Use helper-owned keyed maps with key-hit verification ONLY for the genuinely hot maps (T-S1-2 post-exec refresh, T-S3-4 duplicate/dependency on the 10k path). For the small **per-layer** maps (`pendingSourceIndex` `~686`, `statusBySource` `~764` — a handful of entries) prefer a direct `FileSystemPathIdentity::EquivalentPath` comparison over the layer set; no keyed map.

**Required proof:** Tests cover at least three profiles: (1) `ordinalIgnoreCase` blocks duplicate `A.txt`/`a.txt` targets and marks `Readme.txt`→`README.txt` as case-only; (2) `ordinalCaseSensitive` allows `A.txt`/`a.txt` as distinct and does not call it case-only; (3) an unstable (`pathTextStableIdentity == false`) or contract-violating (illegal `componentComparison` such as a plugin-emitted `unknown`) identity disables Batch Rename / emits `provider_path_identity_unknown` before mutation. A parent+child rename and a swap/cycle run must assert cache notification, success callback, target refresh, and undo paths use the same provider identity. Pre-fix RED = mixed hard-coded relations and no provider fail-closed path.
