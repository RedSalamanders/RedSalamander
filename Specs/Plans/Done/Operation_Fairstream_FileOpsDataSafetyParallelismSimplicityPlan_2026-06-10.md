## Why Clearflow's green checkmarks did not end the user reports

Clearflow landed (commits `5bf852933`, `f18332bca`) and its local-path fixes are real: the local plugin merges dir-onto-dir (`CopyDirectoryInternal`, `MovePathInternal` directory-merge exemption), the popup caps conflict prompts at ≤3 primary actions (`BuildConflictActionLayout`), and proportional graph sub-bands exist (`AccumulateStreamHueWeights` → `DrawBandwidthGraph`). The user still sees all three symptoms because the fixes stopped at the path the selftest exercised:

1. **"Copy/move to an existing folder raises *already exists*"** — the top-level local merge works, but four adjacent paths still produce the prompt: (a) **S3** aborts the *whole folder* with top-level `ERROR_ALREADY_EXISTS` on the first colliding object (`ExecuteCopyOrMove` pre-scan) — a verbatim reproduction of the report and a direct violation of the normative merge rule; (b) **Microsoft Drive** move has no merge path at all and `Overwrite` dead-ends on folders; (c) a **READONLY destination folder** (any Explorer-customized folder with `desktop.ini`) makes *move*-merge prompt with AccessDenied while copy-merge does not; (d) per-child file conflicts inside a successful merge reuse the **same generic message** "Destination already exists." with no hint it is a child file — indistinguishable from the old folder-level bug, and re-running a cancelled copy floods the user with them.
2. **"Too many options / too many buttons"** — the caps are honored *mechanically*, but composition still overloads: the conflict card stacks up to 6 interactive elements, `SkipAll` in the More menu is semantically identical to "All similar"+Skip, dead-end actions are offered (Overwrite on file-onto-directory, Retry for deterministic buckets), queued tasks show Pause before they start, and the speed-limit dropdown is the *widest* control on every card.
3. **"4 parallel files don't produce 4 equal surfaces"** — the sub-band fix only activates in the opt-in **Rainbow theme** (`theme.menu.rainbowMode`); default themes always draw one solid fill. Even in Rainbow, completed streams are evicted before their tail bytes are sampled, multi-bucket flushes fall back to a single full-weight hue, and `hash(path) % 360` gives no minimum color separation (for 4 files, all pairwise gaps ≥30° only ~30% of the time). The green `FileOps_ParallelGraphFairColorWeight` selftest is fully synthetic (hand-injected ideal weights, one bucket) and cannot catch any of this.

**Standing lesson for every Fairstream slice:** a slice is not done because a synthetic selftest is green. Each slice's proof must exercise the *real pipeline end-to-end* on the *route the user uses*, and provider-parity slices must run against deterministic provider stubs, not only the local plugin.

## Guiding Principle (applies to every phase)

> **Simple, always working, clear status.**

1. **Always working.** Each slice lands self-contained and shippable; no phase depends on a later phase to be correct.
2. **Simple.** Prefer removing options and special cases over adding them. Deleting a confusing branch beats adding a clever one.
3. **Clear status.** At every moment the user can glance at a task and know: *what is happening and is it OK*. Never two conflicting states at once; never a silent destructive act.
4. **(New for Fairstream) Prove it on the user's route.** Synthetic snapshots and single-provider selftests do not close a slice that exists because the last synthetic test lied.

## Performance / Safety Validation Contract (mandatory, per repo rules)

Every slice that can affect pre-calc, queueing, progress cadence, pause/cancel responsiveness, throughput, lock hold time, or destructive correctness MUST (per `Specs/FileSystem/FileSystem_FileOperations.md` "Performance Validation Contract"):

- name the protected scenario before the slice is considered done,
- add or reuse `FileOps.*` instrumentation,
- add deterministic `--fileops-selftest` coverage,
- archive before/after runs under `Specs/TestRuns/<machine>/FileOps/<timestamp>/`,
- support any perf/correctness claim with archived evidence.

Destructive-correctness slices (Phase 1, Phase 6) additionally MUST include a **byte-for-byte / tree-equality integrity assertion** and an **out-of-tree sentinel assertion**.

## Phase 1 — Stop the data loss (highest priority, verified high-severity)

These five were each confirmed by adversarial verification walking the exact call sequences. They are the reason this plan exists beyond the three user reports.

### 1A. Move fallback deletes files it never copied
`MovePathInternal` (`Plugins/FileSystem/FileSystem.FileOps.cpp`): after the copy phase of a cross-volume (or same-volume merge) move succeeds, the fallback runs `deleteContext.recursive = true; DeletePathInternal(context, source)` — a *fresh recursive enumeration at delete time*, with `useRecycleBin = false`. Any file created in the source during the copy window (downloads, logs, active folders) is permanently destroyed without ever being copied. The loss window is the entire copy duration.
**Fix:** delete only what was actually copied — per-child delete-after-copy or a copied-path set — and finish each directory with non-recursive `RemoveDirectoryW` so a non-empty directory surfaces as `ERROR_PARTIAL_COPY` ("source preserved") instead of silent loss. Never recursively rollback the *destination* after source children were already deleted (same root cause, cancel-during-delete-phase variant).

### 1B. Concurrent cross-FS move bypasses the bridge
`Task::ExecuteOperation` `processIndex` lambda (`FolderWindow.FileOperations.State.cpp`): COPY has the `useCrossFileSystemBridge` branch; MOVE does not — it hands the *source* plugin a destination path in another plugin's namespace. Any 2+ item cross-FS move (default concurrency 4) takes this path; only the serial loop implements bridge copy+delete.
**Fix:** mirror the serial path (bridge `CopyPath` + source `DeleteItem` with `moveCopyCompleted` semantics) in `processIndex`; until then clamp `_perItemMaxConcurrency = 1` for cross-FS moves. Add the missing multi-item cross-FS move selftest.

### 1C. Conflict prompt clobber race misroutes answers
`Task::FileSystemIssue` (`FolderWindow.FileOperations.State.cpp`) sets the prompt unconditionally (`setConflictPromptLocked`) while the concurrent `processIndex` path correctly gates on `_conflictCv.wait(..., !_conflictPrompt.active)`. With parallel streams hitting conflicts simultaneously (near-deterministic after `clearConflictPrompt`'s `notify_all` herd release), one user answer can be applied to a file the user never saw, read as Cancel (spurious whole-task cancel), or lost (stall on the manual-reset event).
**Fix:** gate prompt creation on `!_conflictPrompt.active` under `_conflictMutex` exactly like `processIndex`, re-check the decision cache after the wait, and give each prompt a sequence number that `waitForConflictDecision`/`SubmitConflictDecision` must match. This also unifies one of the three diverged conflict state machines (see backlog).

### 1D. A single "Overwrite" click silently overwrites everything after it
Two cooperating bugs: host `processIndex` retries the whole item with `FILESYSTEM_FLAG_ALLOW_OVERWRITE`, and the plugin makes the grant sticky (`context.allowOverwrite = true`) for the rest of the recursion (sequential) or per-worker (parallel — so prompt counts are scheduling-dependent). The prompt has an explicit **Apply-to-all** toggle whose unchecked state is therefore a lie: one Overwrite during a folder merge replaces every later conflicting file without consent.
**Fix:** modifier actions become **one-shot** — applied to the single conflicting path only (local retry override, never context mutation); subsequent conflicts re-raise `FileSystemIssue`; the host's per-bucket Apply-to-all cache is the *only* broadening mechanism, identical in sequential and parallel modes. Update the spec wording "retry the item allowing overwrite" → "retry the conflicting path allowing overwrite".

### 1E. Reparse-point edge cases that destroy or dangle data
(a) `CopyReparsePointInternal`: overwriting an existing destination *directory* with a reparse point recursively wipes the directory — amplified by 1D's sticky grant; require a separately-raised explicit decision (or fail `ERROR_DIR_NOT_EMPTY`).
(b) `FileSystem::MoveItem`/`MoveItems` never set `reparseRootSourcePath/DestinationPath` (CopyItem does), so intra-tree links in a moved tree keep pointing into the source — which the move then deletes.
**Fix:** set retarget roots in all move entry points; add containment + dangling-link selftests for move (Clearflow 4B covered copy only).

## Phase 2 — Kill the false "already exists" everywhere (user report #1)

- **2A. S3:** `ExecuteCopyOrMove` pre-scan returns top-level `ERROR_ALREADY_EXISTS` on the first colliding destination object — abort-the-folder semantics, then Overwrite bulk-overwrites every collision. Make the pre-scan collect per-object collisions, merge the rest, raise `FileSystemIssue` per colliding object, and reserve hard failure for type mismatches. This is the verbatim user symptom on S3 panes.
- **2B. Microsoft Drive:** `MoveOrRenameItem` returns ALREADY_EXISTS for dir-onto-dir with no merge path and `PrepareOverwriteBackup` rejects folders, so even Overwrite dead-ends. Implement per-child merge (or declare the capability honestly and have the host route through the bridge).
- **2C. READONLY destination folder:** `MovePathInternal` returns ACCESS_DENIED before any merge attempt when the existing destination folder has FILE_ATTRIBUTE_READONLY, then strips the attribute; `CopyDirectoryInternal` ignores it. Skip the readonly check (and never mutate attributes) when `directoryMergeDestination` is true — merging *into* a folder does not replace it.
- **2D. Resume-aware retry:** Retry/Overwrite of a partially processed directory re-enumerates from scratch — duplicate enqueues and spurious ALREADY_EXISTS for already-copied children; re-running a cancelled copy floods the user with child prompts. Make directory retry skip children whose destination matches (size+time), and consider the same identity check for re-runs.
- **2E. Say what actually collided:** child-file conflicts inside a merge currently reuse the generic "Destination already exists." (`conflictBucketToMessageId`) with child paths only in small/clippable text. Add a bucket message variant that names the colliding *child* (new `.rc` strings, indexed placeholders). Document the merge rule in `Common/PlugInterfaces/FileSystem.h` itself — plugin authors implement against the header, and S3/MS Drive prove the spec alone did not reach them. Also fix `IFileSystemDirectoryOperations::CreateDirectory` doc: dir-exists (merge OK) vs file-exists (conflict) must be distinguishable.

## Phase 3 — One-prompt simplicity (user report #2)

The ≤3-primary cap is honored; the overload is composition. Target: conflict card = message + "All similar" toggle + at most 3 buttons, **no More menu at all** for common buckets.

- **3A.** Remove `SkipAll` from emitted actions — it is semantically identical to "All similar"+Skip (both land in `setCachedDecision(bucket, Skip)`). The More menu then disappears for most buckets (it is the only item there today). Keep the enum value for ABI.
- **3B.** Never offer dead-end actions: no **Overwrite** lead for file-onto-directory collisions (it cannot succeed — bridge `ValidateDestinationOverwritePolicy` always fails it), no **Retry** for deterministic buckets (Exists/ReadOnly). Selftest asserts the exact action set per bucket.
- **3C.** Stop clearing the task-global Apply-to-all cache when a *single* item fails its modifier twice (`kMaxCachedModifierAttemptsPerBucket`) — track failed-modifier state per item; only that item re-prompts.
- **3D.** Card diet: no Pause button on not-yet-started (queued) tasks; demote the speed-limit dropdown to compact chevron width (it is currently the widest control on every copy/move card, inverting hierarchy); and fix the real input bug — `HitTest` has no viewport clipping, so scrolled-out card buttons steal clicks aimed at the footer ("Cancel all"!). ## Phase 5 — Performance with proof

- **5A.** Same-volume directory-merge move currently **copies every byte then deletes** (`MovePathInternal` falls back to the full copy engine). Walk the tree and `MoveFileExW` each child into the existing destination, creating missing subdirectories and recursing only where both sides exist. Hours → seconds on large folders, removes the transient 2× disk usage, and shrinks the 1A loss window to near zero on this path.
- **5B.** Recycle-bin batch delete (`DeleteToRecycleBinBatchedCore`, IFileOperation batches up to 1000) is **dead code from the UI**: every route uses `ExecutionMode::PerItem` → one IFileOperation + one dedicated STA thread per item. Route multi-select recycle deletes through bulk `DeleteItems` or batch same-parent items host-side.
- **5C.** Delete throughput: `FlattenDeleteDirectoryTree` opens every entry twice (attributes already in `WIN32_FIND_DATAW`) and **discards the entire flatten** above 200k entries, re-running sequentially. Delete files inline during enumeration (reusing the verified no-follow handle), keep only directories for post-order. Make the cross-volume move's delete phase use the configured delete budget and report visible progress (today: hardcoded sequential, progress-suppressed — a long silent tail users read as a hang).
- **5D.** Storage adaptivity: local volumes report `storageKind = UNKNOWN` with flat `preferredConcurrency = 4` (`FillStorageCharacteristicsLocal`), so HDDs get NVMe-grade fan-out and seek-thrash. Probe `StorageDeviceSeekPenaltyProperty`/bus type, clamp internal concurrency (1–2 for seek-penalty media), and record the kind in diagnostics. Matrix selftest asserts HDD-profile sequential ≥ parallel.
- **5E.** Scheduler health: recursive-copy consumer loops pin shared scheduler workers for the duration of the operation (concurrent ops can stall at zero progress), and nested bridge jobs block workers in `WaitJob` (full-pool occupancy can wedge cross-FS tasks). Schedule queue items as work items (not long-lived loops) and let waiting producers help-execute.
- **5F.** Early admission (Clearflow 5B was claimed but `ThreadMain` still runs `RunPreCalculation` to completion before `ExecuteOperation`): allow transfers to start while pre-calc streams totals in, keeping ETA marked "estimating" until totals stabilize.

## Phase 6 — Security hardening

- **6A.** Delete TOCTOU: recursion verifies a directory by handle, then closes it and re-enumerates **by path** (`DeletePathInternal` → `DeleteDirectoryRecursiveSequential` / `FlattenDeleteDirectoryTree`) — a swap-to-junction in that window deletes link-target content. Enumerate through the verified handle (`GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` or relative opens), or re-verify volume serial + file id before enumerating. Extend the existing injection selftest to cover *all* delete entry points (recycle path, permanent, move's delete phase, overwrite cleanup).
- **6B.** `CopyDirectoryInternal`/`processDirectory` accept an existing destination directory that is a **junction** as a merge target and write through it. Check `IsReparsePoint(destinationAttributes)` and raise an explicit conflict instead.
- **6C.** The copy-into-self guard (`IsSameOrChildPath`) is an ordinal string-prefix test — no canonicalization, defeated by junction/subst aliases, no cycle guard. Canonicalize both sides via opened-handle final-path resolution before comparing.
- **6D.** Bridge temp files (`CopyFileWithBuffer`): predictable name, `CREATE_ALWAYS` without no-follow. Use unpredictable names, `FILE_FLAG_OPEN_REPARSE_POINT`-safe creation, and verify cancel cleanup.

## Phase 7 — Status truth & consistency

- **7A.** Find Files removes result rows when the move/delete task merely **starts** (`CopyOrMoveSelectedResultsToOtherPane` / `DeleteSelectedResults`); a failed task leaves the UI lying. Defer removal to the completion callback (per-task source paths + hr already delivered).
- **7B.** Partially-skipped directories credit **full pre-calc bytes** as completed (percent jumps over skipped children), and `NormalizeCompletedTaskSnapshotForDisplay` forces 100%/"N of N" for succeeded-with-warnings tasks, hiding that items were skipped. Account skipped bytes/items separately and show a skipped count on the completed card.
- **7C.** Canceled outranks Partial in `ResolveTaskStatusKind` and cancel-with-issues can auto-dismiss — recorded warnings become invisible; live snapshots never set `finished`, so a just-finished task briefly renders Running. Keep one status, but make diagnostics reachable after cancel and close the finished gap in `BuildSnapshot`.
- **7D.** Parallel delete aborts everything on the first unopenable child and ignores continue-on-error (`FlattenDeleteDirectoryTree`); record the failure, continue, return `ERROR_PARTIAL_COPY`.
- **7E.** Bridge conflict retry restarts the **entire top-level item** (duplicate transfer of every byte) and prompts once per item where local prompts per file. Raise per-file conflicts from `CopyFileWithBuffer` via the task's issue path; never re-transfer promoted files.
