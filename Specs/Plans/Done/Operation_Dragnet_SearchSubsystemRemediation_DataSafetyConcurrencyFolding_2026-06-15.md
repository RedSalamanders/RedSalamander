## Why this plan exists

The search happy paths are genuinely well-built: spec conformance, WIL/RAII discipline, SQLite parameter binding (no injection), `BEGIN IMMEDIATE`+scope-exit-ROLLBACK transaction framing, the self-destroy `WM_NCDESTROY`/`_dispatchDepth` guard, and immediate first-visible-batch delivery are all correct. The defects are concentrated in failure handling, concurrency lifetime, and folding consistency — exactly the surfaces a green self-test suite that never injects adversarial faults will not catch.

Three findings are **reachable in normal interactive use**: the parallel-scan `condition_variable`-destruction use-after-free (default recursive scan path), the cancelled/invalid-regex Intersect that **silently wipes the user's result set**, and the journal move-in that leaves moved/extracted folders' contents **silently absent from indexed search**. Two more are **liveness/availability** failures (stalled-service hang that freezes the app on window close; symlink-loop OOM in the fallback). The subsystem is **NOT ship-ready** until the P0 block lands.

**Standing rule for every Dragnet slice:** a slice is not done because a self-test is green. For each P0/P1 slice the proof must make the *dangerous condition observable* and **FAIL (RED) on the current tree** before the fix, then pass after. Crash/UAF slices additionally require Application Verifier / ASan validation.

**Cross-cutting first:** four defects are instances of one architectural mistake each. Fix the **class**, not the instance — see Phase P3 (external-count preflight with true OOM still fatal, single invariant fold helper, threadpool ownership model, fault-injection harness). Patching instances individually leaves the class alive.

## 2026-06-20 challenge amendments — architecture to implement

This section supersedes older slice-local fix wording where there is any conflict. The original audit evidence remains useful, but implementation must follow the simpler architecture below so the fixes do not become one-off patches.

### Corrections to the original plan

- **Do not implement "catch `std::bad_alloc` and fall back" as a query-path policy.** Repo guidance treats real OOM as fatal. The safe architecture is to validate every external count and byte length **before** allocation, return `ERROR_INVALID_DATA`, a failing `HRESULT_FROM_WIN32(RPC_S_PROTOCOL_ERROR)`, or a documented preflight `E_OUTOFMEMORY`/ceiling result before `reserve`, and keep actual `std::bad_alloc` fail-fast behavior.
- **Do not add a blanket empty-set guard to `KeepOnlyKeysInResults`.** A successful Intersect with zero matches must legitimately clear the set. The guard belongs at the set-operation transaction boundary: apply Intersect/Subtract only when the operation completed successfully and belongs to the current search epoch.
- **Do not promise hard cancellation inside `std::regex_search`.** The standard regex engine cannot be interrupted cooperatively once a call begins. This plan must use a shared conservative safety validator, per-entry cancellation before/after regex calls, visible `REGEX_REJECTED`/`WARNING_OVERFLOW` degradation, and leave any future hard-time-budget regex engine swap as a separate product decision.
- **Do not archive under an ad hoc `Specs/TestRuns/<machine>/Search/` area unless the test-run README is extended first.** Use the existing `Commands`, `CompareDirectories`, or `SelfTest` archive areas and identify the search scenario in `trace.txt`/case names.
- **Do not make a mega-PR.** Land one slice per commit except where this amendment explicitly pairs slices because the same boundary must be changed together.

### Target architecture

1. **Transactional UI result mutations.**
   - Files: `RedSalamander/FindFilesWindow.cpp`, `RedSalamander/FindFilesWindow.h` if debug payloads need new fields, and resource files only if new user-facing status text is required.
   - Shape: each search has an epoch and an operation context. Result/progress/complete payloads carry the epoch. Find/Append mutate as results arrive; Intersect/Subtract collect keys in a staging set and apply exactly once only when the matching epoch completes with success. Cancelled, stale, invalid-regex, transport-failed, or abandoned operations preserve the previous result set and surface an incomplete-operation status.

2. **Journal replay as a delta transaction.**
   - Files: `Common/LocalSearchIndexCore.cpp`, `Common/SqliteIndexStore.cpp`, and compare selftests.
   - Shape: replay builds a deliberate `JournalDelta` with `deletedIds`, `upsertIds`, and `directoriesToHydrate` as `NodeId`s, never copied `Entry` values. `RENAME_OLD_NAME` removes the old tracked subtree; `RENAME_NEW_NAME` upserts the new tracked location and hydrates newly tracked directories after `RebuildDerivedState`. SQLite applies deletes before upserts, so an in-tree rename can delete the old identity and re-upsert the new one in the same delta without leaving stale rows.

3. **Owned threadpool work, no fire-and-forget stack contexts.**
   - File: `Plugins/FileSystem/FileSystem.Search.cpp`.
   - Shape: replace both parallel scan paths with a small RAII work-batch helper (`CreateThreadpoolWork` + WIL/`unique_any` close, or a `TP_CLEANUP_GROUP` if cleanup-group cancellation is chosen). The coordinator owns work objects and waits/cancels them before any state, context, `condition_variable`, chunk vector, or module pin can be destroyed. `TrySubmitThreadpoolCallback` with raw pointers to stack-owned contexts is forbidden in these two paths after this slice.

4. **One cancelable client pipe I/O layer.**
   - Files: `Common/SearchServiceBroker.cpp`, `Common/SearchServiceBroker.h` only if public options/status are needed, and `Plugins/FileSystem/FileSystem.Search.cpp` for fallback mapping if HRESULTs change.
   - Shape: open client pipes with `FILE_FLAG_OVERLAPPED`; route status, query, rebuild, and compact through shared `ReadExactCancelable`/`WriteExactCancelable`/`ReceiveFrameCancelable` helpers. The helpers wait in bounded slices, poll `CancelCheckFn` where available, enforce per-frame/per-operation deadlines, call `CancelIoEx` on cancel/timeout, and return fallback-eligible HRESULTs for service unavailability. Do not add a query-only special case that leaves status/rebuild/compact able to hang.

5. **Find close is asynchronous when a worker is active.**
   - File: `RedSalamander/FindFilesWindow.cpp`.
   - Shape: `WM_CLOSE` requests cancel, hides/disables the window, records `_closeRequested`, and returns without destroying the owned `HWND` while the worker is active. The worker's completion/quiet-point message lets the UI destroy with `_hWnd.reset()`. Reuse must explicitly join or prove idle before starting a new worker; `std::jthread` move-assignment must never perform a hidden UI-thread join.

6. **Shared invariant text helpers.**
   - Files: `Common/SearchTextHelpers.h/.cpp`, `Plugins/FileSystem/FileSystem.Search.cpp`, `RedSalamander/SearchFallbackEngine.cpp`, `RedSalamander/FindFilesWindow.cpp`, and the folding-only parts of `RedSalamander/FolderViewIncrementalSearch.h`.
   - Shape: content literal folding, result identity, native/fallback name helpers, and in-pane incremental search all call a single invariant Windows-style fold/compare helper. The broader in-pane search performance review remains follow-up scope; the fold divergence does not.

7. **Shared regex validation, conservative by design.**
   - Files: `Common/SearchTextHelpers.h/.cpp`, `Plugins/FileSystem/FileSystem.Search.cpp`, `RedSalamander/SearchFallbackEngine.cpp`.
   - Shape: move safety validation out of the native plugin into common search helpers and use it before native or fallback traversal. Reject known catastrophic constructs and excessive size/depth with the existing single-completion `REGEX_REJECTED` contract. Accept bounded quantifiers only when the parser can prove they are bounded; otherwise prefer a visible reject over a hang. Oversized content must either match a documented capped prefix with `WARNING_OVERFLOW` or report `WARNING_OVERFLOW` and no match; it must not silently look like a clean miss.

### P0 implementation order

1. D-S0-4 result-set transaction and epoch drop. Smallest blast radius; protects user data immediately.
2. D-S0-6 external-count and USN bounds. This removes terminate-on-corruption without changing true OOM policy.
3. D-S0-3 journal delta transaction. Lands after D-S0-6 so corrupt snapshot/SQLite evidence cannot mask rename correctness.
4. D-S0-1 owned threadpool work for both parallel scan paths.
5. D-S0-2 cancelable broker I/O plus asynchronous Find close. Pair with D-S2-4 epoch checks if not already completed by D-S0-4.
6. D-S0-5 fallback loop guard. Pair with D-S1-2/D-S2-7 only if the same fallback enumeration loop is already being rewritten; otherwise keep the commit focused.

Each item starts with a RED selftest/harness that reproduces the dangerous condition on the current tree, then the minimal product change, then the GREEN run archived under the suite's existing `Specs/TestRuns/<ComputerHashName>/<Area>/...` folder.

## Phase P0 — Stop the data loss, crashes, and hangs (blocks ship; slices independent)

### D-S0-1. `[CRITICAL]` `condition_variable`-destruction use-after-free in both parallel scan paths

**Symptom (reachable, default scan path):** Intermittent heap/stack corruption and crashes on the built-in local recursive name-only scan (large trees) and the parallel content-scan path (directories ≥ chunk threshold with content search). Probability rises under load and core count. Because it is a data race on a destroyed sync primitive it can present as silent memory corruption, not a clean crash.

**Root cause:** In `ParallelDirectoryWalkWorkerCallback` (`FileSystem.Search.cpp` ~605-619) the completion guard decrements `state.remainingWorkers` under `state.mutex`, **releases the mutex at the end of the inner scope (~615), then calls `worker->state->cv.notify_all()` (~617) on the now-unlocked state.** The coordinator `SearchDirectoryTreeParallelNameOnly` (~765-876) does not depend on that notify: `ready()`/`workersDone` become true purely from observing `remainingWorkers==0`, and `wait_for(lock, 50ms, ready)` (~777) re-checks on the timeout. So after the last worker releases the mutex (count==0) but before it reaches `notify_all`, the coordinator can acquire the mutex, set `workersDone`, break (~855-858), read `maxActiveWorkers`, and **return — destroying the stack-local `state`/`cv` (~703) and the `workers` vector (~713).** The straggler then calls `notify_all()` on a destroyed `std::condition_variable` and dereferences a destroyed context → UB. Workers are submitted via fire-and-forget `TrySubmitThreadpoolCallback` (~726) with **no cleanup group and no `WaitForThreadpoolWork` anywhere**, so nothing blocks the coordinator from returning mid-notify. `modulePin` (`wil::unique_hmodule`) only ref-counts the DLL, not `state`. **The identical pattern is in the content path:** `ParallelScanWorkerCallback` completion guard (~2055-2072) unlock-then-`notify_all` vs `ParallelEvaluateEntries` stack locals `chunks`/`completionMutex`/`completionCv`/`remainingChunks` (~2178-2181) waited at ~2216-2236.

**Fix:** Do not let the coordinator destroy `state` while any worker can still touch it. Preferred: replace the `TrySubmitThreadpoolCallback` fire-and-forget submissions with coordinator-owned threadpool work objects (`CreateThreadpoolWork` wrapped in WIL/RAII, or a `TP_CLEANUP_GROUP` if cleanup-group cancellation is chosen). The coordinator must signal cancellation on terminal failure, wait for every submitted work item to reach its quiet point, and only then destroy `state`, worker contexts, condition variables, chunk vectors, and module pins. A worker-owned event/latch is acceptable only if the worker performs **no** state/context access after the signal and the coordinator waits all signals before returning; do not keep raw stack-context callbacks without a proven wait. Notify-under-lock alone is insufficient because the 50 ms timeout path can still wake without the final notify. Apply the same helper/pattern to both name-only and content parallel paths; keep `RequestParallelDirectoryWalkStop`/`EnqueueParallelDirectory` notifies as wakeups, not lifetime guarantees.

**Required proof:** A stress selftest that runs the parallel name-only and content scans over a many-worker fixture repeatedly under **Application Verifier / ASan**; RED = the analyzer reports the use-after-free / CV-destruction race on the current tree, GREEN after the fix. Archive the run.

**Status 2026-06-20:** Complete. The name-only parallel directory walk now creates one `CreateThreadpoolWork` item per worker, stores each work handle in a WIL RAII vector before submission, and waits all submitted work callbacks with `WaitForThreadpoolWorkCallbacks` before reading final worker metrics or leaving the stack-owned state scope. The content parallel evaluator uses the same ownership model for each chunk; failed work-item creation falls back to synchronous evaluation for that chunk, and submitted chunks are waited before result draining. Search scan paths no longer pass stack-owned contexts to `TrySubmitThreadpoolCallback`.

### D-S0-2. `[CRITICAL]` Stalled-service broker reads hang the worker forever and freeze the app on window close

**Symptom:** A search service that accepts the connection then stalls (deadlock, paging, long SQLite/scan) blocks the Find worker in `ReadExact` indefinitely; the search can never be cancelled. Because window close joins that worker **synchronously on the UI thread**, closing the Find window — and, with the pump blocked, the whole application — hangs with no recovery but killing the process. Violates `Core_Search.md` §148/§243 ("UI thread must never block on service calls"; "fall back safely when the service is … hung").

**Root cause:** The client pipe is opened synchronous/blocking — `CreateFileW(... FILE_ATTRIBUTE_NORMAL ...)` with no `FILE_FLAG_OVERLAPPED` (`SearchServiceBroker.cpp` ~1048); `ReadExact` (~686-707) loops on blocking `::ReadFile(..., nullptr)` with **no timeout**; `ReceiveFrame` (~757-784) builds on it. In `Query` (~2406-2425) `cancelCheck` is polled only at the **top** of each loop iteration, *before* the blocking `ReceiveFrame`. The cancel path is a pure atomic-flag poll (`Cancel()` stores a bool; `FileSystemSearchShouldCancel`) — a flag cannot interrupt a blocked `ReadFile`. There is no `CancelSynchronousIo`, no overlapped read + cancel event, no client-side watchdog (the only overlapped/`CancelIoEx` machinery is server-side). Teardown: `WM_CLOSE` → `OnClose` (~4359) → `_session.Shutdown` (~4372) → `Cancel()` + unconditional `_worker.join()` (~2338-2344), all on the UI message thread. **Same-slice hazard:** `std::jthread` is move-assigned over a still-joinable previous worker in `Start()` (~2304-2331), hiding an implicit `join()` on the UI thread.

1. Replace client-side blocking pipe helpers with shared overlapped helpers used by `GetStatus`, `Query`, `RequestRebuild`, and `RequestCompact`: open with `FILE_FLAG_OVERLAPPED`, wait in bounded slices, poll `CancelCheckFn` where available, enforce a per-frame and overall operation deadline, call `CancelIoEx` on cancel/timeout, and translate timeout/broken/malformed transport to existing service-fallback HRESULTs (`ERROR_SEM_TIMEOUT`, `ERROR_BROKEN_PIPE`, failing `HRESULT_FROM_WIN32(RPC_S_PROTOCOL_ERROR)`, etc.).
2. Keep the fallback boundary in `Plugins/FileSystem/FileSystem.Search.cpp`: a service timeout or protocol error sets `FILESYSTEM_SEARCH_WARNING_SERVICE_UNAVAILABLE`, cools down the service pipe, and reroutes to `local-index` or `scan` without losing already visible UI responsiveness.
3. Move the worker join off the UI thread: `WM_CLOSE` records `_closeRequested`, disables/hides the window, requests cancel, and returns while the worker is active. The worker completion/quiet-point payload must carry the search epoch; the UI drops stale payloads and destroys the owned window with `_hWnd.reset()` only after the current worker is idle.
4. Add an explicit idle-or-join-before-reuse path in `Start()` so `std::jthread` move-assignment cannot implicitly join on the UI thread.

**Required proof:** Compare-selftest with a foreground service fixture that accepts then stalls mid-`Query` → client returns a fallback-eligible error and the search degrades (asserts `WARNING_SERVICE_UNAVAILABLE`); commands-selftest with a deliberately slow-cancel path asserts window close completes within a bounded ms budget and surfaces a `find.ui.*` teardown metric. ### D-S0-3. `[CRITICAL+HIGH]` Journal-replay rename pipeline is structurally incomplete (move-in not indexed; move-out leaves stale rows)

**Root cause:** In `ReplayJournal` (`LocalSearchIndexCore.cpp`):
- **Move-in (~2693-2729):** `directoriesToHydrate` (~2612) captures an `Entry` *value copy* whose `fullPath` is always empty (the create branch ~2680-2686 never sets `fullPath`, and the push fires only on `!wasTracked` so the `find` at ~2675 already missed). `RebuildDerivedState` mutates only the in-map entries (~1942) and `pathIndex` (~1985), not the copies. The hydration loop (~2711) looks the directory up by `FoldPathKey(directory.fullPath)` with `fullPath==""`, which resolves to the process CWD, never a tracked key → `continue` skips hydration for **every** moved-in directory, so `HydrateDirectorySubtree` (~2719) is dead. The directory node itself is indexed; its pre-existing children (which emit no `CREATE` journal records) are not.

1. **Move-in:** store only `NodeId`s in `directoriesToHydrate`; after `RebuildDerivedState`, resolve the fresh `fullPath` by id from `volume.entries` (skip if absent/empty), then `HydrateDirectorySubtree`. Bound the hydration recursion and honor `cancelCheck`.
2. **Move-out:** decide upsert-vs-remove by testing **NEW-parent-tracked before `wasTracked`**. When a tracked entry's new parent is not tracked (and `record.id != trackedRootId`), call `RemoveSubtree` and record ids in `deletedIds` regardless of `wasTracked`; verify `ApplyJournalDelta` deletes on the normal (existing-volume) path.
3. Handle `RENAME_OLD_NAME` deliberately instead of leaving it as a no-op. Treat the old-name record as removal of the previously tracked identity; let the following `RENAME_NEW_NAME` record upsert the new tracked identity and hydrate newly tracked directories. The SQLite delta must delete first and then upsert, so in-tree renames end in the new path, move-out ends deleted, and move-in hydrates pre-existing children.

**Required proof:** Compare-selftests via the `RunIndexedNameQuery` harness over BOTH snapshot and SQLite stores: `move-in-hydrates-children`, `unzip-into-indexed-root`, `move-out-removes-stale-row`, `in-tree-rename-still-upserts`, each asserting no full root rebuild / no NTFS enumeration fallback occurred. ### D-S0-4. `[CRITICAL]` Cancelled/failed Intersect or Subtract silently corrupts or wipes the curated result set

### D-S0-6. `[P0]` Untrusted/oversized counts reserved before validation → `std::terminate` (process abort)

**Symptom:** A corrupt/truncated local snapshot header, or a malformed/torn/hostile `QueryBatch` frame from the service, aborts the **entire file-manager process** via `std::terminate` instead of self-healing (rebuild) or cleanly falling back. ## Phase P1 — Reliability, performance, and correctness (each independent)

### D-S1-1. `[HIGH]` Every read query takes a write transaction; prefix search can't use its index

**Root cause:** `EnumerateVolume`/`InspectVolume`/`LoadVolume` (the hot read paths, `SqliteIndexStore.cpp` ~1939/1989/2639-2727) call `EnsureBootstrap` (~1833-1884), which opens a `READWRITE|CREATE` connection and runs `EnsureSchema → EnsureSchemaVersion2(db,false)` (~1054-1164). On an already-v2 DB that function still runs `BEGIN IMMEDIATE` + meta `UPDATE`/`INSERT…ON CONFLICT` + `PRAGMA user_version=2` + `COMMIT` **unconditionally**, on a WAL database — so each read grabs the writer lock, writes ~4 meta rows + WAL frames, commits, closes the RW connection, then opens a second `READONLY` connection for the actual query. `TryEnumerateFromConfiguredSqliteStore` calls both `InspectVolume` and `EnumerateVolume` → **two** write transactions per user query. Under concurrent multi-Find-window load, reads serialize on a write lock they don't need and can stall up to the 5 s `busy_timeout`. Separately, the prefix prefilter emits `name_folded LIKE 'foo%'` (~851-859, bound ~906-916) against `idx_entries_name_folded` (~1042) on a `BINARY`-collation column (~1030) with default case-insensitive `LIKE` → SQLite cannot use the index-prefix optimization and full-scans the volume.

**Fix:** Split bootstrap from query — migrate once at store open/first use, and short-circuit `EnsureSchemaVersion2(db,false)` to `S_OK` (no `BEGIN IMMEDIATE`, no meta writes) when all columns exist and `user_version==2`. Make the read paths open read-only without forcing `EnsureBootstrap`'s write transaction. For prefix, use a half-open range (`name_folded >= ?prefix AND name_folded < ?prefixUpper`) instead of `LIKE`; this guarantees index-prefix usage and closes D-S2-2 without introducing `ESCAPE` complexity. The prefix-upper helper must operate on the invariant folded UTF-16 string and return "no upper bound" only when every code unit is maxed.

**Required proof (Performance Validation Contract):** Compare-selftest asserts NO write transaction on a v2 read and no `SQLITE_BUSY` under concurrent readers; a plan/IO assertion shows the prefix path uses the index. Archive the sqlite metric.

**Status 2026-06-20:** Complete. Read APIs now use `OpenReadOnlyReadyConnection(...)` and reject missing/incomplete/non-v2 stores without bootstrapping or migrating on the hot query path. The already-current v2 bootstrap path exits before `BEGIN IMMEDIATE`, so maintenance/writer APIs keep the migration contract while read APIs no longer acquire writer locks. Prefix prefilters now build a folded half-open range and a dedicated regression fixed a dangling `wstring_view` over `std::wstring::substr(...)` that corrupted folded prefix values.
