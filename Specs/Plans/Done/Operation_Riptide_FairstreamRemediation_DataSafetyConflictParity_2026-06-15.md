## Phase P0 — Stop the data loss (blocks ship; slices independent)

### R0-1. `[CRITICAL]` Size+mtime "already-copied/identical" heuristic skips a real conflict and deletes the MOVE source

**Symptom (reachable, normal interactive use):** Move a file `S` into a folder already containing a *different* same-name file `D` of equal size whose last-write time is within 2 seconds. The source `S` is permanently destroyed, `D` (different content) is kept, **no conflict prompt is shown**.

**Root cause:** `CopyFileInternal` (`FileSystem.FileOps.cpp` ~3315-3350). When `destinationExisted && !HasOverwriteGrant`, the code calls `FilesMatchBySizeAndWriteTime` (~768-798; size + 2s `kLastWriteToleranceHundredNs = 20'000'000`) and, on a match, returns `S_OK` with **no `FileSystemIssue` raised** and folds the bytes into `completedBytes` as if freshly written. The comment claims "resume-aware … artifact of an earlier pass," but **no resume/retry state gates the branch** — it fires on a normal first-pass merge, sequentially and in parallel. On cross-volume / same-volume-merge MOVE, the copy "succeeds," then `DeleteCopiedSourceEntryForMove` → `DestinationMatchesSourceFile` (~3035-3067, 3177-3189) applies the **identical** size+2s-mtime heuristic and deletes the source.

This violates the normative ABI rule (`FileSystem.h` Copy/Move doc): `ERROR_ALREADY_EXISTS` MUST be raised for file-vs-existing-file so the user can choose.

**Fix:**
1. Delete the content-blind size+mtime silent-skip branch in `CopyFileInternal`; an existing destination without a grant raises `ERROR_ALREADY_EXISTS` unless both paths are no-follow plain files and their bytes compare equal. This keeps rerun/resume noise down only for byte-proven identical files.
2. Fully content-prove `DestinationMatchesSourceFile`: reopen the live source no-follow, verify it is the same file identity as the delete snapshot, open the destination no-follow, and compare bytes. A MOVE source MUST NOT be deleted on size+mtime alone.
3. If a broader resume optimization is later wanted, gate it to an explicit retry/resume context and prove identity by content/hash; never infer identity from timestamp metadata.

**Required proof:** new `Riptide_MoveDistinctSameSizeFilePreservesSource` — cross-volume MOVE (held-open handle forces fallback) of `S` and a colliding `D` (same size, mtime within 2s, **different content**): RED on current branch (source deleted, dest keeps old bytes, 0 prompts); GREEN after fix (exactly 1 conflict, source intact on Skip, dest unchanged). Add a byte-equality + out-of-tree sentinel assertion.

**Evidence captured on 2026-06-15:** RED reproduced in a detached temp worktree at the trunk-integrated gate commit with only the new selftests applied: `Riptide_MoveDistinctSameSizeFilePreservesSource` failed because the old engine completed `S_OK`, showed 0 prompts, and deleted/changed the source. GREEN on the current engine passed the exact case. Archived under `Specs/TestRuns/SINON/FileOps/2026-06-15_125929/Riptide_R0_P0_DataSafetyRollback/` as `R0-1_RED_selftests_only_old_engine/` and `R0-1_GREEN_current_engine/`.

**Note for product/UX:** this fix *raises* prompt counts on re-run/merge flows that previously skipped silently. That is correct behavior, not a regression — but flag it to whoever owns the conflict-prompt UX before landing.

### R0-2. `[HIGH]` Reparse-point move rollback destroys pre-existing overwritten destination

**Symptom:** A reparse-point (junction/symlink) MOVE with an overwrite grant lands on pre-existing destination data; the copy succeeds but source removal fails (source held open / ACCESS_DENIED). The rollback then recursively deletes the destination — but the original content was already overwritten, so the user loses it.

**Root cause:** `MovePathInternal` reparse branch (`FileSystem.FileOps.cpp` ~5029-5058). Both source-removal-failure paths (`RemoveDirectoryW` ~5034, `DeleteFileW` ~5057) call `TryRollbackCopiedDestination(destination.extended)` **unconditionally** — a recursive `RemovePathForOverwrite`. The non-reparse copy+delete path was explicitly hardened (~5286: rollback only when `!deleteStats.anyDeleted && !destinationExistedBeforeCopy`); the reparse branch omits that guard, even though the copy-*failure* rollback at the same site (~5022-5025) already guards on `destinationAttributes == INVALID_FILE_ATTRIBUTES`.

**Fix:** gate both reparse-branch rollbacks on `destinationExistedBeforeCopy == false` (the value is already computed and in scope at ~4954). When the destination pre-existed, return `ERROR_PARTIAL_COPY` and leave it in place. Factor a single `ShouldRollbackCopiedDestination(...)` helper shared by the reparse, non-reparse, and copy-failure paths so they cannot diverge again.

**Required proof:** new `Riptide_ReparseMoveRollbackKeepsOverwrittenDestination` — junction over pre-existing data + overwrite grant + forced source-removal failure: RED (destination recursively deleted), GREEN (destination preserved, item `ERROR_PARTIAL_COPY`).

**Evidence captured on 2026-06-15:** RED on the current engine before the rollback fix failed with `Riptide reparse rollback deleted the overwritten destination after source delete failure.` GREEN after introducing `ShouldRollbackCopiedDestination(destinationExistedBeforeCopy, sourceContentDeleted)` passed the exact case and preserved the overwritten destination while returning `ERROR_PARTIAL_COPY`. Archived under `Specs/TestRuns/SINON/FileOps/2026-06-15_125929/Riptide_R0_P0_DataSafetyRollback/` as `R0-2_RED_current_engine_before_fix/` and `R0-2_GREEN_current_engine/`.

## Phase P1 — Make the headline workloads honest (each independent; R1-2/R1-3 land together, R1-4 before R1-5)

### R1-1. `[HIGH]` Cross-FS bridge aborts the whole subtree on nested child issues and mishandles directory destination races

**Root cause:** `FolderWindow.FileOperations.State.cpp`. The bridge raises `FileSystemIssue` only for the file-vs-file destination-exists case (`ValidateDestinationOverwritePolicy` ~6500-6537). Every other per-child failure returns a raw FAILED hr that aborts the directory on first occurrence: `EnsureDestinationDirectory` dir-vs-file (~6286-6290), `ValidateDestinationOverwritePolicy` file-vs-dir (~6486-6491), reader/writer-create, commit, size-mismatch in `CopyFileWithBuffer`. `CopyDirectorySequential` propagates immediately (~7095-7099, 7171-7174). When the surfaced `ERROR_ALREADY_EXISTS` is answered Overwrite, the per-item loop OR-s `FILESYSTEM_FLAG_ALLOW_OVERWRITE` into `itemFlags` and re-runs `CopyPath` **from the tree root** (~7978-7986 / 8530-8533) — re-reading/re-uploading every already-committed child to S3/OneDrive/Curl — and the flag now applies bridge-wide, so an unrelated sibling file-vs-file collision is silently overwritten without prompting (violates the one-shot-grant contract, `FileSystem.h` ~428-430).

Two additional bridge defects are part of this same slice because they live in `EnsureDestinationDirectory` and have the same per-child conflict-routing shape:
- A source directory landing on a destination file deletes the blocking destination with `FILESYSTEM_FLAG_NONE`. If the destination file is read-only, a user-granted `ReplaceReadOnly` retry never reaches the delete, so the retry loops/fails even though the user made the required destructive choice.
- `CreateDirectory(destination)` treats `ERROR_ALREADY_EXISTS` as success without re-probing. If a file appears between `GetAttributes` and `CreateDirectory`, an empty source directory can be reported as copied even though the destination is a file; non-empty directories then fail later with misleading child errors.

**Additional root cause found during implementation:** the local `IFileSystemIO` methods used raw Win32 paths even though the high-level copy/move engine already normalizes through extended `\\?\` paths. In nested Codex worktrees, bridge temp names appended to a valid 238-character destination produced ~280-character temp paths. The local writer failed with `ERROR_PATH_NOT_FOUND`; the bridge returned that raw child failure, and the per-item host wrapper raised a misleading top-level Unknown conflict for the whole source root. This was why the long-root R1-1 RED failed while the same case passed under a short `C:\R\...` selftest root.

**Fix:**
1. Change `EnsureDestinationDirectory(destinationPath)` to `EnsureDestinationDirectory(sourcePath, destinationPath)` so every directory-blocking issue can be reported with both source and destination paths.
2. When an existing non-directory blocks a source directory, call `task.FileSystemIssue(... ERROR_ALREADY_EXISTS ...)` before any delete. On Skip, record a skipped conflict and return the same internal skip sentinel used by file conflicts. On Overwrite, delete the blocking destination for this child only. On ReplaceReadOnly, pass `FILESYSTEM_FLAG_ALLOW_REPLACE_READONLY` into `destinationFs.DeleteItem`; do not retry with `FILESYSTEM_FLAG_NONE`. On Cancel, return `ERROR_CANCELLED`.
3. After `destinationDirOps->CreateDirectory(destinationPath)` returns `ERROR_ALREADY_EXISTS`, immediately call `destinationIo.GetAttributes(destinationPath)`. Return `S_OK` only when the target is a directory. Return/reroute `ERROR_ALREADY_EXISTS` when it is a file or unknown non-directory. Treat reparse-point directories according to the bridge's existing reparse policy; do not silently merge through an unverified target.
4. Route non-collision child failures and the type-mismatch cases through `task.FileSystemIssue` at the child path, mirroring the same-FS plugin's recursive loop (`FileSystem.FileOps.cpp` ~3913-3956).
5. Keep grants scoped to the answered child. Do not OR child `Overwrite` or `ReplaceReadOnly` back into root-level `itemFlags`; that is the source of whole-tree re-transfer and sibling overwrite leakage.

**Required proof:**
- `Fairstream_BridgePerFileConflictSkips` — retained and tightened: cross-FS dir copy with a colliding child prompts for the child, Skip preserves the existing destination, copies the non-colliding sibling, and ends `ERROR_PARTIAL_COPY`.

### R1-6. `[HIGH]` Early-admission COPY can terminate the process on thread creation failure

**Root cause:** `Task::ThreadMain()` is `noexcept`, but the early-admission path constructs a `std::jthread` directly. `std::jthread` construction may throw `std::system_error` when the process or OS cannot create another thread; escaping `ThreadMain() noexcept` calls `std::terminate`. The branch also enables early admission for copy even when pre-calculation is disabled, so a copy can start a thread whose target immediately returns.

**Fix:**
1. Compute `useEarlyAdmission` from the same predicate that makes pre-calculation meaningful, not just `_operation == FILESYSTEM_COPY`. At minimum: `_operation == FILESYSTEM_COPY && _enablePreCalc`.
2. Extract thread creation into a small helper in `FolderWindow.FileOperations.State.cpp`, for example `StartPreCalculationThread(std::jthread& thread) noexcept -> HRESULT`, so the throwing constructor is isolated.
3. Catch only `const std::system_error&` in that helper, log one `Debug::Warning(...)` with the error code/message, and fall back to the existing serial/no-precalc path. Do not catch `std::bad_alloc`; let it remain fatal per repo policy.
4. Add a selftest-only injection hook that makes `StartPreCalculationThread` return `HRESULT_FROM_WIN32(ERROR_NOT_ENOUGH_MEMORY)` before constructing `std::jthread`. Keep the hook compiled out or inert in normal builds.

**Required proof:**
- `Riptide_EarlyAdmissionThreadStartFailureFallsBack` — force the injection hook, run a copy that would normally use early admission, and assert the task completes or reports a normal file-operation HRESULT without process termination.
- `Riptide_EarlyAdmissionDisabledDoesNotStartThread` — run a copy with `_enablePreCalc == false` and assert the thread-start hook is not called.

**Evidence captured on 2026-06-15:** RED on the current engine with only the new hook/tests failed `Riptide_EarlyAdmissionThreadStartFailureFallsBack` because the forced failure path was not honored (`attempts=0`).
