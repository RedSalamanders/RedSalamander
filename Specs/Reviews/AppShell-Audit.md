# App-Shell Audit — Final Report: RedSalamander

## 1. Verdict

The app shell is functional on the happy path but **fragile at every boundary the user does not control**: OS session end, real crashes, multi-instance coexistence, plugin worker threads, and untrusted folders. The single most damaging confirmed defect is that **nothing is saved when Windows logs off, restarts, or shuts down** — there is no `WM_QUERYENDSESSION`/`WM_ENDSESSION` handler anywhere, so window placement and all session/pane/history state silently revert on every reboot. The most dangerous *security* themes are **two binary/DLL-planting gaps** (the launcher hands the child an attacker-controlled CWD with no `SetDefaultDllDirectories` hardening; the file-action launcher will run a bare exe name from a browsed untrusted folder) and a **fail-open cross-thread race on unsynchronized in-process secret maps** that can corrupt the heap or leak plaintext credentials. The crash subsystem is the other weak spot: the handler does **heap/DbgHelp/symbol work on the faulting thread with no reentrancy guard and no stack-overflow margin**, so it can hang or re-fault for exactly the corruption/stack-overflow crashes you most need captured — and the **plugin-quarantine feature is dead code** (the prompt is shown before the host window exists, so it never disables anything) while *also* mis-attributing blame to the built-in local filesystem plugin. Themes: unhandled session-end data loss; crash-handler minimal-work-discipline violations; DLL/binary planting via working directory; fail-open IPC/threading guards on secret state; and a quarantine pipeline that is simultaneously unreachable and wrong.

## 2. Findings by Severity

### DATA-LOSS

**No save-on-exit on Windows logoff/restart/shutdown — window placement and session state silently lost**
`RedSalamander/RedSalamander.cpp:11055` (WndProc dispatch); persistence at `:10966` → `:2553` → `:2378`
Severity: **data-loss** · **CONFIRMED**
*(Consolidates three duplicate findings reported at lines 11055/11124 — same root cause.)*
The main `WndProc` (`:11055`–`11131`) handles `WM_CLOSE`/`WM_DESTROY` but has **no** case for `WM_QUERYENDSESSION` or `WM_ENDSESSION`; both fall through to `DefWindowProcW`. A repo-wide grep for `WM_QUERYENDSESSION|WM_ENDSESSION|ShutdownBlockReasonCreate|RegisterApplicationRestart|SetProcessShutdownParameters` returns **zero** matches. The *only* runtime-state persistence path is `SaveAppSettings(hWnd)` at `:10966`, reached exclusively via `WM_DESTROY` (which follows `WM_CLOSE`). `CaptureRuntimeSettings` (`:2378`) records the only copy of: main+child window placement, active pane, split ratio, both panes' folder paths, per-pane view settings, folder history and history filters, and menu/function-bar visibility — none persisted eagerly.
*Failure scenario:* User resizes/moves the window and navigates to new folders, then chooses Start ▸ Restart (or the OS ends the session for an update). Windows sends `WM_QUERYENDSESSION`/`WM_ENDSESSION` and terminates the process **without** `WM_CLOSE`/`WM_DESTROY`; `SaveAppSettings` never runs, and on next launch the stale pre-session layout is restored. Worse, `OnMainWindowClose` (`:10916`) normally calls `ConfirmCancelAllFileOperations` to drain/cancel in-flight copy/move ops — that drain is also bypassed, so a running file op is torn down mid-write. (Note: plugin config / theme / preference edits *are* persisted eagerly elsewhere — `HostServices.cpp:2189/2464`, `ManagePluginsDialog.cpp:3973`, `Preferences.Dialog.cpp` — so those are **not** lost; the genuinely lost data is window placement + pane/folder/view/history state.)
*Deeper fix:* Add a `WM_QUERYENDSESSION` handler (return `TRUE`, optionally `ShutdownBlockReasonCreate` while a save is pending) and a `WM_ENDSESSION` handler that, when `wParam==TRUE`, synchronously runs `CaptureRuntimeSettings` + `SettingsHotReload::SaveSettingsAndSchema` — idempotent with the `WM_DESTROY` save, kept fast to fit the OS shutdown timeout. Drain/cancel in-flight file ops on the same path, and call `SetProcessShutdownParameters` so the main window shuts down last. The save already uses the atomic temp+`MoveFileExW(MOVEFILE_REPLACE_EXISTING|MOVEFILE_WRITE_THROUGH)` path (`SettingsStore.cpp:400-437`), so torn-file corruption is not a concern — only the *non-execution* of the save is.

### SECURITY

**Launcher spawns the child with an attacker-controlled CWD and no DLL-search hardening (DLL planting)**
`RedLauncher/Main.cpp:358`
Severity: **security** · **CONFIRMED**
`::CreateProcessW(targetPath.c_str(), …, nullptr /*lpCurrentDirectory*/, &startupInfo, &processInfo)` passes `nullptr` for the 8th argument, so the child `RedSalamander.exe` inherits the launcher's CWD. The trusted install dir (`packageDirectory`, derived at `:332` from `GetFinalPathNameByHandleW` of the launcher's own image) is already computed but unused here. No `SetDefaultDllDirectories`/`SetDllDirectory` exists in the launcher or the main exe's `wWinMain` (grep finds these only in test projects and `Plugins/ViewerVLC`). The child EXE itself is a full path (not plantable), but its dependent-DLL resolution — CRT, delay-load imports, COM/D2D activation, or any plugin calling `LoadLibraryW` by name — includes the inherited CWD.
*Failure scenario:* User opens a file from a malicious network/USB/downloads folder via association/Explorer/shortcut Start-in; the child starts with that folder as CWD; a DLL resolved through the standard search order (e.g. `version.dll`, `dwmapi.dll`) is satisfied from the attacker's folder → code execution in the user's session.
*Deeper fix:* Pass `packageDirectory.c_str()` as `lpCurrentDirectory`, and call `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)` in both the launcher and early in the main exe's `wWinMain` to remove the CWD from the implicit DLL search path entirely.

**File-action launcher runs a bare executable name from the browsed (untrusted) folder (binary/DLL planting)**
`RedSalamander/FileActionLauncher.cpp:614` (also `:584`, `:616`)
Severity: **security** · **CONFIRMED**
`BuildExternalLaunchPlan` only checks `executablePath` for emptiness (`:517`, `:562`) — there is **no** requirement that it be fully qualified. When no `workingDirectory` is configured, `:584` defaults `out.workingDirectory` to the browsed folder (`CurrentDirectoryForContext` → `context.currentDirectory`, which callers set to `focusedPath.parent_path()` at `FolderWindow.Viewers.cpp:917/1207/1465`). `LaunchExternalPlan` then passes the bare `lpFile` (`:614`) and the untrusted `lpDirectory` (`:616`) to `ShellExecuteExW`, which resolves a bare name against `lpDirectory`+PATH and starts the process's DLL search from that folder. The only availability guard (`ExecutablePathLooksAvailable`, `FolderWindow.Viewers.cpp:70-92`) *intentionally accepts* bare names via `SearchPathW` and is used only for optional UserMenu visibility, not the View/Edit launch path.
*Failure scenario:* Attacker ships a folder containing a benign document plus a planted `tool.exe` (or a DLL a PATH-resolved tool loads). Victim opens the folder and triggers a pre-configured File Action with a bare `executablePath` → planted `tool.exe` runs from the browsed folder, or the real tool loads the planted DLL → arbitrary code execution. *Precondition:* requires a user-configured File Action using a bare name with no working directory — a plausible misconfiguration the SearchPath logic actively supports, not a default zero-click.
*Deeper fix:* Require `executablePath` to resolve to a fully-qualified, existing path in `BuildExternalLaunchPlan` (reject bare/relative names there, not just in the optional check). Do not default `lpDirectory` to the browsed folder; set the working dir only after the image is resolved to an absolute path, and prefer `CreateProcessW` with the full application name so the browsed folder is never part of the executable or DLL search order.

**Fail-open cross-thread guards run UI-thread secret bodies on a worker, mutating unsynchronized session-secret maps**
`RedSalamander/HostServices.cpp:657` (guards at `:658/694/717/787/618`; inner at `:1625/2231/2363`; maps at `:2100-2102`)
Severity: **race** (security-relevant: heap corruption / UAF / plaintext leak) · **CONFIRMED**
Every secret entrypoint marshals to the UI thread only with `if (hostWindow && !IsCurrentThreadWindowThread(hostWindow))`. When `GetInitializedHostWindow()` returns null — before the folder window is published during plugin discovery, or after teardown when `IsWindow()` is false — the `hostWindow &&` short-circuits the condition to false and control falls through to run `…OnUiThread` **on the calling worker thread**. The inner "assertions" use the same pattern, so they also pass. The bodies read/write `_sessionPasswordByConnectionId` / `_sessionPassphraseByConnectionId` / `_sessionRefreshTokenByConnectionId` (find at `:1652`, insert/`SecureClear`/`assign` at `:2262-2273`, `erase`/`SecureClear` at `:2390-2394`) which have **no mutex** (the only `<mutex>` use in the file is a `std::once_flag` at `:153`). The same maps are torn down by `clearAllSessionSecrets()` in `~HostServices` (`:360`). Reachability at teardown is concrete: `SaveAppSettings` nulls `g_hFolderWindow` at `RedSalamander.cpp:2559` **before** shutting plugins down at `:2563`; a plugin FS worker still alive in that gap (e.g. GoogleDrive OAuth refresh, `FileSystemGoogleDrive.cpp:1614`) sees a null window and runs the secret body on its own thread, racing the destructor.
*Failure scenario:* Worker A `SetConnectionSecret` while the UI thread (or another worker that also saw null) is in `GetConnectionSecret` for the same kind → concurrent `unordered_map` insert/find/erase + `std::wstring` assign corrupts buckets/rehash → crash, UAF of a `SecureClear`'d string, or a leaked plaintext secret buffer.
*Deeper fix:* Fail **closed**, matching the existing safe pattern of `PromptForConnectionSecret` (`:747`): require a valid `hostWindow` up front (`if (!hostWindow) return HRESULT_FROM_WIN32(ERROR_INVALID_WINDOW_HANDLE);`) and only run the body when `IsCurrentThreadWindowThread` is true. Additionally guard the three `_session*ByConnectionId` maps **and the destructor** with a `std::mutex`.

### CRASH

**Crash handler does heavy heap/DbgHelp/symbol work on the faulting thread with no reentrancy guard — hangs or re-faults on heap-corruption / stack-overflow crashes**
`RedSalamander/CrashHandler.cpp:352` (`WriteDumpAndMarker`); `:187` (`BuildStackTraceText`); handlers at `:390/396/402/408`, installed `:470-473`
Severity: **crash** · **CONFIRMED**
*(Consolidates the two "heavy work / not reentrancy-guarded" findings at `:352` and `:390`, plus the stack-overflow finding — same root cause: non-minimal, non-reentrant crash path on the faulting thread.)*
The handlers run `WriteDumpAndMarker` directly on the crashing thread. `WriteCrashReportFile` (`:372`) **unconditionally** runs `BuildStackTraceText` **before** `WriteMiniDumpFile` (`:374`), and that text path allocates freely and takes both the process heap critical section and the DbgHelp global lock: `out.reserve(16*1024)` (`:234`), many `std::format`/`std::wstring`, `EnsureDirectoryExists`→`create_directories` (`:71`), `SymInitialize` (`:205`), `StackWalk64` (`:270`), `SymFromAddr` (`:285`), `SymGetLineFromAddr64` (`:298`), `SymCleanup` (`:307`). There is **no** reentrancy guard (`g_installed` only gates `Install()` itself), **no** dedicated handler stack, and **no** stack-overflow margin anywhere (repo-wide grep finds no `SetThreadStackGuarantee`, `_resetstkoflw`, or `AddVectoredExceptionHandler`; the lone `EXCEPTION_STACK_OVERFLOW` hit is a label in `Common/ExceptionHelpers.h:39`). The `try/catch` boundaries (`:190/355`) catch only `std::exception` — they do not break a deadlock on an already-held heap lock (a hang, not a throw) nor a hard AV from DbgHelp re-entrancy.
*Failure scenario:* (a) Crash while the faulting thread holds the heap CS (corruption inside `malloc`/`free`, or an AV inside the allocator) → the first allocation in the filter blocks **forever** on the held lock → process hangs with no dump. (b) `EXCEPTION_STACK_OVERFLOW` → only one guard page remains, so the heavy `Sym*`/`StackWalk64`/`MiniDumpWriteDump` frames re-fault → OS kills the process with no dump and no marker — losing exactly the runaway-recursion crash you needed. (c) Crash inside DbgHelp → `SymInitialize`/`StackWalk` re-entrancy faults. Ordinary null-deref AVs still produce dumps; this degrades the worst-case diagnostics.
*Deeper fix:* Make the crash path allocation- and lock-free: add a process-wide `std::atomic` reentrancy guard at the top of `WriteDumpAndMarker` (second entrant → `TerminateProcess`); pre-create the crash dir at `Install()` time; build the dump filename into a fixed `wchar_t[]`, open with raw `CreateFileW`, and call `MiniDumpWriteDump` **first**, before any symbolization. Move `BuildStackTraceText`/`Sym*` off the in-process crash path entirely (defer symbolization to the next launch reading the `.dmp`, or a watchdog process). Reserve a dedicated handler stack / `SetThreadStackGuarantee` (e.g. 64KB) or a vectored handler that switches to a pre-allocated alternate stack on `EXCEPTION_STACK_OVERFLOW`.

### LEAK

**InitInstance failure path abandons initialized plugin managers (no orderly plugin Shutdown)**
`RedSalamander/RedSalamander.cpp:7558` (early return); managers initialized `:7465`/`:7481`
Severity: **leak** · **CONFIRMED**
`RunApplication` initializes both plugin managers (`:7465`/`:7481`) — real work: `Discover`→`LoadLibraryExW` the active DLL (`:1048`) and construct live COM `IFileSystem`/`IInformations` objects — *before* `InitInstance` creates the window (`:7549`). On window-creation failure it does `if (!hWnd) { startupPerf->SetHr(E_FAIL); return FALSE; }` (`:7558-7562`). The only two `wil::scope_exit` guards in scope (`comCleanup` `:7324`, `shutdownProcessSingletons` `:7332`) tear down COM and DxUi/singletons but **neither** calls `FileSystemPluginManager`/`ViewerPluginManager::Shutdown`. Plugin `Shutdown` (`:246`, which invokes each plugin's `RedSalamanderPluginShutdown` export at `:1176-1180` — the documented hook to quiesce worker threads, close named-pipe/search-service connections, release COM) runs only from `SaveAppSettings` (`:2563-2564`, `WM_DESTROY`) and selftest paths (`:7526-7527`, `:10950-10953`), none of which execute on this early return.
*Failure scenario:* `RegisterClassExW`/`CreateWindowW` fails (desktop-heap/window-station exhaustion) after plugins loaded; the active plugin's `RedSalamanderPluginShutdown` is never called, leaving worker threads, search-service pipe connections, and COM objects abandoned to raw OS teardown. (Trigger is low-probability; the confirmed harm is the abandoned-resource leak, not a proven shutdown crash.)
*Deeper fix:* Wrap each manager in a `wil::scope_exit` immediately after `Initialize` succeeds (`auto fsCleanup = wil::scope_exit([]{ FileSystemPluginManager::GetInstance().Shutdown(g_settings); });`) so every exit path — including the `InitInstance`-failure early return — performs orderly plugin shutdown before COM/DxUi teardown; dismiss the guards on the normal `WM_DESTROY` path that already shuts them down.

**Window-scoped alert overlay map grows unbounded — entries never erased on target-window destruction**
`RedSalamander/HostServices.cpp:1872` (insert); map decl `:2099`; find-only `:1907`
Severity: **leak** · **CONFIRMED**
`_windowOverlays[request.targetWindow]` lazily creates and stores a D2D `AlertOverlayWindow` keyed by raw `HWND`. The only three references are insert (`:1872`), find (`:1907`), and the declaration (`:2099`) — there is **no `erase`** anywhere for this map. `ClearAlertOnUiThread` only calls `Hide()` (`:1910`). The `IsWindow()` check at `:1867` validates only the *incoming* target, not stored entries.
*Failure scenario:* A plugin showing `HOST_ALERT_SCOPE_WINDOW` alerts on many short-lived windows (per-operation progress windows) accumulates one overlay (each owning a D2D window + resources) per distinct HWND indefinitely — a slow handle/memory leak over a long session. Because HWNDs are recycled, a stale entry can also collide with an unrelated future window (`:1867` passes, the dead/foreign overlay is reused).
*Deeper fix:* Erase the entry when its overlay is hidden/destroyed or when the anchor window goes away (subscribe to the target's `WM_DESTROY`, or prune dead entries by `IsWindow()` on each `ShowAlert`/`ClearAlert`). Do not key persistent state on raw recycled HWNDs without a destruction hook.

**Crash minidump captures reachable heap memory (incl. potential plaintext secrets); dumps left on disk indefinitely**
`RedSalamander/CrashHandler.cpp:151-152` (dump flags); file create `:140`
Severity: **leak / info-disclosure** · **PLAUSIBLE** *(the original "ShellExecute path injection" half was refuted; the marker dir is an app-controlled constant, not marker-derived)*
`kDumpType = MiniDumpWithIndirectlyReferencedMemory | MiniDumpScanMemory | MiniDumpWithThreadInfo | MiniDumpWithUnloadedModules | MiniDumpWithHandleData`. The indirect/scan flags pull heap regions reachable from the stack/registers into the dump — which for this app can include decrypted cloud-FS connection secrets / OAuth tokens resident in memory. The `.dmp` is created with no `SECURITY_ATTRIBUTES` (`:140`) under `LocalAppData/company/crash`; on next launch only the marker is removed (`:500`), leaving `.dmp`/`.txt` on disk indefinitely. (Exposure is limited to the same user by `LocalAppData` ACL inheritance, not other accounts.)
*Failure scenario:* A crash while a secret is in a reachable heap block writes that secret verbatim into the `.dmp`, which is then likely attached to a bug report — contradicting the no-plaintext-secrets mandate.
*Deeper fix:* Use `MiniDumpNormal | MiniDumpWithThreadInfo | MiniDumpWithUnloadedModules` (drop Scan/Indirect/HandleData), or add a `MINIDUMP_CALLBACK` that strips memory ranges holding secrets. Prune old dumps and consider restricting the crash-dir ACL.

**ShowPrompt TOCTOU between `IsWindow()` and `SendMessageW` leaks payload and returns S_OK with an indeterminate result**
`RedSalamander/HostServices.cpp:545`
Severity: **leak** · **PLAUSIBLE** *(scoped down: only `ShowPrompt` is affected; the connection-secret paths cited in the original finding retain the `unique_ptr` via RAII and fail definitively — no leak, no misreport)*
`ShowPrompt` does `auto* raw = data.release();` then `SendMessageW(hostWindow, …, raw)` (`:545-546`). If the host window is valid at `GetInitializedHostWindow()` (`:524`/`IsWindow` `:250`) but destroyed before the send, `SendMessageW` to a dead HWND returns 0 without delivering the message; `TakeMessagePayload<PendingPrompt>` never runs → the released `PendingPrompt` leaks, the function returns `S_OK` (`:553`), and `*result` is never written. Unlike `ShowConnectionManager` (`:571`), `ShowPrompt` does not initialize `*result`, so it stays indeterminate, and `HostPromptResult` is a `uint32_t` Yes/No/OK decision.
*Failure scenario:* During shutdown, a plugin's `ShowPrompt` leaks the heap object and returns success while `*result` is garbage — the plugin proceeds as if a never-shown overwrite confirmation returned "Yes".
*Deeper fix:* Keep the `unique_ptr` and release only inside the handler, or check the result against window validity (`SendMessageTimeoutW` BOOL return / re-check `IsWindow`); on non-delivery, reclaim ownership and return a definite failure HRESULT, never leaving `result` indeterminate. Initialize `*result` before the send.

### RACE / ROBUSTNESS

**Crash handler: same-second filename collisions + DbgHelp single-thread race when two threads fault concurrently**
`RedSalamander/CrashHandler.cpp:462`/`:84` · Severity: **robustness** · **PLAUSIBLE**
`BuildDumpPath` (`:84`) names dumps `…-{date}-{time}-p{PID}.dmp` — PID is constant within a process and there is **no thread id or counter**, so two threads faulting in the same wall-clock second compute an identical path. `WriteMiniDumpFile` (`:140`) and `WriteCrashReportFile` (`:326`) open with `CREATE_ALWAYS`, so the second writer truncates the first. Concurrently, both enter `BuildStackTraceText`→`SymInitialize`/`SymCleanup` on the shared (single-threaded) DbgHelp handle, corrupting symbol state. (`Install()`'s own `g_installed` exchange guard is fine — the title's "Install() not idempotent" framing is inaccurate; the real gap is the *un-serialized* `WriteDumpAndMarker` reachable from 5 paths incl. the `__except` filter at `RedSalamander.cpp:7839`.) Low-probability (two faults within one second); impact is degraded forensics, not a new crash. *Fixed by the same process-wide serialization guard recommended for the crash-handler finding above, plus a thread id + counter in `BuildDumpPath`.*

**Splash teardown race: worker reads stale `g_owner` HWND cross-thread; `g_owner` never cleared**
`RedSalamander/SplashScreen.cpp:603` (also `:554`) · Severity: **robustness** · **CONFIRMED**
`CenterOverOwner`/`GetWorkAreaForOwner` dereference the main-thread-owned owner HWND from the splash worker thread, guarded only by a racy `IsWindow()` (`:603`/`:554`) before `GetWindowRect`/`MonitorFromWindow`. `SetOwner` (`:895`) only ever stores a live HWND; there is no `SetOwner(nullptr)` on main-window teardown (`WM_DESTROY` clears only `g_hwnd` at `:518`), so a stale owner handle persists. Benign in practice — HWNDs are opaque kernel handles, so `GetWindowRect` returns FALSE for a destroyed handle and `CenterOverOwner` falls back to work-area centering (`:606`/`:599`) — no UAF, no crash. *Fix:* call `SetOwner(nullptr)` on main-window destroy; better, capture the owner rect once on the main thread and pass it via the recenter message to avoid cross-thread HWND access.

### INCORRECT-BEHAVIOR / CONTRACT

**Crash quarantine is dead code in production — prompt shown before the host window exists, so the YES branch is unreachable**
`RedSalamander/RedSalamander.cpp:7395` → `CrashQuarantine.cpp:159` → `HostServices.cpp:507/527`
Severity: **incorrect-behavior** · **CONFIRMED**
`OfferPluginDisableIfPreviousCrashDetected(g_settings)` runs at `:7395` inside `RunApplication`, but `g_hFolderWindow` is not stored until the `WM_CREATE` handler at `:8638` — so it is still null. `CrashQuarantine.cpp:159` calls `HostShowPrompt` → `ShowPrompt` (`HostServices.cpp:507`) → `GetInitializedHostWindow()` returns null → `ShowPrompt` returns `HRESULT_FROM_WIN32(ERROR_INVALID_WINDOW_HANDLE)` (`:527`). Back at `CrashQuarantine.cpp:160`, `FAILED(hrPrompt)` is true so the function returns at `:162` without ever running `DisablePluginIdInSettings`. The only short-circuit (`HostServices.cpp:2539-2557`) is `#ifdef ENABLE_TESTS`; unit tests stub `HostShowPrompt`, so this integration gap is untested.
*Failure scenario:* Plugin X crash-loops the app on startup. The marker and session state are present, `ComputePluginsToDisable` returns `{X}`, but the prompt fails (no window yet) and the function silently returns. X is never disabled — the user is stuck in an unbreakable crash loop and the entire quarantine feature provides zero recovery.
*Deeper fix:* Either call the quarantine after `g_hFolderWindow` is stored (after `:8638`) but before plugins are initialized, or have `CrashQuarantine` show a plain modal `MessageBox` (owner `nullptr`) instead of routing through `HostShowPrompt`. Add a non-test integration test driving the real prompt path.

**Crash mis-attributed to the last active FS plugin regardless of where the crash occurred — falsely disables the built-in local plugin**
`RedSalamander/CrashQuarantine.cpp:67` (`ComputePluginsToDisable`); default button `:156`
Severity: **incorrect-behavior** · **CONFIRMED**
The crash marker (`CrashHandler.cpp` `WriteMarkerFile` `:100-131`) carries **no attribution** — only the dump path — and is written by all four global handlers for any fault. Separately, `SessionState` records the last active FS plugin id on every browse/copy/compare (`FileSystemPluginManager.cpp:371`, `FolderWindow.FileOperations.State.Runtime.Part.cpp:115`, `CompareDirectoriesWindow.cpp:2852`), including the built-in local `FileSystem` plugin on a plain browse. `ComputePluginsToDisable` (`:67-90`) blames whatever ids are in `session_state.txt`; the dump's faulting module / call stack is **never** inspected.
*Failure scenario:* User browses `C:\` (local plugin recorded) then crashes in `ViewerImgRaw` or a D2D/UI bug. On next launch the quarantine offers to disable the **local FileSystem plugin** — the core of the file manager. The default prompt button is **YES** (`:156`), so a stray Enter cripples the app while the real culprit stays enabled; `DisablePluginIdInSettings` (`:48-64`) also clears `currentFileSystemPluginId`.
*Deeper fix:* Attribute via the minidump's faulting module/call stack (already captured by `BuildStackTraceText`) and only offer to disable a plugin whose DLL appears in the faulting frames. Never auto-target the built-in/local provider. Change the default button from YES to NO.

**`FindWindowW` lookups match windows of *other* RedSalamander instances (no single-instance guard) — cross-process dialog dedup + cross-process pointer send in test hooks**
`RedSalamander/RedSalamander.cpp:463` (also `:8223/10985/10991`; test hook `:11032`)
Severity: **incorrect-behavior** · **CONFIRMED**
There is no general single-instance guard (the only mutex in `wWinMain`/`RunApplication` is the self-test run guard `Local\RedSalamander_SelfTestRun`, `:1442/1472`), so multiple instances coexist. `FindWindowW(class, nullptr)` matches by class-name string session-wide, and the class names are fixed/shared (`:120-122`). `AboutDialogWindow::ShowModal` (`:463`) thus calls `ShowWindow`/`SetForegroundWindow` on **another process's** About dialog (`:465-466`) and returns `S_FALSE`, suppressing its own. The `ENABLE_TESTS` hook `DebugGetFatalErrorDialogSnapshot` (`:11032`) sends `SendMessageW(hwnd, …, reinterpret_cast<LPARAM>(&out))` — an in-process pointer — which the receiver dereferences as a local pointer (`:945-946`); if `hwnd` is foreign, that pointer is meaningless in the target address space.
*Failure scenario:* (production) Two windows open, one already showing About; pressing About in the second silently activates the first's dialog and never opens its own. (test) Two `ENABLE_TESTS` instances each with a fatal-error dialog → the snapshot hook dereferences an invalid pointer in the wrong process → crash/garbage.
*Deeper fix:* Scope lookups to `GetCurrentProcessId()` via `EnumWindows` + `GetWindowThreadProcessId`, or track these HWNDs in process-local globals. Gate the cross-process-pointer test hooks on a same-PID check and never pass an in-process pointer to a possibly-foreign window.

**Virtual-FS / UNC focused path forwarded unvalidated to `ShellExecuteEx` local verb**
`RedSalamander/FileActionLauncher.cpp:614` · Severity: **incorrect-behavior** · **CONFIRMED**

## 3. Cross-Cutting Themes

1. **Session end (`WM_QUERYENDSESSION`/`WM_ENDSESSION`) is completely unhandled.** This is the single highest-impact theme: it causes the confirmed data-loss finding *and* aggravates two others (quarantine-decision loss, crash-marker leak) and the in-flight-file-op drain bypass. One handler + `ShutdownBlockReasonCreate`/`SetProcessShutdownParameters` closes several findings at once.

2. **Fail-open boundary guards.** The pattern `if (hostWindow && !IsCurrentThreadWindowThread(hostWindow))` short-circuits to "run anyway on this thread" when the window is null, instead of failing closed. The same file already has the correct fail-closed pattern (`PromptForConnectionSecret`), so the fix is a mechanical alignment. This is the root of the most severe race/security finding.

3. **Crash-handler minimal-work discipline is absent.** Heap allocation, DbgHelp/symbolization, and `create_directories` all run on the faulting thread *before* the dump is written, with no reentrancy guard, no dedicated/guaranteed stack, and no same-second uniqueness. One refactor (dump-first, allocation-free, serialized, deferred symbolization, reserved stack) resolves four crash-subsystem findings.

4. **DLL / binary planting via working directory.** Both launchers (`RedLauncher` and `FileActionLauncher`) let an untrusted folder enter the executable/DLL search order, and `SetDefaultDllDirectories` is called nowhere in the shipping binaries. A process-wide hardening call plus full-path/`lpCurrentDirectory` discipline addresses both.

5. **Raw recycled HWNDs keyed/cached/looked-up without lifetime hooks.** `_windowOverlays` (leak), `FindWindowW` class-name lookups (cross-process), and stale `g_owner` (splash) all treat HWNDs as stable identity. Each needs a destruction hook or a PID/validity scope.

6. **Crash quarantine is structurally broken end-to-end.** It is unreachable in production (no window yet), mis-attributes blame (no module correlation), defaults to YES, leaks its marker, and loses its decision on early exit. It should be treated as a feature to re-architect, not a set of independent bugs.

## 4. Coverage & Residual Risk

**Covered with confirmed defects:** startup/init order (`RunApplication`/`InitInstance` cleanup), shutdown/save-on-exit (session-end gap), single-instance behavior (none exists; cross-process `FindWindowW`), crash handler + minidump (work discipline, reentrancy, stack overflow, secret capture, encoding), crash quarantine (reachability, attribution, persistence, marker hygiene), `RedLauncher` bootstrap (CWD/DLL planting, STARTUPINFO), external file-action launcher (bare-exe planting, virtual-path forwarding), host services (fail-open secret race, overlay leak, prompt TOCTOU, secret residue), splash (DPI dead code, owner race).

**Residual risk / not fully exercised by these findings:**
- **WM_COPYDATA validation itself was not in scope of any confirmed finding** despite being the named IPC channel — the single-instance unit surfaced `FindWindowW`/test-hook issues but no `COPYDATASTRUCT` parsing path was audited here. If a `WM_COPYDATA` receiver exists for command-line/file-open forwarding, its `cbData`/`dwData`/`lpData` bounds validation is **unverified** and is the most likely untested cross-process attack surface.
- **Plugin-side shutdown behavior** is assumed, not verified: the leak finding proves the host skips `RedSalamanderPluginShutdown` on one path, but whether individual plugins actually spawn threads / hold pipe connections that would crash on raw teardown was not confirmed per-plugin.
- **Search-service named-pipe IPC** (`RedSalamanderSearchService`) is referenced (orphaned connections) but its own pipe-security/ACL/message-framing was not audited in this pass.
- **Concurrency timing windows** (crash same-second race, ShowPrompt TOCTOU, splash owner race) are real but low-probability; none were reproduced dynamically — severities reflect code inspection, not observed failures.
- **Several PLAUSIBLE findings depend on user configuration or rare OS conditions** (file-action bare-exe requires a pre-configured action; InitInstance leak requires desktop-heap exhaustion). These are correctly hardening/robustness, not guaranteed exploits, but should not be dismissed.

**Recommended fix order:** (1) `WM_QUERYENDSESSION`/`WM_ENDSESSION` save handler; (2) fail-closed secret guards + map mutex; (3) the two DLL-planting hardening fixes + `SetDefaultDllDirectories`; (4) crash-handler dump-first/serialized/reserved-stack refactor; (5) crash-quarantine re-architecture (reachability + module attribution + immediate persist + NO default). Then audit the **WM_COPYDATA receiver** explicitly, which this pass did not cover.
