## Source instrumentation gap and limits

The cited source ranges in `source-callsites.txt` show that ViewerSpace's provider-read timer encloses the whole `IFilesystem::ReadDirectoryInfo` call, while the FileSystem `PopulateFilesInformation` scope starts after `FilesInformation` allocation and `MakeAbsolutePath`, then ends before the caller's `MaybeTrimBuffer`. `MaybeTrimBuffer` releases its enumeration handle/buffer before its conditional TrimBuffer scope begins. Thus the two instrumentation boundaries differ. The inner `Debug::Perf::Scope` computes its elapsed value before its destructor calls the JSONL writer; its synchronous serialization, write mutex and `WriteFile` execute before `ReadDirectoryInfo` returns, so they can be included in ViewerSpace's outer provider-read wall time while absent from the inner Enumerate duration. If ETW is active, its event write also happens after the inner elapsed sample. These are concrete unmeasured terms, not proven causes of the observed gap.

The current evidence does not establish that the large provider-read aggregate is filesystem I/O, observer cost, path canonicalization, object/buffer setup or cleanup. The next diagnostic should preserve the current sink-on metric-contract case unchanged, then run an explicitly separate sink-off control from a fresh process with PerfJsonl and ETW confirmed disabled. The control must use the same fixture, operation and outer wall-clock/snapshot endpoint, record results outside PerfJsonl, and be labeled diagnostic so no metric-presence assertion is weakened in the existing case. If an equivalent sink-off ViewerSpace run cannot be driven by the current harness without skipping those assertions, use a narrow test-only control or a targeted PerfScope sink microbenchmark; do not claim it measures the full scan. Keep path/allocation/trim phases separate if the sink toggle does not explain the gap.
