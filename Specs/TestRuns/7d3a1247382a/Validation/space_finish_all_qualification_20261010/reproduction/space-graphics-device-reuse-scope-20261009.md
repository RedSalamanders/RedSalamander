# ViewerSpace bounded idle graphics-device slot: feasibility scope

Read-only proposal. No implementation, build, test, source, or tracked-document changes. This does not claim the Open-to-successful-current-map 100 ms target is achievable or passed.

## Decision

A single bounded idle slot is a plausible experiment for the expensive D3D device-creation stage, but it is not a drop-in reuse of the current `RendererResources`. The safe narrow candidate is an idle device-only core (D3D11 device plus the minimum immutable metadata needed to recreate its consumer context). On acquisition, create/rebind per-viewer DXGI/D2D resources and a fresh swap chain for that viewer HWND. Do not retain a swap chain, target bitmap, render target, static treemap bitmap, brushes, or HWND in the module slot. If further savings require retaining D2D context/factory objects, first resolve and test their thread affinity and cross-instance state reset.

Existing evidence reported separately by the parent shows D3D device setup at median 29 ms / p95 35 ms. Reusing the device could avoid some of this stage in a sequential reopen, but the evidence does not establish how much of the 100 ms endpoint it would save or whether p95 would pass.

## Shared-helper check (performed first)

`Specs/Core/Core_SharedHelpers.md` names `Common/HwndRenderTargetResources.h` for the exact FunctionBar/StatusBar factory/target/brush lifecycle. That is not the ViewerSpace D3D11 + DXGI flip-swap-chain + D2D device-context contract. No canonical graphics-device cache appears in the catalog or `Common/`; do not wrap/recreate that helper under a graphics-cache name. If this plugin-specific slot is implemented, document why its one-owner plugin lifetime, D3D device-loss policy, and HWND-free state differ from the existing HWND target helper. A generally reusable cache would need a fresh shared-helper extraction review and catalog/spec/tests.

## Source facts and lifecycle

- `Plugins/ViewerSpace/ViewerSpace.h:645-657` stores D3D device/context, DXGI factory, D2D device/context, swap chain, target bitmap and dimensions together per viewer. Instance members also own a single-threaded D2D factory, render target, brushes, text formats and a device-dependent static bitmap (`:659-686`).
- `ViewerSpace.cpp:5882-6150` lazily creates the D3D device with `DxUi::CreateD3D11DeviceWithWarpFallback`, derives DXGI/D2D resources, then creates the HWND swap chain and target bitmap. `CreateSwapChainForHwnd` ties that swap-chain object to the current window; it is not reusable across reopened HWNDs.
- `DiscardDirect2D` (`ViewerSpace.cpp:6460-6502`) invalidates the static bitmap, detaches the D2D target, and resets target/swap-chain/context/device/factory-dependent drawing resources. `OnDestroy` invokes it and releases the factories (`:3302-3341`). DPI change also invokes it (`:3365-3385`). Device-loss paths invoke it on `D2DERR_RECREATE_TARGET`, `DXGI_ERROR_DEVICE_REMOVED`, or `DXGI_ERROR_DEVICE_RESET` (`:3657-3667`, `:4947-4958`). A returned cache candidate must therefore be distinct from this all-resources discard path, or the device-loss path could republish a known-bad device.
- `Factory.cpp:112-125` exposes `RedSalamanderPluginShutdown`, `RedSalamanderPluginCanUnloadNow`, and `RedSalamanderPluginRetainModuleUntilProcessExit`. Shutdown currently clears the scan cache/scheduler and class brush (`ViewerSpace.cpp:2122-2143`); `CanUnload` checks worker unload gates only. `PluginModuleLifecycle::UnloadModule` calls shutdown before `CanUnloadNow`, resource unregister, and `FreeLibrary`; at process shutdown it queries the retain export after shutdown. Viewer plugin API requires live COM instances to be closed/released before this module quiet point (`Specs/Plugins/Plugins_PluginAPI.md:144-152`). Thus a slot can be synchronously emptied in the existing shutdown export before either runtime unload or the process-shutdown retain decision. The export alone does not define a graphics owner thread, however.
- The current plugin returns TRUE from `RedSalamanderPluginRetainModuleUntilProcessExit`, so the host keeps the DLL mapped during process teardown after running shutdown. Any slot still held after that shutdown would intentionally retain graphics resources until OS teardown.
- The Direct2D factory is created `D2D1_FACTORY_TYPE_SINGLE_THREADED` (`ViewerSpace.cpp:5896-5901`). `IViewer`/module shutdown documentation does not establish that every unload/shutdown call is on the same thread that created the cached D2D objects. Do not put single-threaded D2D factory/context state in a cross-thread module slot without an explicit owner-thread contract or owner-thread drain.

## Proposed bounded ownership contract

1. At most one idle slot exists, independent of the number of live viewers. An active viewer owns its renderer as today; it never aliases an in-use immediate context with another viewer. On close, publish only a healthy eligible device-only bundle when the slot is empty; otherwise release the closing bundle. A second live viewer must create/own its own device when the slot is empty after the first borrower took it.
2. Bind the slot to its creating UI thread and acquire only on that thread. Prefer storing only the D3D device and scalar feature-level/driver metadata; `GetImmediateContext` returns that device's existing associated immediate context, not a new independent context. Treat that context as retained device state, enforce one active owner, clear/flush/reset it before slot publication and before reuse, then create the DXGI/D2D viewer context, target bitmap, and swap chain for the new window. If shutdown may run on another thread, prove D3D-device release is valid there or marshal slot destruction to its owner before unload; plugin API currently gives no such guarantee.
3. Return-to-slot is allowed only after window-specific D2D target/context references, target bitmap, render target, static bitmap, and swap chain are released. Clear/flush any retained immediate-context state before slot publication. Never cache HWND, swap-chain, back-buffer surface, or target-bitmap references.
4. Any device-removed/reset or D2D-recreate-target outcome poisons that bundle and bypasses the slot. DPI/theme/resize paths must recreate window-specific resources without publishing stale targets. Define how SetConfiguration/cache disable interacts with the graphics slot; scan-cache policy changes must not implicitly evict unrelated roots or leave an undocumented device owner.
5. Shutdown is idempotent and clears the slot before `CanUnloadNow` and resource-owner unregister. If an owner-thread drain cannot complete, unload must remain deferred (with an appropriate unload predicate), never release thread-affine COM on the wrong thread.

The smallest candidate likely avoids caching D2D factories, contexts, swap chains, or HWND-bound objects. Before implementation, compare that scope against the creation-stage measurements; if it does not plausibly remove meaningful work, do not widen retention speculatively.

## Required unresolved checks before implementation

- Establish the actual `Open`/`Close`/module-shutdown thread on normal, embedded, settings-refresh unload, and process-shutdown paths. Confirm no concurrent or reentrant render can touch a bundle while it is idle or transferred.
- Prove acquire/return atomicity for two simultaneous ViewerSpace instances and for a Close racing a new Open. Define single-slot replacement/drop behavior; no wait, unbounded queue, or device-pool growth.
- Device-loss fault injection must prove a poisoned device is never reissued; cold device recreation still recovers with hardware/WARP fallback. Exercise resize, DPI change, target recreation, close-before-first-paint, and shutdown with a populated slot.
- Add observability for slot hit/miss/drop/poison/shutdown-release and retained slot ownership. Existing `ViewerOwnedBytes` admission intentionally treats graphics resources as opaque (`Specs/Plugins/Plugins_ViewerSpace.md:279`); process private bytes/working set alone cannot establish driver/GPU allocation size. Record the one-slot bound plus process-memory phases and avoid claiming an exact graphics byte cap without a trustworthy API.
- Preserve the current Close behavior as a contract decision: today each instance discards its renderer on destroy. A slot deliberately retains one device after Close and changes the quiet-after-close memory observation. Measure after Close and after module shutdown; verify no growth beyond one retained slot across repeated fresh-instance cycles and across simultaneous viewers.
- Rendering work is performance-sensitive. If pursued, reuse/add creation-stage and slot metrics, deterministic same-thread sequential and overlapping-viewer selftests, device-loss/shutdown tests, and archived perf evidence. Run the unchanged fresh-`IViewer` cached-reopen endpoint and unchanged 100 ms p95 target, with matched runtime binaries and counterbalanced repetitions. The slot result is a hypothesis until that endpoint passes.
